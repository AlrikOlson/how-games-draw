Draw Calls & Instancing

A draw call is the CPU telling the GPU "draw this mesh with this material, now". The GPU reads one in a blink, but the CPU spends microseconds setting each one up, and a few thousand of them can eat the whole frame while the GPU sits waiting. Batching, instancing and indirect draws all shrink the same number: how many times per frame the CPU has to say "draw". The part people get wrong is that on Vulkan and DX12 the draw itself is nearly free, and the cost moved into the culling, sorting and texture bookkeeping around it.

What one draw call costs

A market street full of crates, barrels and trees, and every prop is one order to the GPU. Move the sliders and watch which of the CPU or the GPU runs out of time first.

budget 16.7 ms · 512 draws per submit

A draw call is one order from the CPU to the GPU: draw this mesh, with this material, now. The GPU reads it in a blink. The CPU spends about 5 microseconds getting each one ready, and 3,000 of them fill 15 of your 16.7 ms. A frame full of small draws can leave the GPU idle, and a faster graphics card fixes nothing.

The real version

Before the GPU sees anything, every draw makes the CPU do four things. It binds a pipeline, checking the shader stages and fixed settings. It updates a descriptor set or constant buffer, the records that say where this draw's textures and material values live. It binds the vertex and index buffers. Then it writes the draw command.

On D3D11 and OpenGL each of those steps went through a driver that re-checked everything on every call, and 5 to 20 µs per draw was normal. On Vulkan and DX12 the same four steps run in your own code and cost 1 to 3 µs. They still run once per draw.

The GPU only starts on a command buffer, the recorded list of draws, once the CPU submits it. While the CPU is still recording the next batch, the GPU waits. When the CPU lane crosses the 16.7 ms line the frame is CPU bound: the GPU finishes early, idles, and a faster GPU changes nothing. Push the GPU slider up and it flips: the CPU finishes first and the GPU lane sets the frame time.

In words: CPU time is draws times the cost of the four steps, GPU time is draws times its own cost, and the frame lasts as long as the slower of the two.

t_cpu = N · (Σ state_change_cost + submit_cost) = 3000 · (2.0 + 1.5 + 0.5 + 1.0) µs = 15.0 ms t_gpu = N · gpu_cost_per_draw (fixed per-frame passes not modelled) frame = max(t_cpu, t_gpu_end) fps = 1000 / frame idle = 1 − gpu_busy / frame

N is draws per frame. The four costs in the bracket are the pipeline bind, the descriptor update, the buffer binds and the draw write, in microseconds. t_gpu_end is when the GPU finishes its last submitted batch. idle is the share of the frame the GPU spent waiting.

What this code does: loops over every object, does the four binds, writes one draw, and only hands the whole list to the GPU at the end.

// the naive render loop, one draw per object (C++)
for (const Draw& d : draws) {
  cmd.bindPipeline(d.pso);            // ~2.0 µs: validate stages, patch state
  cmd.bindDescriptorSet(d.material);  // ~1.5 µs: textures + material constants
  cmd.bindVertexBuffer(d.mesh.vb);    // ~0.5 µs
  cmd.bindIndexBuffer(d.mesh.ib);
  cmd.drawIndexed(d.mesh.indexCount); // ~1.0 µs to write; the GPU reads 5 words
}
queue.submit(cmd);                    // GPU starts here, not at the first draw

The GPU reads a draw in nanoseconds, the CPU spends microseconds writing it, and with thousands per frame the CPU is what runs out of time.

Sort draws so binds become free

The 200 props on the market square, in the order the CPU sends them. Sort that list by one packed key and watch most of the state changes disappear.

each strip is one prop's draw · gap = state change

A bind that doesn't change costs nothing. If two draws in a row use the same pipeline, the second one skips that bind. So the renderer sorts the draw list so draws that share the priciest state sit next to each other. It's a delivery driver grouping stops by street: the trips between them vanish.

What you're seeing

The top list is the order the level file happens to list the props, the bottom is the same 200 sorted. The first 32 draws of each list are drawn as the props they stand for, so you can watch the sort put crates next to crates and trees next to trees.

Under the prop icons, three colour rows cover all 200 draws: pipeline in amber, which is the shader (wood, leaf, stone), material in blue, which is the paint or bark texture, and mesh in grey, the shape. A run of one colour is a stretch of draws sharing that state, and every break in a run is a state change, counted in red on the right. Under the lists is the 64-bit sort key with its fields laid out from the most expensive change on the left to the cheapest on the right. At the bottom, two bars stack the estimated CPU time for each list by what changed.

The real version

The draw itself is the cheap part. The binds before it are the expensive part, and a bind that does not change costs nothing. So the renderer packs everything that determines state into one 64-bit integer, puts the most expensive change in the most significant bits, and sorts the list once. Draws next to each other then share a pipeline, then a material, then a mesh, and the loop only rebinds when a field differs from the previous draw.

Depth goes in the low bits so that within one mesh the draws still run front to back. That helps early-Z, the GPU's trick of skipping pixels already covered by something closer. Transparent draws need the opposite order, back to front, so for them depth moves into the high bits and state sorting is given up. The layer field sits at the very top for that reason: it keeps opaque and transparent draws apart before any other field applies.

In words: stack the fields into one number, dearest change on top, then sort. CPU time is the submits plus one cost for each time a field changes down the list.

key = layer<<60 | pipeline<<48 | material<<32 | mesh<<16 | depth16 t_cpu ≈ N · submit + Σ_changes cost(field) pipeline 2.0 µs · material 1.5 µs · mesh 0.5 µs · submit 1.0 µs

The numbers after the << are how far up the 64-bit key each field is shifted. depth16 is the distance squeezed into 16 bits. Σ_changes cost(field) means: for each place in the sorted list where a field differs from the previous draw, add that field's bind cost.

What this code does: shifts each field into its slot in one 64-bit number, then sorts the draws by that number.

// pack a sort key (C++). Higher bits = more expensive to change.
uint64_t packKey(uint8_t layer, uint16_t pso, uint16_t mat,
                 uint16_t mesh, float depth01) {
  uint64_t k = 0;
  k |= (uint64_t)(layer & 0xF)   << 60;
  k |= (uint64_t)(pso   & 0xFFF) << 48;
  k |= (uint64_t)mat             << 32;
  k |= (uint64_t)mesh            << 16;
  k |= (uint64_t)(depth01 * 65535.0f); // low bits: front to back inside a mesh run
  return k;
}
std::sort(draws.begin(), draws.end(),
          [](auto& a, auto& b) { return a.key < b.key; }); // radix sort in practice

Sort the draw list by one packed key, priciest state in the top bits, and most binds turn into no-ops.

Instancing: one mesh, thousands of copies

The player stands in a forest of 5,000 trees that all share one mesh. Drag the player and the aim point, and compare three ways of getting the trees in view onto the screen.

Five thousand trees share one mesh, so drawing them one at a time is 5,000 orders for the same thing. Instancing sends one order with a count of 5,000 and a list of where each copy goes. One draw, 320 KB of positions, and every tree can still move. It is the photocopier set to 5,000 copies: one press, the machine handles the rest.

What you're seeing

For individual draws it shows the command buffer repeating the same bind-and-draw pair 5,000 times against the 16.7 ms budget.

The real version

Instancing keeps one copy of the mesh and one draw call, and moves the per-object data into a buffer that the vertex shader indexes with gl_InstanceID, the number of the copy it is currently working on. Each instance here is a 3×4 world matrix, the numbers that place and scale the tree, plus a colour: 64 bytes. So 5,000 trees are 320 KB of instance data next to a 12.8 KB mesh. The CPU issues one draw with instanceCount = 5000 and is done.

Static batching is the older answer: move every tree's vertices into world space ahead of time and merge them into one giant vertex buffer. That is also one draw, but the mesh is copied 5,000 times, the index buffer outgrows 16-bit indices, and nothing can move without a rebuild. Instancing wins on memory by more than two orders of magnitude and costs one buffer load per vertex.

Without culling the GPU still processes all 5,000 instances. The ones outside the frustum run the vertex shader and get thrown away afterwards. The next section moves that decision onto the GPU as well.

In words: instance memory is count times record size; a static batch is count times the whole mesh; each vertex is placed by the 3×4 matrix in its instance's record.

instance_bytes = N × stride = 5000 × 64 B = 320,000 B static_batch = N × (vb + ib) = 5000 × (12,800 + 10,800 → 21,600 with 32-bit indices) B ≈ 172 MB world_pos = vec4(p, 1) · mat3x4 3 rows × 16 B = 48 B, + rgba 16 B = 64 B

N is the tree count, stride the bytes per instance record. vb and ib are the vertex and index buffer sizes of one mesh. p is a vertex position in the mesh's own space, mat3x4 the matrix that moves it into the world.

What this code does: reads the record for the copy it is on, moves the vertex into the world with that record's matrix, and passes the colour along.

// instanced vertex shader (GLSL). HLSL: SV_InstanceID, StructuredBuffer.
struct Instance { mat3x4 world; vec4 color; };       // 64 bytes, std430
layout(std430, binding = 0) readonly buffer Instances { Instance inst[]; };
layout(location = 0) in vec3 aPos;
uniform mat4 uViewProj;
out vec4 vColor;
void main() {
  Instance I = inst[gl_InstanceID];     // Vulkan: gl_InstanceIndex includes firstInstance
  vec3 wp = vec4(aPos, 1.0) * I.world;  // row-major 3x4: one vec4 per row
  gl_Position = uViewProj * vec4(wp, 1.0);
  vColor = I.color;
}

Let the GPU write its own draws

The player walks through a village of 6,579 props in 200 kinds: trees, bushes, crates, barrels, rocks, fences. Drag the player; a GPU pass tests every prop against the view and fills in the draw arguments while the CPU issues the same one command every frame.

hover a bar or a prop for its args

Instancing still leaves the CPU deciding what's in view and how many copies to ask for. An indirect draw hands that job to the GPU: the CPU points at a buffer and says "the numbers in here are the draw". A small GPU program fills the buffer by testing every object against the camera. The CPU's work per frame becomes a constant, whether the scene holds 500 objects or 50,000.

What you're seeing

The map is the village from above. Every prop is one instance of one of 200 mesh types, drawn in its own colour: greens for trees, pines and bushes, browns for crates, barrels, fences and stumps, grey for rocks. A prop with an amber ring passed the camera test and gets drawn. The dim ones failed it and are skipped. Below the map is the argument buffer: one bar per mesh type, grouped by kind of prop, and the bar's height is how many copies of that type survived. A flat red bar is a type with zero survivors.

The line under the bars prints the four numbers in one type's argument record, and the last line is the single command the CPU issued. Hover a bar or a prop to inspect its type.

The real version

With an indirect draw the CPU no longer supplies the arguments. It points at a buffer and says "the four uints at this offset are the draw". A compute shader, a GPU program that runs one thread per object rather than per pixel, fills that buffer. Each thread tests one instance against the frustum. On pass it does an atomicAdd, a counter increment that is safe when thousands of threads hit it at once, on its mesh type's instanceCount, and writes the instance index into a compacted list. The vertex shader then reads inst[visible[gl_InstanceIndex]].

MultiDrawIndirect extends this to an array of argument records, one per mesh type, run by a single CPU call. The 200 commands here are one vkCmdDrawIndexedIndirect. A mesh type whose count ended at zero is an empty draw the GPU skips in a few cycles. Or the compute pass compacts the array and writes the survivor count to a count buffer for DrawIndirectCount. Either way the CPU's draw work per frame is a constant, no matter how many objects the scene holds.

In words: each mesh type owns a 16-byte record and a fixed stretch of the visible list; every surviving instance grabs the next slot in its type's stretch and bumps that type's count.

args[m] = { vertexCount, instanceCount, firstVertex, firstInstance } 4 × uint32 = 16 B firstInstance[m] = Σ_{k<m} capacity[k] prefix sum, computed once slot = atomicAdd(args[m].instanceCount, 1); visible[firstInstance[m] + slot] = i CPU per frame: 1 dispatch + 1 multi-draw, independent of N

m is a mesh type, i an instance. capacity[k] is the most instances type k can ever have, so firstInstance[m] is where type m's stretch of the visible list begins. slot is the position this instance won inside that stretch.

What this code does: one thread per instance tests it against the camera, and survivors append themselves to their mesh type's draw record.

// GPU culling that appends to the indirect args (GLSL compute)
struct DrawArgs { uint vertexCount, instanceCount, firstVertex, firstInstance; };
layout(std430, binding = 1) buffer Args    { DrawArgs args[]; };   // zeroed each frame
layout(std430, binding = 2) buffer Visible { uint visible[]; };
layout(local_size_x = 64) in;
void main() {
  uint i = gl_GlobalInvocationID.x;
  if (i >= uInstanceCount) return;
  Instance I = inst[i];
  if (!sphereInFrustum(I.boundsCenter, I.boundsRadius, uPlanes)) return;
  uint m    = I.meshType;
  uint slot = atomicAdd(args[m].instanceCount, 1u);   // GPU-side counter
  visible[args[m].firstInstance + slot] = i;          // firstInstance is a fixed prefix
}
// CPU, once per frame:
// vkCmdDrawIndexedIndirect(cmd, argsBuf, 0, 200, sizeof(DrawArgs));

With indirect draws the GPU culls and writes its own draw arguments, and the CPU's per-frame draw work stops depending on scene size.

Bindless and the material problem

48 crates on the market with 9 different paint jobs. See why different textures break a batch apart, and compare four ways of putting it back together.

hover an atlas tile for its UV remap

Instancing only works while every copy uses the same textures. Give each crate its own paint job and the batch splits back into one draw per material. The old fixes glue the textures together into one big image. Bindless skips the gluing: every texture goes in one long list and the shader picks by number, so the batch never has to split.

What you're seeing

Top left is a 4096² atlas: one big sheet with every crate paint job packed in as a tile. The red bands on each tile are bleed, the strip near the edge where the blurry lower-resolution copies of the sheet pull in colour from the neighbouring tile. Top right is a texture array, the same paint jobs stacked as separate layers with no shared edges. Under it is what the player sees: a near crate and a far crate with the same paint job. The far one is sampled from the blurry mip level, so its neighbours' paint creeps in at the edges.

The bottom row is the 48 crates lined up on the market ground, coloured by paint job and grouped by pipeline, the shader they use. Each white bracket is one draw. Fewer brackets means fewer draws.

The real version

Instancing needs every instance in a draw to use the same bound textures. Give each crate its own paint texture and the batch splits back into one draw per material, because a descriptor bind sits between them. The two classic fixes remove the bind by removing the separate texture. A texture array puts every material in one resource, one layer each, picked by an integer from the instance data. An atlas packs them into one 4096² image and remaps UVs, the coordinates that say where on the texture a vertex lands, with a scale and an offset.

The atlas has a cost. Mipmaps, the chain of half-size copies the GPU samples from at a distance, are built on the whole image. At level L each mip texel covers 2^L base texels and the filter reaches that far into the neighbouring tile. Wrapping UVs do not work at all. A texture array has neither problem, but every layer must share size, format and mip count.

Bindless removes the bind instead of the texture. The shader indexes a descriptor array holding every texture with an integer from a material buffer, so draws only need to split on pipeline. With an uber-shader, one shader that handles every material's features through flags, that count is one, and the whole scene is a single indirect draw.

In words: an atlas tile is found by scaling and shifting the UVs; bleed doubles with every mip level; draws split wherever the pipeline or the bound descriptors differ.

uv' = uv · scale + offset scale = tile / 4096, offset = tileOrigin / 4096 bleed(L) = 2^L texels L = 8 on a 1024² tile: 256 texels per edge, 25 % of the area left draws = unique (pipeline, bound descriptor set) pairs pipelines = unique shader variants bindless does not lower this; an uber-shader does

uv is the texture coordinate the mesh came with, uv' the one that lands in the right atlas tile. L is the mip level, and a texel is one pixel of a texture. The 25 % is what remains of a 1024² tile after 256 texels are lost on each of its four edges.

What this code does: reads the pixel's material number, looks up that material's texture number, and samples from the big texture list at that number.

// bindless fragment shader (GLSL, VK_EXT_descriptor_indexing)
#extension GL_EXT_nonuniform_qualifier : require
layout(set = 0, binding = 0) uniform sampler2D textures[];   // every texture in the scene
struct Material { uint albedo; uint normal; uint orm; uint flags; };
layout(std430, set = 0, binding = 1) readonly buffer Materials { Material mats[]; };
layout(location = 0) flat in uint vMaterialId;  // came from the instance record
void main() {
  Material m = mats[vMaterialId];
  vec3 albedo = texture(textures[nonuniformEXT(m.albedo)], vUV).rgb; // index may differ per pixel
  ...
}
// HLSL SM 6.6: Texture2D t = ResourceDescriptorHeap[m.albedo];

Textures are what split a batch; atlases and arrays merge the textures, bindless merges the lookup, and only an uber-shader merges the pipelines.

Tradeoffs

Every technique buys a lower CPU cost per object with some mix of memory, rigidity and hardware requirements.

Read this table top to bottom as a ladder: each row cuts the CPU's per-object work further than the one above, and pays for it in memory, in what is allowed to differ between objects, or in the hardware it needs. You are choosing how much of the per-draw work to move off the CPU and what you give up to do it.

One trap: "draw calls are expensive" was a statement about D3D11 and OpenGL, where the driver re-checked state inside every call. On Vulkan and DX12 that overhead is gone and a raw draw is a few hundred nanoseconds. The cost moved to managing descriptors, and the real limit became how many objects the CPU can cull and sort per frame, which is why culling and sorting now move onto the GPU too.
