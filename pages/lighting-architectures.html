Forward, Deferred & Clustered

A renderer lights a picture by doing one job over and over: for each spot on a surface, add up every light that reaches it. Forward, deferred and clustered are three places to put that job, and the choice decides how much memory traffic you pay and how many lights you can afford. Deferred does not make lighting cheaper on its own. It only pays off once many lights overlap the same pixels, and that is the part people get backwards.

Forward: light it while you draw

Drag a light or a box on the left and watch the per-pixel cost change on the right.

scene26 m × 26 m · near 0.5 m · far 24 m
hover a pixelheat = fragments × lights

A forward renderer draws objects one after another, and every fragment runs the whole light loop the moment it is drawn. A fragment is one candidate pixel that a draw produces. If a nearer object covers that pixel later, the earlier work is thrown away, but you already paid for it. So the bill is overdraw times lights.

The real version

Each draw binds its own list of lights. For every pixel the draw covers, the fragment shader (the small program that computes one pixel's colour) loops over that list and adds each light's contribution. The depth test, which keeps only the nearest fragment per pixel, runs after the shading, so a losing fragment costs the same as a winner.

A depth prepass fixes the overdraw factor. It draws the scene once with a shader that writes only distance, so the colour pass can skip any fragment that is not the winner. It does nothing about the light factor: with 64 lights each surviving fragment still runs 64 iterations, even if no light is anywhere near it.

In words: the cost is every covered pixel of every object, times the number of lights.

cost_forward ≈ Σ_objects pixels_covered(o) × N_lights fragments = visible pixels × overdraw // no prepass grid → 1080p = ×900 (each cell is a 30×30 px block)

pixels_covered(o) is how many fragments object o produces, N_lights is the length of the light list, and ×900 converts one cell of this 64×36 grid into a 30×30 block of real 1080p pixels.

What this code does: for one fragment, it walks every light bound to the draw, skips the ones out of reach, and adds the rest. The depth test may throw the result away afterwards.

// forward fragment shader: runs once per covered pixel, per draw
uniform Light lights[MAX_LIGHTS];  uniform int numLights;   // bound per draw
vec3 N = normalize(vNormal), V = normalize(-vPos);
vec3 color = albedo * ambient;
for (int i = 0; i < numLights; i++) {        // every light, every fragment
  vec3  L = lights[i].pos - vPos;
  float d2 = dot(L, L);
  if (d2 > lights[i].radius * lights[i].radius) continue;  // still costs the fetch and the branch
  L *= inversesqrt(d2);
  color += brdf(N, V, L, albedo, rough, metal) * lights[i].color * falloff(d2, lights[i].radius);
}
outColor = vec4(color, 1.0);   // depth test may throw this away after all that

Forward pays fragments times lights, and overdraw makes you pay for pixels you never see.

Deferred: save the surface, light it once

Deferred splits the work in two. First pass: draw everything and write down what the surface looks like at each pixel, no lighting yet. Second pass: light each pixel exactly once from those notes. Overdraw and object count drop out of the light loop, but writing and reading the notes costs memory traffic every frame, with one light or a hundred.

The real version

The geometry pass writes the G-buffer: colour, an encoded normal, roughness, metalness and depth. Depth plus the pixel position is enough to rebuild where the point sits in the world, so nothing else about the geometry needs to survive. The lighting pass then draws each light as a volume, a sphere mesh or a screen rectangle, and shades only the pixels the volume covers. The loop runs once per pixel, so overdraw and object count no longer multiply it.

The price is bandwidth, the bytes moved to and from memory. The G-buffer is written for every fragment that passes the depth test and read for every pixel that gets lit, and that traffic is the same at one light or a hundred. With eight lights that is more traffic than forward would ever generate; with 64 overlapping lights it is the only sane option.

In words: pay to write the G-buffer (more with overdraw), pay to read it, then pay only for the lights that touch each pixel.

cost_deferred ≈ pixels × bytes_gbuffer (write, × overdraw) + pixels × bytes_gbuffer (read) + Σ_pixels lights_touching(p) G-buffer bytes = Σ layer formats (RGBA8 + RG16 + RGBA8 + D32 = 16 B)

pixels is the target size, bytes_gbuffer is the total from the table, and lights_touching(p) is how many light volumes cover pixel p. The default layout adds up to 16 B.

What this code does: the first block writes three layers and no lighting; the second reads them back for one pixel, rebuilds its position from depth, and adds one light's contribution.

// geometry pass: no lights here, just describe the surface
layout(location=0) out vec4 gAlbedo;    // RGBA8, .a spare
layout(location=1) out vec2 gNormal;    // RG16, octahedral
layout(location=2) out vec4 gMaterial;  // rough, metal, ao, shadingModelId
gAlbedo = vec4(albedo, 0); gNormal = octEncode(N); gMaterial = vec4(rough, metal, ao, model);

// lighting pass: one fragment per pixel inside the light volume
float z   = texelFetch(gDepth, px, 0).r;
vec3  P   = reconstructViewPos(px, z, invProj);     // depth + pixel is enough
vec3  N   = octDecode(texelFetch(gNormal, px, 0).rg);
vec4  M   = texelFetch(gMaterial, px, 0);
if (M.a != MODEL_STANDARD) discard;                 // one lighting model per pass, branch per model
outColor += brdf(N, normalize(-P), normalize(light.pos - P), ...) * falloff(...);   // additive blend

Three things a G-buffer cannot do. MSAA, the hardware anti-aliasing that keeps several samples per pixel, would need every layer at 4× samples and a per-sample lighting pass, so nobody does it and deferred renderers use TAA instead. The lighting model is baked into the pass, so a cloth or skin BRDF (the formula for how a material reflects light) costs a branch or a stencil bit per pixel. And a transparent surface has no single depth, so glass, particles and hair go through a forward pass afterwards regardless.

Deferred trades a fixed memory bill for a light loop that runs once per pixel, and that only wins when many lights overlap.

Tiled culling: a short light list per tile

Hover a tile on the left to see its wedge of space and which lights it keeps.

hover a tileheat = lights in the tile list
tile frustumgreen = kept, dim = culled

Most lights are nowhere near most pixels, so cut the screen into small squares called tiles and give each one a list of only the lights that can reach it. Neighbouring pixels want almost the same lights, so one list serves a whole tile. It is like sorting mail by postcode before delivering. The trick fails on tiles where a near object meets a far one, because their list has to cover everything in between.

The real version

One compute shader thread group per tile reads the depth buffer, finds the nearest and farthest depth in the tile, and builds a small frustum: four side planes through the eye plus those two depth bounds. Each light is a sphere, and it is kept if it pokes inside all four planes and the depth range. The list is a few dozen indices, written once and read by every pixel in the tile. The same list works in front of a forward shader (Forward+) or a deferred lighting pass (tiled deferred).

The failure is the red tile. Where a near box meets the far floor, the depth range spans most of the scene and the little frustum becomes a long wedge that every light along the view direction touches. Every pixel in that tile, near or far, then walks the whole list. Silhouette edges are exactly where this happens, and a scene is mostly silhouette edges.

In words: build four tilted planes for the tile, then keep a light if its sphere is not fully outside any plane and its depth overlaps the tile's depth range.

tile planes through the eye: n_left = norm(1, 0, −x_a·tanH) n_right = norm(−1, 0, x_b·tanH) n_bot = norm(0, 1, −y_a·tanV) n_top = norm(0, −1, y_b·tanV) keep light (c, r) ⇔ n_i·c ≥ −r for all four and z_min − r ≤ c.z ≤ z_max + r

x_a, x_b, y_a, y_b are the tile's edges on screen from −1 to 1, tanH and tanV are the tangents of the view's half-angles, c and r are the light's centre and radius, and z_min, z_max are the tile's depth bounds.

What this code does: every thread reads one depth, the group agrees on the min and max, then the 256 threads split the lights between them and each appends the ones that pass to a shared list.

// compute shader, one 16×16 thread group per tile
groupshared uint gMinZ, gMaxZ, gCount;  groupshared uint gList[MAX_PER_TILE];
float z = depthTex[pixel];                 // linearize first if depth is nonlinear
if (z < farPlane) { InterlockedMin(gMinZ, asuint(z)); InterlockedMax(gMaxZ, asuint(z)); }
GroupMemoryBarrierWithGroupSync();
float4 planes[4] = tileFrustum(tileId, invProj);   // four side planes, eye at origin
for (uint i = threadIndex; i < numLights; i += 256) {   // 256 threads share the lights
  Light L = lights[i];
  bool inside = L.pos.z + L.radius >= asfloat(gMinZ) && L.pos.z - L.radius <= asfloat(gMaxZ);
  for (int p = 0; p < 4 && inside; p++) inside = dot(planes[p].xyz, L.pos) >= -L.radius;
  if (inside) { uint slot; InterlockedAdd(gCount, 1, slot); if (slot < MAX_PER_TILE) gList[slot] = i; }
}
GroupMemoryBarrierWithGroupSync();
if (threadIndex < gCount) tileLightIndices[tileId * MAX_PER_TILE + threadIndex] = gList[threadIndex];

Tiles shrink the light loop to the lights near each screen square, except where a tile spans a big depth gap.

Clustered: slice the tiles by distance

Hover a pixel on the left to pick which tile row appears on the right, and drag the slider to cut finer slices.

Take each tile and cut it into slices by distance from the camera. Now a near box and the far floor sit in different clusters with different light lists, so the depth-gap problem goes away. The slices are fixed in advance, so the lists never touch the depth buffer and work for glass and particles too.

The real version

A cluster is one tile times one depth slice, small enough to bound with a box in view space. A sphere-versus-box test is tighter than the four-plane test a tile uses, which over-includes lights near the corners of a long wedge. The slice planes are chosen once, spaced so that each slice is the same fraction deeper than the last, which matches how perspective compresses distance. Because the grid is fixed, the light lists can be built before the geometry is drawn, or even on the CPU, and they serve transparent surfaces too since no depth read was involved.

The cost is the list count. Sixteen tile columns by nine rows by 24 slices is 3,456 lists for this grid, and at 1080p with 16-pixel tiles it would be 120×68×24, close to 200,000. Most of them are empty or hold one or two lights, so the storage is a small header per cluster plus a packed index list, and the average list a pixel walks is what drops.

In words: turn a depth into a slice number with a logarithm, find the cluster, then keep a light if the nearest point of the cluster's box is inside its sphere.

slice(z) = floor( log(z / near) / log(far / near) · N ) z_k = near · (far / near)^(k / N) // slice k starts here cluster = (tile.x, tile.y, slice) list memory = clusters × 8 B + entries × 2 B keep light ⇔ |clamp(c, aabb_min, aabb_max) − c|² < r² // sphere vs cluster box

z is the view depth, near and far are the camera's near and far planes, N is the slice count, k is a slice index, c and r are the light's centre and radius, and aabb_min, aabb_max are the corners of the cluster's box.

What this code does: works out which cluster the fragment sits in, reads that cluster's header, and loops over only the lights in its list.

// clustered lighting in the fragment shader (forward or deferred, same code)
float zView  = -vPos.z;
uint  slice  = uint(log(zView / near) * sliceScale);       // sliceScale = N / log(far/near)
uint3 c      = uint3(gl_FragCoord.xy / TILE_PX, slice);
uint  id     = c.x + tilesX * (c.y + tilesY * c.z);
uint2 hdr    = clusterHeaders[id];                    // .x = offset into index list, .y = count
vec3 color = albedo * ambient;
for (uint i = 0; i < hdr.y; i++) {                  // only the lights near this cluster
  Light L = lights[lightIndices[hdr.x + i]];
  color += shade(L, vPos, N, V, albedo, rough, metal);
}
// transparent surfaces run the same loop: no depth buffer was read to build the lists

Clusters give each small piece of the view its own light list, fixed ahead of time, so near and far stop sharing a bill.

Three renderers, same frame, different memory. Forward+ keeps only depth and the final colour. Deferred keeps the whole surface and forgets the triangle. A visibility buffer keeps only which triangle landed on the pixel, one 32-bit number, and rebuilds everything else later.

The real version

The visibility buffer stores one 32-bit id per pixel, instance plus triangle index, and nothing else. The material pass then fetches the three vertices again, recomputes the barycentrics from the pixel position, interpolates the attributes and shades, all in one full-screen pass with no geometry overdraw at all.

That makes it the smallest footprint and the cheapest geometry pass, which is why Nanite uses it for micro-triangle meshes where rasterising is the bottleneck. It also brings back MSAA and material variety, since the id is a per-sample integer and the material pass can branch or sort by material id. The cost moves to the resolve: three vertex fetches and a derivative computation per pixel.

In words: pack which object and which triangle into one integer, then solve for the three weights that place the pixel inside that triangle.

visibility id = (instanceId << 8) | triangleIndex // 32 bits, 24 + 8 in Nanite's case is 32 + 32 with depth barycentrics: solve p_screen = λ0·s0 + λ1·s1 + λ2·s2, Σλ = 1 (perspective-correct via 1/w)

instanceId and triangleIndex name the triangle, s0, s1, s2 are its three vertices on screen, λ0, λ1, λ2 are the barycentric weights, and 1/w is the perspective correction.

What this code does: reads the id, looks up the triangle's three vertices, works out where the pixel sits inside the triangle, then evaluates the material and lights it.

// visibility buffer material pass, full-screen, one invocation per pixel
uint id = visBuf[px];  if (id == 0) return;             // sky
Instance inst = instances[id >> 8];
uint3 tri = indexBuffer[inst.indexBase + (id & 0xFF) * 3];
Vertex v0 = fetch(inst, tri.x), v1 = fetch(inst, tri.y), v2 = fetch(inst, tri.z);  // 3 fetches per pixel
Bary b = computeBarycentrics(v0.clip, v1.clip, v2.clip, px);   // also gives ddx/ddy for texture LOD
vec2 uv = b.l0 * v0.uv + b.l1 * v1.uv + b.l2 * v2.uv;
Material m = evalMaterial(inst.materialId, uv, b);             // branch by material id, or one pass per material
outColor = shadeClustered(m, P, N);

Store the surface (deferred), or store the triangle and rebuild the surface (visibility buffer); the second is smaller and gets MSAA back.

Tradeoffs

Memory and bandwidth are at 1080p with the layout chosen above, no MSAA. Light scaling is how the per-frame cost grows as lights are added.

Read this as a checklist. You are choosing between anti-aliasing and free choice of materials on one side and cheap handling of many lights on the other. The memory column follows the G-buffer table above, and the scaling column says what multiplies the bill as you add lights.
