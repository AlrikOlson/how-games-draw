Texture Filtering & Mipmaps

A texture is a picture wrapped over a 3D shape, and it is made of tiny coloured cells called texels. Every pixel on the screen asks "what colour is my spot of the texture", and that question goes wrong in two opposite ways. Up close the spot lands between texels, so the picture goes blocky or soft. Far away one pixel covers dozens of texels, so the picture shimmers. Mipmaps fix the far case by keeping pre-shrunk copies of the texture. The thing people get wrong: anisotropic filtering does not replace mipmaps. It picks a sharper shrunk copy and reads it several times along the long side of the pixel's patch of texture.

Up close: reading one texel

The player stands nose to the tavern's brick wall. Move the white dot and watch which texels get read.

Past the edge of the tile

Bilinear is four texels blended by how close the spot is to each, and it can never average more than four.

Under the hood: the math and the code

The sampler never sees pixels. It gets a continuous coordinate (u, v), two numbers in [0, 1] that say how far across and down the texture you are, and it has to answer with a colour.

Texel centres sit at half-integers, so u·16 − 0.5 is the position in texel units. Its floor names the top-left texel of the 2×2 footprint, the small square of texels being read, and the fractional part is the blend weight. Nearest filtering skips the subtraction and takes whichever texel the point falls in.

Bilinear is two lerps, where a lerp is a straight blend between two values by a fraction. Lerp the top pair by fx, lerp the bottom pair by fx, then lerp the two results by fy. The four weights always sum to one.

At the texture edge the address mode decides what the missing neighbour is. Clamp repeats the edge texel. Wrap pulls from the far side, which is why tiling textures like this wall need matching borders.

In words: find the position in texel units, split it into a whole part and a fraction, and use the fraction to weight the four texels around it.

x = u·N − 0.5 i = ⌊x⌋ fx = x − i y = v·N − 0.5 j = ⌊y⌋ fy = y − j w00 = (1−fx)(1−fy) w10 = fx(1−fy) w01 = (1−fx)·fy w11 = fx·fy Σw = 1 c = w00·T[i,j] + w10·T[i+1,j] + w01·T[i,j+1] + w11·T[i+1,j+1]

N is the texture size in texels, i and j pick the top-left texel, fx and fy are the fractions, w00 to w11 are the four weights, and T[i,j] is the colour stored at texel (i, j).

What this code does: fetches the four texels around the point and blends them in two steps, first across, then down.

// what the hardware does for one bilinear tap, written out
vec4 sampleBilinear(sampler2D t, vec2 uv, vec2 texSize) {
  vec2 x  = uv * texSize - 0.5;      // texel centers are at +0.5
  vec2 i0 = floor(x);
  vec2 f  = x - i0;                    // the two weights
  vec4 c00 = texelFetch(t, wrap(i0 + vec2(0,0)), 0);
  vec4 c10 = texelFetch(t, wrap(i0 + vec2(1,0)), 0);
  vec4 c01 = texelFetch(t, wrap(i0 + vec2(0,1)), 0);
  vec4 c11 = texelFetch(t, wrap(i0 + vec2(1,1)), 0);
  return mix(mix(c00, c10, f.x), mix(c01, c11, f.x), f.y);
}

Shimmer is bilinear reading four texels out of dozens; the shrunk copies make those four the average of all of them.

Under the hood: the math and the code

Without mipmaps, a bilinear tap (one read of the sampler) still fetches four texels and ignores the rest, so the pixel colour depends on exactly which four it landed on. Neighbouring pixels land on different ones. The mortar lines between the stones beat against the pixel grid into moiré bands, and the bands crawl the moment the camera moves.

Mipmaps prefilter the answer. Level k is the texture averaged down by 2k: level 1 is half size, level 2 a quarter, and so on. The sampler picks the level where one texel is about one pixel wide, so the four texels it reads already hold the average of everything the pixel covers. λ (lambda) is the name for that picked level, and it can sit between two whole levels.

Trilinear blends the two nearest levels so the switch between them is invisible. Anisotropic filtering fixes the blur that is left. At grazing angles the footprint, the patch of texture one pixel covers, is long and thin. One level choice has to blur along the short side too. So the sampler picks the level that fits the short side and takes several taps along the long one.

In words: trilinear blends the level below λ with the level above it. Anisotropic splits the long side into N taps, picks a level finer by log2(N), and averages them.

trilinear: c = lerp(bilinear(L⌊λ⌋, uv), bilinear(L⌈λ⌉, uv), λ − ⌊λ⌋) aniso: N = min(⌈ρ_major / ρ_minor⌉, maxAniso) λ' = log2(ρ_major / N) ← finer level than log2(ρ_major) c = (1/N) Σ_k trilinear(uv + axis · ((k + ½)/N − ½), λ')

L⌊λ⌋ and L⌈λ⌉ are the levels just below and above λ. ρ_major and ρ_minor are the long and short widths of the footprint in texels, N is the number of taps, and axis is the direction of the long side.

What this code does: does the trilinear blend with two textureLod calls, then walks N points along the long side of the footprint and averages a trilinear read at each one.

// trilinear and anisotropic, spelled out with textureLod
float l0 = floor(lod), f = lod - l0;
vec4 c = mix(textureLod(t, uv, l0), textureLod(t, uv, l0 + 1.0), f);

// anisotropic: same idea, N taps along the long axis of the footprint
float pMax = max(length(dx), length(dy));   // dx, dy in texels
float pMin = min(length(dx), length(dy));
float N    = min(ceil(pMax / pMin), maxAniso);
float lodA = log2(pMax / N) + lodBias;
vec2  axis = (length(dx) > length(dy)) ? dFdx(uv) : dFdy(uv);
vec4  sum  = vec4(0.0);
for (int k = 0; k < int(N); k++)
  sum += textureLod(t, uv + axis * ((k + 0.5) / N - 0.5), lodA);
c = sum / N;

The stack of shrunk copies

The road texture and its eight half-size copies. Choose a copy, stretch the pixel's patch, and see which copy gets read and where on the road it is used.

How to pick the copy

The whole stack of copies costs a third more memory than the texture, and that buys a four-texel read at any distance.

Under the hood: the math and the code

Each level is a quarter the size of the one before, so the whole chain costs one third more than the base level. For the 256² RGBA8 texture that is 262,144 bytes for the base and 349,524 bytes for the chain. Without the chain, a minified lookup either aliases (shows the shimmer from the last section) or has to read hundreds of texels per pixel.

The footprint ellipse is the pixel projected into texture space. On level 0 it covers 2λ texels across its long axis. On level ⌊λ⌋ the same ellipse is about one texel wide, which is what makes a 2×2 bilinear read a fair average.

The levels below 8×8 are single digits of bytes. They still matter, because the sampler needs a level for every distance, and a flat far level is exactly the grey the road averages to at the horizon.

In words: add up the bytes of every level; the total is four thirds of the base level.

bytes(chain) = N²·b + (N/2)²·b + (N/4)²·b + … + 1·b = N²·b · (1 + ¼ + 1/16 + …) → N²·b · 4/3 256², RGBA8: 262,144 B base → 349,524 B chain = 1.333 × base

N is the base width in texels, b is the bytes per texel (4 for RGBA8), and the arrow shows what the sum settles to as the levels get small.

What this code does: builds the next level by averaging each 2×2 block of the level above into one texel.

// generating level L+1 from level L: one thread per destination texel
ivec2 src = 2 * dstId;
vec4 a = texelFetch(levelL, src + ivec2(0,0), 0);
vec4 b = texelFetch(levelL, src + ivec2(1,0), 0);
vec4 c = texelFetch(levelL, src + ivec2(0,1), 0);
vec4 d = texelFetch(levelL, src + ivec2(1,1), 0);
imageStore(levelL1, dstId, (a + b + c + d) * 0.25);   // box filter; average sRGB in linear

The copy level is how many halvings it takes until the longer pixel step is about one texel; everything else here is built on that.

Under the hood: the math and the code

The GPU shades pixels in 2×2 groups called quads, so it can subtract neighbouring pixels' UVs. Those differences are the screen-space derivatives: how far the texture coordinate moves for one pixel step in x and one in y. Multiplied by the texture size they are vectors in texels, and their lengths are the two footprint widths.

The isotropic rule (one size in every direction) takes the larger width, ρ, and sets λ = log2(ρ), so one texel at that level is about one pixel.

The anisotropic rule divides the long width by N taps first, then takes the log. The level gets finer by log2(N) and the cost goes up by N bilinear taps, or 2N with trilinear. Sixteen is the usual cap because past that the extra taps stop being visible, and the footprint is being averaged over more texels than the screen can show.

The live arithmetic for the pixel you are hovering:

In words: measure the pixel step in texels in both directions, take the longer one, and its log base 2 is the level.

dx = ∂(u,v)/∂x · texSize dy = ∂(u,v)/∂y · texSize (texels) ρx = |dx| = √(du/dx² + dv/dx²) ρy = |dy| = √(du/dy² + dv/dy²) ρ = max(ρx, ρy) λ = log2(ρ) + bias, clamped to [0, levels−1] aniso: N = min(⌈max(ρx,ρy) / min(ρx,ρy)⌉, 16) λ' = log2(max(ρx,ρy) / N)

dx and dy are the pixel steps in texels, ρx and ρy are their lengths, ρ is the larger one, λ is the level, and bias is a per-sampler nudge. N and λ' are the anisotropic tap count and level.

What this code does: computes the level the same way texture() does silently, then shows the two ways to hand the sampler your own gradients.

// what texture(t, uv) computes implicitly inside a fragment shader
vec2 dx = dFdx(uv) * texSize;     // finite difference across the 2×2 quad
vec2 dy = dFdy(uv) * texSize;
float rho = max(length(dx), length(dy));
float lod = log2(rho) + lodBias;  // hardware then clamps to the mip range

// explicit gradients: mandatory inside divergent branches and in compute
vec4 c = textureGrad(t, uv, dFdx(uv), dFdy(uv));
// cheaper scalar guess some shaders use; fwidth = |dFdx| + |dFdy|
float lodApprox = log2(max(fwidth(uv.x), fwidth(uv.y)) * texSize.x);

Compress with a block format and keep the shrunk copies; the copies are what keep texture reads landing in the cache.

Under the hood: the math and the code

Block compression is what makes the chain affordable. BC1 packs a 4×4 block into 8 bytes: two RGB565 endpoint colours (16 bits each) and a 2-bit index per texel that picks one of four colours between them. That is 4 bits per texel instead of 32. BC7 spends 16 bytes per block on better endpoints and partitions. ASTC picks the block size per texture, and a 6×6 block at 16 bytes lands at 3.56 bits per texel. The texture unit decodes blocks on the way into its cache, so the shader never sees the difference.

Bandwidth is about cache lines, not texels. A cache line is the 64-byte chunk that memory hands over in one go. A bilinear tap reads four neighbouring texels that usually share one line, and the next pixel's tap usually hits the same line.

Mipmaps are what keep that hit rate high: at the right level, consecutive pixels read consecutive texels. Sample a 2048² texture without mips at heavy minification and every tap lands on a different line, the hit rate collapses, and the slider is what your frame time pays.

How to read the table: the same texture in each format. Bits per texel is the compression, and the last two columns are the bytes it takes without and with a mip chain.

In words: bytes are blocks across times blocks down times bytes per block; bandwidth is pixels times taps times one cache line for every miss.

bytes(level n) = ⌈n / bw⌉ · ⌈n / bh⌉ · blockBytes BC1: 4×4 → 8 B, BC7: 4×4 → 16 B, ASTC 6×6 → 16 B bandwidth/frame = pixels · taps · 64 B · (1 − hitRate) taps: bilinear 1, trilinear 2, aniso N× up to 2N bandwidth/s = bandwidth/frame · 60 Hz

n is the level width, bw and bh are the block width and height, blockBytes is the bytes per block, taps is the reads per pixel, and hitRate is the share of reads served from cache.

What this code does: unpacks one BC1 block into its four-colour palette and picks a texel's colour with its 2-bit index.

// BC1 block decode sketch: 8 bytes → 16 texels
uint  c0 = block.lo & 0xFFFFu, c1 = block.lo >> 16;       // two RGB565 endpoints
vec3  p0 = unpack565(c0), p1 = unpack565(c1);
vec3  pal[4];
pal[0] = p0; pal[1] = p1;
if (c0 > c1) { pal[2] = mix(p0, p1, 1.0/3.0); pal[3] = mix(p0, p1, 2.0/3.0); }
else         { pal[2] = 0.5 * (p0 + p1);      pal[3] = vec3(0.0); }  // 3-colour + transparent
uint  idx = (block.hi >> (2u * (ty * 4u + tx))) & 3u;         // 2 bits per texel
vec3  texel = pal[idx];

The "up to" matters. The read count is per pixel and depends on that pixel's patch shape, so a 16× setting costs almost nothing on surfaces facing the camera. What you pay in practice is the texture unit's filtering rate: bilinear runs at full rate for 32-bit formats on current GPUs, trilinear and each extra anisotropic read take extra cycles, and wide formats (RGBA16F, BC6H) filter at a reduced rate.
