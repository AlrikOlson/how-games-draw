Normal Mapping & Parallax

A normal map is a texture that stores, for every tiny square of a surface, which way that spot faces. The lighting code uses that stored direction instead of the flat triangle's own, so a flat wall shades as if it had bricks and grooves, for the price of one extra texture read. The thing people get wrong: the stored directions are relative to the surface and its texture layout, so the map only means something together with the mesh's tangent data. The bumps live in the lighting alone: edges, depth and shadows stay flat, and parallax tricks fake depth by shifting where the texture is read, not by moving the surface.

From bumps to directions

Hover either picture to watch one texel's height turn into a direction.

A height map is a grayscale picture where brighter means higher. A normal map holds the same bumps stored differently: each texel says which way that spot faces instead of how high it is. The GPU wants directions, not heights, because lighting depends on which way a surface points. Steeper slope, more tilted arrow.

What you're seeing

The real version

Each texel of the height map is one number. To get a slope, take the height of the texel on the right minus the height of the texel on the left, and halve it. That is a central difference, a slope estimate from the two neighbours, and it is done on both axes. Because it spans three texels, the normal map is one texel blurrier than the height map.

The slope becomes a normal, the arrow of length exactly one that says which way the surface faces. Its z part is always positive: a height map cannot overhang, so the surface can never face downward. That is why the map is blue. Stored z sits near 255 while x and y sit near 128, which is how zero is stored.

The strength s is the real height range divided by the texel size. For this quad, 30 mm over 15.6 mm gives s = 1.92 as the physically correct slope. Artists push s higher for punchier lighting. That is harmless for shading and wrong for parallax, where the height and the normal must describe the same surface.

In words: take the slope from the two neighbours on each axis, tilt the straight-out arrow by that slope times the strength, then squeeze the result into 0 to 255.

grad = ( (h[x+1] − h[x−1]) / 2 , (h[y+1] − h[y−1]) / 2 ) // height units per texel n = normalize( −grad.x · s , −grad.y · s , 1 ) rgb8 = round( (n · 0.5 + 0.5) · 255 ) // flat = (128, 128, 255)

grad is the slope on each axis in height units per texel, s is the strength, n is the normal and rgb8 is what gets written into the texture.

What this code does: reads the four neighbours, forms the slope, builds the normal and writes it out as a colour. It runs once when the map is made, not every frame.

// height → tangent-space normal, one texel. Runs once, offline in the baker or in a compute pass.
float hL = height.Load(id + int2(-1, 0)), hR = height.Load(id + int2(1, 0));
float hD = height.Load(id + int2(0, -1)), hU = height.Load(id + int2(0, 1));
float2 grad = float2(hR - hL, hU - hD) * 0.5;      // slope from the two neighbours on each axis
float3 n = normalize(float3(-grad * strength, 1.0));  // z > 0 always: a height field never overhangs
normalMap[id] = float4(n * 0.5 + 0.5, 1.0);            // or store n.xy only, see the storage section

A normal map is a height map's slopes stored as directions, and it only matches the real surface if the strength is the physical one.

Lighting a flat surface with fake bumps

Drag the light and the eye, and hover along the surface to pick a spot.

The GPU draws a flat square. When it colours each pixel it needs to know which way that spot faces, and normally the answer is straight out. With a normal map it reads the answer from the texture instead, so the light lands as if the bumps were there. Only the lighting changes. The square is still flat to its edges, to the depth buffer and to the shadows.

The real version

The rasterizer, the part of the GPU that turns triangles into pixels, only ever sees the flat quad. The fragment shader, the program that runs once per pixel to pick its colour, reads the normal from the map and uses it in every lighting dot product. A dot product of two length-one arrows is 1 when they point the same way and 0 when they are at right angles, so N·L (normal dot light direction) says how squarely the light hits.

Diffuse light, the soft matte part, is N·L. Specular light, the shiny highlight, uses N·H, where H is the direction halfway between the light and the eye. That pair is Lambert plus Blinn-Phong, the classic lighting model, and the exponent p = 64 sets how tight the highlight is.

What does not happen matters more. The profile is dashed because it never exists in the pipeline. The quad's edge is straight from any angle, the depth buffer (the per-pixel record of how far away things are) holds the flat depth, and a shadow map, the depth picture rendered from the light, sees a flat caster. That is why the parallax section exists.

In words: turn the stored colour back into a direction, then use that direction in the same two lighting terms as always.

n = normalize( tex(normalMap, uv).rgb · 2 − 1 ) // still in tangent space here diffuse = max(0, n·l) specular = max(0, n·h)^p, h = normalize(l + v) // Blinn-Phong, p = 64 in the render

n is the decoded normal, l points at the light, v points at the eye, h is halfway between l and v, and p is the highlight exponent.

What this code does: reads the map, converts the direction to world space, and feeds it into ordinary diffuse and specular. Nothing else in the pipeline changes.

// fragment shader: same lighting as before, only N changed
float3 nTs = normalMap.Sample(s, uv).xyz * 2.0 - 1.0;
float3 N = normalize(mul(nTs, TBN));                    // tangent → world, next section
float3 L = normalize(lightPos - P), V = normalize(eyePos - P);
float3 H = normalize(L + V);
float NdotL = saturate(dot(N, L));
float spec  = pow(saturate(dot(N, H)), 64.0);
color = albedo * NdotL * atten + spec * atten;         // depth, stencil, shadow casting: untouched

Normal mapping changes which way each pixel thinks it faces, and nothing else.

Turning the map with the mesh

Rotate the square and drag the light; the map's directions have to turn with the mesh.

The directions in a normal map are relative to the surface: "tilted a bit toward the right edge of the texture". When the mesh rotates, the right edge of the texture goes somewhere else, so the stored direction has to be turned to match. That is the job of the tangent basis. Skip it and the bumps light from a direction that spins with the mesh.

What you're seeing

The square is rotated in the plane by θ; the map and the light are not. At the sample point, the amber arrow is T, the world direction in which the texture's u coordinate increases, and the blue arrow is B, the same for v. The normal N points out of the screen.

The box under the controls shows the numbers: the stored normal, the turned normal, and the N·L each one gives.

The real version

Texture coordinates, called UVs, are the two numbers that say where on the texture each vertex lands: u across, v down. Tangent space is the set of three directions attached to the surface at a point: T along increasing u, B (the bitangent) along increasing v, and N straight out. A stored normal's x, y and z are amounts of T, B and N.

Put those three world-space arrows side by side as the columns of a matrix and you have TBN. Multiplying the stored normal by it gives the world-space normal. T and B come from one triangle: two of its edges and their UV differences form a small linear system, and solving it gives how position changes per unit of u and per unit of v.

Two classic bugs. Using the stored normal as if it were already in world space lights the bumps from a direction that turns with the mesh; it looks right at θ = 0 on a floor, which is how it ships. And T, B and N are interpolated across each triangle, so they drift out of being at right angles; either re-square them in the fragment shader or accept the small error, as most engines do.

MikkTSpace is a standard algorithm for computing tangents. It exists because the tool that bakes the map and the engine that reads it must build this basis identically, sign included.

In words: from one triangle's two edges and their UV changes, solve for the directions of increasing u and v, then mix the stored normal out of T, B and N.

E1 = P1 − P0, E2 = P2 − P0, (Δu1, Δv1), (Δu2, Δv2) // one triangle r = 1 / (Δu1·Δv2 − Δu2·Δv1) T = r · ( Δv2·E1 − Δv1·E2 ) // ∂P/∂u B = r · ( Δu1·E2 − Δu2·E1 ) // ∂P/∂v n_world = T·n_ts.x + B·n_ts.y + N·n_ts.z = TBN · n_ts

E1 and E2 are the triangle's edges, the Δu and Δv values are the UV differences along them, r undoes a 2 by 2 determinant, and n_ts is the normal read from the map.

What this code does: builds T, B and N per vertex, fixes the drift and the mirrored-UV sign, then applies the matrix per pixel. The last line is where the bug lives.

// vertex shader: tangent comes from the mesh (MikkTSpace), sign in tangent.w
float3 N = normalize(mul(normalMatrix, vin.normal));
float3 T = normalize(mul((float3x3)world, vin.tangent.xyz));
T = normalize(T - N * dot(N, T));                        // re-square T against N after interpolation drift
float3 B = cross(N, T) * vin.tangent.w;                  // w = ±1 fixes mirrored UVs
vout.TBN = float3x3(T, B, N);                            // interpolated as three float3s

// fragment shader
float3 nTs = normalMap.Sample(s, uv).xyz * 2.0 - 1.0;
float3 N = normalize(mul(nTs, vin.TBN));                 // bug: using nTs here directly

A normal map only means something with its tangent basis; TBN translates "relative to the texture" into "in the world".

Faking depth by shifting the lookup

Drag the eye and the entry point, and watch where each method reads the texture.

Normal mapping reads the texture where your line of sight hits the flat surface. If the bumps were real, your line of sight would hit them somewhere else, closer to you on a high spot. Parallax methods shift where the texture is read to that spot. Nothing moves; only the lookup does. Done well, near texels slide past far ones as the camera moves, the way real depth does.

The real version

Parallax mapping guesses once. Read the height at the flat spot, then shift the lookup sideways in proportion to that depth and to how slanted the view is, and hope the height at the new spot is similar. It costs one extra read. It swims at grazing angles, where the eye is nearly level with the surface, because the guess is worst exactly where the shift is largest.

Parallax occlusion mapping, POM, stops guessing and marches. It steps the view ray down through the height field in fixed depth layers, reading the height once per layer, until the ray is below the surface. The last two readings are blended to place the hit. More layers means fewer stair-steps and more reads, so engines scale the count with the view angle: 8 head-on, 32 to 64 at grazing angles.

The three renders share one view direction, taken from the eye in the side view, and use an orthographic projection, meaning no perspective and every pixel looking the same way. Rays that leave the texture at the quad's edge have nothing to hit. That is the dark band on the edge away from the eye in the parallax and POM renders, and the reason POM silhouettes are still flat.

In words: walk down the ray one layer at a time until it is under the surface, then blend the last two steps to find the crossing.

v = viewDir in tangent space, pointing at the eye, v.z > 0 uv(d) = uv0 − (v.xy / v.z) · d · heightScale // where the ray is at depth d, in uv units parallax: d0 = 1 − h(uv0), uv' = uv(d0) // one guess POM: for k = 1..L: d_k = k / L, if d_k ≥ 1 − h(uv(d_k)) → hit between k−1 and k t = (d_{k−1} − depth_{k−1}) / ((d_{k−1} − depth_{k−1}) − (d_k − depth_k)), uv' = lerp(uv_{k−1}, uv_k, t)

v is the view direction in tangent space, uv0 is the flat lookup, d is depth as a fraction of heightScale, h is the height read from the map, L is the layer count and t is the blend between the last two steps.

What this code does: picks a layer count from the view angle, steps until the ray is under the surface, then interpolates the crossing. Every other texture is read at uvHit too.

// POM loop, fragment shader, tangent-space viewDir v (v.z > 0)
float layers = lerp(64.0, 8.0, abs(v.z));               // more steps at grazing angles
float2 step = v.xy / v.z * heightScale / layers;
float2 uvc = uv; float d = 0.0, dStep = 1.0 / layers;
float depth = 1.0 - heightMap.Sample(s, uvc).r;
while (d < depth) {                                       // ray still above the surface
  uvc -= step; d += dStep;
  depth = 1.0 - heightMap.SampleGrad(s, uvc, ddx, ddy);  // explicit grads: the loop breaks quad ddx
}
float2 uvPrev = uvc + step;                              // blend between the last two samples
float after  = depth - d;
float before = (1.0 - heightMap.Sample(s, uvPrev).r) - (d - dStep);
float2 uvHit = lerp(uvc, uvPrev, after / (after - before));
float3 nTs = normalMap.Sample(s, uvHit).xyz * 2.0 - 1.0; // everything else samples at uvHit too

Parallax never moves the surface; it moves where you read the texture, and POM marches to find the right spot.

Storing the map small

The same map three ways; hover a texel to see what compression costs it.

A normal is three numbers, but an arrow of length one that points outward is fully described by two: the third can be rebuilt. GPUs use that to store normals in one byte per texel with a format called BC5. Shrinking the map for distance is a separate problem: averaging bumps loses the roughness they stood for, and there is a trick to keep it.

The real version

Three bytes per texel wastes one. BC5 is a block-compressed format: each 4 by 4 block of texels stores two 8-bit endpoints and sixteen 3-bit indices per channel, and it does that for two channels independently, one byte per texel in total. The shader rebuilds z. The error map shows what that block rounding costs: worst on steep slopes, where x or y covers a wide range inside a single block, near zero on the flat areas.

BC7 spends the same byte per texel on three or four channels with eight encoder modes. It is the usual choice for colour textures and the fallback for normals only when a format needs all the channels.

Mips are the half-size copies of a texture used when it is far away, and they lose something else. Averaging four length-one normals gives an arrow shorter than one, and normalizing it, stretching it back to length one, throws away the fact that the surface was rough at that scale. Toksvig's method keeps it: the length of the averaged normal says how spread out the originals were, and that spread widens the highlight.

Renormalizing and keeping the base exponent is why distant bumpy surfaces sparkle and shimmer. The fix is to bake the shrink into the roughness mips. The mip table below is computed from this map.

In words: rebuild z so the arrow has length one again; for mips, use how much the average shrank to soften the highlight.

BC5: x = R/255 · 2 − 1, y = G/255 · 2 − 1, z = sqrt( max(0, 1 − x² − y²) ) Toksvig: |n̄| = length of the box-filtered, un-normalized normal f_t = |n̄| / ( |n̄| + s · (1 − |n̄|) ), s' = f_t · s // s = Blinn-Phong exponent

R and G are the two stored bytes, |n̄| is the length of the averaged normal, s is the highlight exponent and f_t is the factor that softens it.

What this code does: decodes two channels into a full normal, reads the per-mip average length, and uses it to widen the highlight where bumps were averaged away.

// decode a BC5 normal and apply the Toksvig factor from a fourth channel or a roughness mip
float2 xy = normalMap.Sample(s, uv).rg * 2.0 - 1.0;   // BC5: only r and g exist
float3 n = float3(xy, sqrt(saturate(1.0 - dot(xy, xy))));
float len = normalLenMip.Sample(s, uv).r;             // |n̄| baked per mip, 1.0 at level 0
float ft = len / (len + specPower * (1.0 - len));
float p = specPower * ft;                             // wider highlight where the mip averaged bumps away
float spec = pow(saturate(dot(n, H)), p) * (1.0 + ft * specPower) / (1.0 + specPower);

Store two channels and rebuild the third; and when you shrink a normal map, the length it loses is roughness you should keep.

Tradeoffs: how much surface to fake

Every row costs extra texture reads per pixel, and the first three are still flat in the depth buffer and in shadow maps.

Read the rows top to bottom as more convincing and more expensive. You are choosing how many texture reads per pixel to pay, on top of the material's own textures, and whether the outline and the shadows need to change too.

The map itself costs the same bandwidth in every row: a 2048² BC5 map with mips is about 5.6 MB, and one sample costs one 16-byte block fetch per texel quad, the 2×2 group of pixels the GPU shades together. POM's cost is the chain of dependent reads in the loop. The texture cache handles them well because consecutive steps land in nearby texels.

Two naming traps. "OpenGL" and "DirectX" normal maps are the same data with the green channel flipped: +Y up (Blender, Unity, glTF) and +Y down (Unreal, most DirectX-era tools) are both tangent-space conventions, and a map baked for one looks lit from below in the other. And in most art tools a "bump map" is a grayscale height, while in engine code "bump mapping" has meant perturbing normals since Blinn's 1978 paper.
