Screen-Space Reflections

A game draws its picture, then wants a mirror in it: a puddle, a wet street, a lake. Drawing the whole scene a second time as seen in the mirror is expensive. Screen-space reflections, SSR for short, take a shortcut: they build the mirror image out of pixels already in this frame's picture, by bouncing the player's line of sight off the surface and walking along it across the picture until it runs into something. Anything in the picture reflects for free, moving or not. The thing people get wrong: SSR is not a cheap ray tracer. It only knows the picture, so anything the camera cannot see, the underside of a balloon or a thing behind the player, comes out missing.

One lake pixel, one walk

A player on a bluff looks down at a still lake. Pick one pixel of the lake and watch SSR find its reflection inside the picture the game already drew.

hover the lake

SSR walks the bounced line across the picture and takes the color at the first stop that dips behind something; it never looks at the 3D objects.

Under the hood: the math and the code

The camera sees the lake at pixel u. Its view ray d lands on water point p with normal n (the direction the surface faces, straight up for still water), and the mirror direction is r = d − 2(n·d)n. SSR does not trace r through the scene. It projects a segment of r back onto the screen, so the start and end become two pixel positions with a depth each, and visits the pixels between them in order.

At each visited pixel the ray has a depth z_ray and the buffer has z_buf, the depth of whatever the camera saw there. While z_ray < z_buf the ray is still in front of everything. The first pixel where it goes behind is the hit, provided it went behind by less than a thickness t. Fetch the color at that pixel and that is the reflection.

Depth is not linear along the screen, but 1/z is, so the ray is interpolated in 1/z between its projected endpoints. Interpolating z directly bends the ray off its true path, which shows up as reflections that slide when the camera moves.

In words: bounce the ray, turn its two ends into pixel positions, blend 1/depth between them, and call it a hit the first time the ray is behind the buffer by less than the thickness.

r = d − 2 (n·d) n u = (0.5 − 0.5 · x_v / (z_v · tan(fov/2))) · N // view space → pixel 1/z(u) = lerp(1/z_0, 1/z_1, (u − u_0) / (u_1 − u_0)) // linear on screen hit ⇔ z_ray > z_buf(u) && z_ray < z_buf(u) + t

d is the view ray, n the water's normal, r the bounced ray. x_v and z_v are a point's sideways and forward position as seen from the camera, fov is the camera's field of view, N the screen width in pixels. z_0 and z_1 are the depths at the two projected ends, u_0 and u_1 their pixel positions, t the thickness.

What this code does: projects both ends of the bounced ray to the screen, then steps between them a few pixels at a time until the ray is behind the depth buffer by less than the thickness.

// per reflective pixel, view space in, color out
vec3 r  = reflect(viewDir, n);
vec3 p0 = posVS, p1 = posVS + r * uMaxDist;
vec4 c0 = uProj * vec4(p0, 1.0), c1 = uProj * vec4(p1, 1.0);
vec2 s0 = (c0.xy / c0.w * 0.5 + 0.5) * uRes;         // pixel coords
vec2 s1 = (c1.xy / c1.w * 0.5 + 0.5) * uRes;
float k0 = 1.0 / c0.w, k1 = 1.0 / c1.w;               // 1/z is linear on screen
float len = length(s1 - s0);
for (float i = 1.0; i < len; i += uStepPx) {
  float w    = i / len;
  vec2  px   = mix(s0, s1, w);
  float zRay = 1.0 / mix(k0, k1, w);
  float zBuf = linearDepth(texelFetch(uDepth, ivec2(px), 0).r);
  if (zRay > zBuf && zRay < zBuf + uThickness)          // behind, but not far behind
    return texelFetch(uColor, ivec2(px), 0).rgb;
}
return vec3(0.0);                                    // miss: hand over to the fallback

Fixed steps or big jumps

Same lake. Walking the bounced line every few pixels is simple but slow; jumping over empty sky in big blocks is faster, most of the time.

Fixed steps trade accuracy for speed; Hi-Z jumps over empty screen in big blocks and only slows down next to a surface.

Under the hood: the math and the code

A fixed step of s pixels costs distance/s fetches and only locates the hit to within s pixels. Small steps are accurate and slow; big steps walk straight over thin objects.

A binary search between the last pixel in front and the first pixel behind (halve the gap, check which side, repeat) recovers sub-pixel accuracy for log2(s) extra fetches. That is why most linear marchers step coarse and then refine.

Hi-Z tracing replaces the fixed step with a test. In the coarsest level whose cell the ray is in, it checks whether the ray stays in front of the cell's minimum depth all the way to the cell's edge. If yes, jump to that edge and go one level coarser. If no, go one level finer without leaving the cell.

The march spends single steps on empty screen and only reaches level 0 next to a surface. The pyramid costs one min-reduction pass per frame and a third more depth memory. Its weak case is a ray running behind something, the balloon here: every pixel of that stretch fails the skip test and costs a fetch or two, which is why the Hi-Z count is not always the smaller one.

The level-0 hit is the exact crossing of the ray with that pixel's depth, so Hi-Z gives sub-pixel hits without a refinement loop. The error readout compares each method against that exact crossing.

In words: build each level by keeping the nearer of two cells; at each step, skip the cell if the ray stays in front of its nearest depth, otherwise zoom in one level; a hit is a level-0 cell the ray is behind by less than the thickness.

hiz[L][i] = min(hiz[L−1][2i], hiz[L−1][2i+1]) cell = floor(u / 2^L), u_exit = (cell + 1) · 2^L // moving +u skip ⇔ max(z(u), z(u_exit)) < hiz[L][cell] → u = u_exit, L = L + 1 descend ⇔ otherwise → u = u where z(u) = hiz[L][cell], L = L − 1 hit ⇔ L = 0 and z(u) < z_buf + t

hiz[L][i] is cell i of level L, u the ray's current pixel, u_exit the pixel where it leaves the cell, z(u) the ray's depth at a pixel, t the thickness.

What this code does: one step of the Hi-Z walk. It finds where the ray leaves the current cell, finds where the ray would reach the cell's nearest depth, and either jumps out and coarsens, or moves to that depth and refines.

// one Hi-Z step; uHiZ is the min-depth mip chain
float cellSize = exp2(float(level));
vec2  cell     = floor(px / cellSize);
vec2  edge     = (cell + step(0.0, dir)) * cellSize;     // exit edge along dir
float tEdge    = min((edge.x - px.x) / dir.x, (edge.y - px.y) / dir.y);
float zMin     = textureLod(uHiZ, cell * cellSize / uRes, float(level)).r;
float tPlane   = (1.0 / zMin - k) / dk;                    // where 1/z hits the cell's min plane
if (tPlane > tEdge) { px += dir * (tEdge + 0.01); level = min(level + 1, uMaxLevel); }
else                { px += dir * max(tPlane, 0.0);  level -= 1; }  // -1 at level 0 means hit

Every SSR miss is the same miss, the target was never drawn, and a probe or the sky fills the hole, faded in near the screen edge.

Under the hood: the math and the code

SSR has one failure with three faces. The reflected object is off screen: nothing was stored, so nothing can be found. The object is on screen but its reflected side is not: the ray passes behind the balloon, keeps going, and lands on the house, so the balloon's reflection is a patch of house wall. Something in the foreground covers the target: the gull's depth is nearer than the ray at those pixels, so the ray counts as behind it and walks on into nothing.

A reflection probe is a cubemap, six square images covering every direction, captured from one point (the ring over the lake, 128 directions here). Sampling it with r gives a plausible color at the wrong parallax, meaning the reflection sits in slightly the wrong place because the probe was not captured from where the lake pixel is. Beyond the probe, the sky.

The blend weight is the SSR confidence: zero on a miss, and faded toward zero near the screen edge so the hole does not pop into view when the camera turns.

In words: measure how close the hit is to the nearest screen edge, turn that into a weight between 0 and 1, and mix the SSR color with the probe (or sky) by that weight.

e = min(uv_hit.x, 1 − uv_hit.x, uv_hit.y, 1 − uv_hit.y) w = hit ? smoothstep(0, f, e) : 0 // edge fade, f ≈ 0.1 color = w · ssr + (1 − w) · (probe(r).a > 0 ? probe(r).rgb : sky(r))

uv_hit is the hit's screen position from 0 to 1, e its distance to the nearest edge, f the fade width, w the weight, and probe(r).a is zero where the probe saw sky.

What this code does: reads the SSR hit, computes the edge fade, looks up the probe with a direction corrected for the probe's position, and mixes the three sources.

// resolve: SSR result carries its hit uv in .xy and a hit flag in .w
vec4  h    = texelFetch(uSSR, px, 0);
float edge = min(min(h.x, 1.0 - h.x), min(h.y, 1.0 - h.y));
float w    = h.w * smoothstep(0.0, uFade, edge);        // 0 on miss, fades near edges
vec3  ssr  = texelFetch(uColor, ivec2(h.xy * uRes), 0).rgb;
vec3  rP   = parallaxCorrect(r, posWS, uProbeBox);       // box-projected lookup dir
vec4  pr   = textureLod(uProbe, rP, roughness * uMips);
vec3  fb   = mix(sky(r), pr.rgb, pr.a);                  // alpha 0 where the probe saw sky
return mix(fb, ssr, w);

Rippled water: scatter the rays

Wind ripples the lake, so its reflection is blurry. Rays go out in random directions inside a cone, and the speckle is averaged away over frames.

Rough surfaces need many random rays; one per pixel is right on average but speckled, so average over frames and blur by roughness times distance.

Under the hood: the math and the code

A mirror needs one ray. A rough surface reflects a cone of directions weighted by the GGX lobe, the standard curve for how much light a rough surface sends each way. The correct way to render that is to sample it: draw a half vector h (the direction halfway between the incoming and outgoing rays) from the distribution, reflect d about it, march. One ray per pixel gives the right answer on average and noise everywhere.

Two things hide the noise. Temporal accumulation averages each frame into a history buffer, which is last frame's result shifted to line up with this frame's camera. After a few dozen frames the estimate converges; move the camera and it starts over.

A spatial blur whose radius grows with roughness and with the distance to the hit does it in one frame, at the cost of smearing detail. Production SSR does both and reuses each ray's hit for several neighbouring pixels (Frostbite's stochastic SSR, 2015).

The blur radius growing with hit distance is the physical effect, not a trick: the lobe's footprint at the hit grows linearly with the length of the reflected ray, so a rippled lake reflects the near boat sharply and the far house softly.

In words: pick a random tilt for the bounce, with rougher surfaces allowing bigger tilts; blend each new frame into the running average; size the blur by roughness times distance to the hit.

α = roughness² cos θ_h = sqrt((1 − ξ₁) / (1 + (α² − 1) ξ₁)), φ = 2π ξ₂ // GGX half vector r = reflect(d, h) hist_n = lerp(hist_n−1, cur, 1 / min(n, 48)) // temporal blend blur_px ≈ α · |hit − p| · N / (2 · z_hit · tan(fov/2)) // lobe footprint on screen

α is the lobe width, ξ₁ and ξ₂ are two random numbers from 0 to 1, θ_h and φ are the tilt and spin of the half vector, hist_n the running average after n frames, |hit − p| the distance from the floor point to the hit, z_hit the hit's depth.

What this code does: turns two random numbers into a tilted half vector, bounces the view ray off it, marches that ray as in section 1, and blends the result into the history.

// importance-sample the GGX normal distribution in tangent space
float a     = roughness * roughness;
vec2  xi    = blueNoise(px, frame);                      // decorrelated per pixel and frame
float cosT  = sqrt((1.0 - xi.x) / (1.0 + (a * a - 1.0) * xi.x));
float sinT  = sqrt(1.0 - cosT * cosT);
float phi   = 6.2831853 * xi.y;
vec3  h     = tbn * vec3(sinT * cos(phi), sinT * sin(phi), cosT);
vec3  r     = reflect(viewDir, h);
if (dot(r, n) <= 0.0) return vec4(0.0);                 // sample went into the surface
vec4  hit   = marchSSR(posVS, r);                        // as in section 1
float w     = 1.0 / max(pdfGGX(h, a), 1e-4);            // weight for the resolve pass
hist = mix(hist, hit, 1.0 / min(frameCount, 48.0));      // after reprojection

The allowance is how far behind a surface the line may go and still count; one fixed number is always wrong somewhere, so size it per pixel from the depth slope.

Under the hood: the math and the code

The thickness t says how far behind a stored surface the ray may be and still count as a hit. Too small, and the first sample past a surface lands beyond it by more than t, so the march reports "passed behind" and walks on into nothing: holes in the reflection of the boat and the house. Too large, and a ray that really did pass under and behind the gull is stopped by it, painting the gull into reflections of the house.

The right t is not a constant. One screen pixel of a surface seen at a grazing angle (nearly edge-on) covers a long range of depth. That is where the smearing near the horizon comes from: the ray moves a fraction of a pixel per metre of depth and either misses the surface or hits a long streak of the same color.

Deriving t per pixel from the depth buffer's own slope, or from the ray's depth change per step, gives a thickness that fits the surface it is testing.

Read the table with care. A hit on the balloon's rim counts as a false hit because the true reflection is its underside, which no thickness rule can find; the derivative rule catches that rim (a grazing surface) where the fixed rule walks past it. The green count is the number to compare.

In words: the fixed rule uses one number; the ray rule allows as much as the ray's depth changes in one step; the slope rule allows as much as the buffer's depth changes across one step, taking the gentler of the two sides so silhouettes stay thin.

fixed: t = t_0 ray step: t = t_min + |z(u + Δu) − z(u)| // never step over a surface derivative: t = t_min + min(|∂z_buf/∂u|₊, |∂z_buf/∂u|₋) · Δu // one-sided: silhouettes stay thin

t_0 is the fixed value, t_min a small floor on the thickness, Δu the step in pixels, z(u) the ray's depth, and ∂z_buf/∂u the buffer's depth change per pixel, measured to the right (₊) and to the left (₋).

What this code does: reads the depth at the ray's pixel and its two neighbours, takes the smaller of the two differences as the slope, and sizes the thickness from it.

// per-pixel thickness from the depth buffer's slope, sampled at the ray's pixel
float z0 = linearDepth(texelFetch(uDepth, px, 0).r);
float zL = linearDepth(texelFetch(uDepth, px - ivec2(1, 0), 0).r);
float zR = linearDepth(texelFetch(uDepth, px + ivec2(1, 0), 0).r);
float slope = min(abs(zR - z0), abs(z0 - zL));         // smaller side: an edge has one steep side
float t = uThicknessMin + slope * uStepPx;
bool  hit = zRay > z0 && zRay < z0 + t;

SSR is rarely used alone. The usual stack is SSR first, a reflection probe or SDF trace where it misses, and hardware ray tracing on top when the platform has it. Each pixel picks a layer by the confidence weight of the one above it.

One naming trap: "screen-space reflection" sounds like a reflection of the scene worked out in screen space. It is a lookup into the picture you already drew. SSR never shows the underside of anything, what is behind the camera, or what a nearer object covers, because none of that was written to the frame it reads. If a reflection has to contain those, the technique is the wrong one, not the tuning.
