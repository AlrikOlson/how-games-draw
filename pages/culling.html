Culling

A game world holds far more than the player can see at once: houses behind them, trees hidden by a wall, crates so far away they would be a speck. Culling is the renderer deciding what not to draw before it draws anything, because skipping a house costs almost nothing and drawing it costs a lot. This page plays through the tests a game runs every frame, from the cheap one (is it in front of the player at all) to the ones that need to know what is hiding what. The thing people get wrong: none of these tests is exact. Each one keeps extra objects on purpose and must never drop something visible, because nothing later in the frame can bring it back.

Skip what the player can't see

An object is skipped only when its wrap shape is fully outside one edge of the wedge; a tighter wrap just means fewer extras.

Under the hood: the math and the code

A plane is a flat cut through space, stored as a direction (its normal, n) and an offset (d). Plugging a point p into n·p + d gives its signed distance: positive on the inside, negative on the outside. The frustum is the space where every one of its planes gives a non-negative distance. This 2D demo has four planes; a 3D camera has six.

An object is rejected the moment any one plane says its whole wrap shape is on the outside. Straddling a plane counts as inside, so an object is never rejected for being half in.

The wrap shape decides how many false positives survive. A sphere around a 30 m wall is 30 m wide in every direction. An aligned box, a box lined up with the world axes (an AABB), grows when the wall rotates 45°. A tilted box that turns with the object (an OBB) stays tight. Even the tight one only checks the frustum's own planes, so a wall lying diagonally across a corner passes every plane and is still outside.

In words: for each plane, take the point of the shape that reaches farthest inward. If even that point is outside, the object is gone.

plane: n·p + d = 0, n unit, inside where n·p + d ≥ 0 sphere: reject if n·c + d < −r (for any plane) AABB: p-vertex p = (n.x ≥ 0 ? max.x : min.x, …) reject if n·p + d < 0 OBB: r_eff = hx·|n·u| + hy·|n·v| + hz·|n·w| reject if n·c + d < −r_eff

n is the plane's direction and d its offset. c and r are a sphere's centre and radius. min and max are the two corners of an aligned box, and the p-vertex is the corner farthest along n. For the tilted box, hx, hy, hz are its half-sizes, u, v, w are its own axes, and r_eff is how far it reaches along n.

What this code does: walks the six planes and bails on the first one the box is fully behind.

bool aabbInFrustum(vec3 bmin, vec3 bmax, vec4 planes[6]) {
  for (int i = 0; i < 6; i++) {
    vec3 n = planes[i].xyz;
    // p-vertex: the corner farthest along the plane normal
    vec3 p = vec3(n.x >= 0.0 ? bmax.x : bmin.x,
                  n.y >= 0.0 ? bmax.y : bmin.y,
                  n.z >= 0.0 ? bmax.z : bmin.z);
    if (dot(n, p) + planes[i].w < 0.0) return false; // whole box behind this plane
  }
  return true; // inside or straddling every plane; may still be a false positive
}

Boxes inside boxes make the cost depend on where the wedge's edge falls, not on the size of the world.

Under the hood: the math and the code

A spatial hierarchy is a tree of nested bounds. The root box covers the whole world and each child covers a quarter of its parent. Each node here also stores the tight box around its own objects, so it is really a small bounding volume hierarchy (a tree of boxes around boxes) laid out as a quadtree.

Walking the tree uses a three-way test per node. If the p-vertex, the corner farthest along a plane's normal, is outside any plane, the node is OUT and the whole subtree is skipped. If the n-vertex, the corner least along the normal, is inside every plane, the node is IN and every object under it is accepted without another test. Anything else is PARTIAL, and only then are the children opened.

Brute force is one test per object, every frame, whether the object is behind the player or not. The hierarchy costs the nodes visited plus the objects in leaves cut by an edge, about O(log N + k), where k is the number of objects near the frustum edge.

In words: brute force grows with the size of the world; the tree grows with what the frustum's edge touches.

brute force: tests = N hierarchy: tests = nodes visited + objects in straddling leaves ≈ O(log N + k), k = objects near the frustum edge node classify: p-vertex outside → OUT n-vertex inside → IN (n-vertex = corner least along n) otherwise → PARTIAL, open it

N is the number of objects and k the number sitting near the frustum's edge. The p-vertex and n-vertex are the two opposite corners of a node's box along a plane's normal n.

What this code does: tests one node, then either drops it, accepts it whole, or steps into its children.

void cullNode(Node n, Plane planes[6]) {
  int r = classify(n.bounds, planes);   // OUT, IN or PARTIAL, one box test
  if (r == OUT) return;                  // whole subtree gone for the price of one test
  if (r == IN) { emitAll(n); return; }   // no per-object tests either
  if (n.isLeaf) {
    for (Object o : n.items)
      if (aabbInFrustum(o.bmin, o.bmax, planes)) emit(o);
  } else {
    for (Node c : n.children) cullNode(c, planes);
  }
}

Skip what's hidden behind a wall

Three stone walls stand between the player and the village. Whatever is behind a wall is hidden, and the test that finds out needs distances from things already drawn.

Where the distances come from
Frame

Hidden-object tests need distances from things already drawn, so they run later, and the distances must come from this frame's camera.

Under the hood: the math and the code

Occlusion needs depth. The occluders are rasterized, meaning drawn, into a depth buffer: here a 1D strip of 256 texels, where a texel is one cell of a texture. That buffer is reduced into a pyramid in which each texel of level L holds the farthest depth of the 2L base texels under it. This is the hierarchical Z buffer, or Hi-Z, since Z is the usual name for depth.

To test an object, project its bounds to a span of texels. Pick the level where that span covers at most two texels, read those two, and if the object's nearest point is farther than the larger of them, nothing of it can show. Two reads answer the question for an object of any screen size.

With only the three walls as occluders the test is correct every frame but weak: small things hide nothing. With everything, last frame, every drawn house and tree becomes an occluder, at the cost of testing this frame's objects against last frame's depth. Move fast and objects that were hidden last frame but are visible now get culled anyway; they pop in a frame later.

The two-pass fix draws what was visible last frame first, builds the pyramid from that with the current camera, then tests only the remaining objects against it and draws the ones that pass. Depth always comes from the current camera, so nothing visible is ever culled. The price is the blue objects: drawn in pass one because they were visible before, hidden now.

In words: turn the object into a strip of screen cells, jump to the pyramid row where that strip is two cells wide, and compare the object's nearest distance with the farther of those two cells.

project: z_v = (p − cam)·fwd, x_v = (p − cam)·right sx = x_v / (z_v · tan(fov/2)) ∈ [−1, 1] texel = floor((sx + 1)/2 · 256) span: w = t1 − t0 + 1 texels level: L = ceil(log2(max(w, h))) → covers ≤ 2 texels test: occluded if z_nearest > max(HiZ[L][t0≫L], HiZ[L][t1≫L]) build: HiZ[L+1][i] = max(HiZ[L][2i], HiZ[L][2i+1])

p is a point on the object, cam the camera, fwd and right its two axes. z_v is depth and x_v the sideways offset as the camera sees them, sx is the screen position from −1 to 1, t0 and t1 are the first and last texel of the span, w and h its width and height, L the level, and ≫ shifts a texel index down to that level.

What this code does: the first function builds one pyramid level from the level below it; the second reads four texels at the chosen level and compares.

// build: each pass halves the texture and keeps the farthest depth
float hizReduce(sampler2D prev, ivec2 p) {
  vec4 d = textureGather(prev, (vec2(p) * 2.0 + 1.0) * invPrevSize); // the 2×2 block
  return max(max(d.x, d.y), max(d.z, d.w));   // min() instead if you use reversed Z
}
// test: ssMin/ssMax = screen-space box of the bounds, z = nearest depth
bool occluded(vec3 ssMin, vec3 ssMax) {
  vec2 sizePx = (ssMax.xy - ssMin.xy) * hizSize;
  int level = int(ceil(log2(max(sizePx.x, sizePx.y))));
  ivec2 t0 = ivec2(ssMin.xy * hizSize) >> level, t1 = ivec2(ssMax.xy * hizSize) >> level;
  float farthest = max(max(texelFetch(hiz, t0, level).r, texelFetch(hiz, ivec2(t1.x, t0.y), level).r),
                       max(texelFetch(hiz, ivec2(t0.x, t1.y), level).r, texelFetch(hiz, t1, level).r));
  return ssMin.z > farthest;   // nearest point behind everything in those texels
}

Rooms, doorways and a lookup table

The player walks through a castle with nine rooms. Walls hide almost everything, so the view only has to be squeezed through the doorways.

Squeezing the view through each doorway is exact for this spot; a lookup table trades that for one yes-or-no bit per room.

Under the hood: the math and the code

Portal culling starts in the room the camera is in. For each doorway of that room it clips the current frustum down to the doorway's outline. If anything is left, the walk continues into the next room with the narrower frustum. Rooms that no wedge reaches are never touched. In this 2D world a frustum is a range of angles, so the clip is just the overlap of two ranges.

A PVS, a potentially visible set, precomputes the answer per room: which rooms can be seen from anywhere inside this one, looking in any direction. The bits below are computed live by walking the portals from a 12×12 grid of sample points in every room and taking the union. At runtime that is one bit lookup per room, which is why Quake could afford it in 1996.

The cost is that the PVS is a superset of the portal result (the blue rooms), and it is only valid while the doors stay where they were when it was built. Bar a door and the whole matrix is rebuilt. Sampling can miss a sliver of visibility between two sample points, so offline tools such as Quake's vis clip portal against portal exactly instead of sampling.

The matrix below: one row per room, and a 1 in each column for a room that might be seen from it.

In words: the view is a range of angles, a doorway is a range of angles, and what passes through is the overlap of the two.

interval: frustum = [θ − fov/2, θ + fov/2] door: [min(a₁, a₂), max(a₁, a₂)], aᵢ = atan2(dᵢ − eye) clip: next = frustum ∩ door; recurse only if next ≠ ∅ PVS: bits[room] = ∪ over samples s in room of walk(s, 360°) 9 rooms → 81 bits ≈ 11 bytes; N rooms → N²/8 bytes

θ is the camera's aim angle and fov its field of view. a₁ and a₂ are the angles from the eye to the two ends of a door, ∩ is the overlap of two ranges, ∅ means nothing left, and ∪ means combining the results of every sample. N is the number of rooms.

What this code does: marks the room, then for every open door it can see through, narrows the view and steps into the next room. The last line is the whole runtime cost of a PVS.

void walkRoom(int room, Frustum f, Portal from) {
  markVisible(room);
  for (Portal p : rooms[room].portals) {
    if (p == from || !p.open) continue;
    Poly door = clipPolygon(p.quad, f);        // door quad against the current planes
    if (door.empty()) continue;
    Frustum g = planesThrough(eye, door);      // new side planes: eye through each door edge
    walkRoom(p.other(room), g, p);
  }
}
// PVS at runtime replaces all of the above with one bit test:
bool maybeVisible = pvs[cameraRoom][r >> 3] & (1 << (r & 7));

Skip what would be a speck

A forest stretches away from the player. A tree that would cover less than a few pixels on screen costs as much to draw as one up close, so it is skipped too.

Size culling is one divide per object: anything that would be a speck on screen is skipped.

Under the hood: the math and the code

A 2 m crate 300 m away is under a pixel wide on a 1080p screen. Drawing it costs a full draw, or a full instance (one copy of a shared mesh), for a speck that anti-aliasing will mostly remove. The projected radius follows from the bounding radius, the view depth and the vertical field of view, so the test is one division per object and it is usually folded into the same loop as the frustum test.

The threshold is a quality knob: 1 px is safe, 4 px is visibly aggressive on foliage. This 200 m world is too small for anything to fall under 2 px at 1080p, so the slider here goes far higher than a shipping threshold would.

In words: an object's radius in pixels is its real radius, shrunk by how far away it is and by how wide the lens is.

r_px = r · (H / 2) / (d · tan(fov_y / 2)), H = 1080 drop if 2 · r_px < threshold CPU estimate: N · 1 µs per test GPU estimate: N / (2 · 10⁹ instances per s) + ~20 µs dispatch (both estimates)

r is the bounding radius in metres, d the distance along the view direction, fov_y the vertical field of view, H the screen height in pixels and r_px the radius on screen. N is the instance count.

Let the GPU write its own list

The same forest, seen from the GPU's side: one worker per object runs the tests, and the survivors count themselves into the draw order.

Run the tests on the GPU, one worker per object, and the CPU never waits for an answer.

Under the hood: the math and the code

Once the tests are this simple, there is no reason for the CPU to run them. The GPU-driven version keeps every instance in a buffer and runs one thread per instance in a compute shader, a GPU program that is not tied to drawing. Threads that pass append their index to a visible list with an atomic add, an add that many threads can do at once without stepping on each other, on the instanceCount field of the indirect arguments, the small record that tells the GPU how much to draw.

The CPU issues one DrawIndexedIndirect per mesh without knowing how many survived, and nothing is read back. At 1 µs per test the CPU side of 5,000 objects is 5 ms, almost a third of a 60 Hz frame; the compute pass is a few microseconds (estimate).

What this code does: one thread per instance runs the frustum, size and Hi-Z tests, then grabs a slot in the visible list with one atomic add.

[numthreads(64, 1, 1)]
void CullCS(uint id : SV_DispatchThreadID) {
  if (id >= instanceCount) return;
  Instance inst = instances[id];
  float z = mul(view, float4(inst.center, 1)).z;
  float rPx = inst.radius * (screenH * 0.5) / (z * tanHalfFovY);
  if (!sphereInFrustum(inst.center, inst.radius, planes)) return;
  if (2.0 * rPx < minPixels) return;          // too small to matter
  if (hizOccluded(inst.center, inst.radius)) return;
  uint slot;
  // instanceCount lives inside the indirect args buffer; the add is the append
  InterlockedAdd(drawArgs[inst.meshId].instanceCount, 1, slot);
  visibleInstances[drawArgs[inst.meshId].firstInstance + slot] = id;
}
// CPU: DrawIndexedIndirect(argsBuffer, meshId * 20)   no readback, no wait
