LOD & Clusters

Everything a game draws is built from triangles, and one big rock can take thousands of them. When that rock is far away it covers only a few pixels, so drawing every triangle is wasted work. A level of detail, or LOD, is a cheaper copy of the rock with fewer triangles, swapped in when the missing detail would be smaller than a pixel anyway. This page follows one 14 m boulder at the end of a road while the player walks away from it. The thing people get wrong: the cheap copy should not be picked by distance. It should be picked by how far it strays from the true shape, measured in pixels on the screen, and whether anyone could see that.

Pick the copy by pixel error

The player walks down a road away from a big boulder. Four copies of the boulder exist, and the demo shows which one gets drawn and how far it strays on screen.

Pick the cheapest copy whose stray on screen stays under the allowed error; distance only matters through that.

Under the hood: the math and the code

Each level is made offline by decimation, which means removing one point at a time, always the one that moves the outline least, until the target count is reached. The level's error is then measured, not guessed: the largest distance in metres from any original point to the simplified outline. That one number is all the runtime needs.

At runtime the error is projected to pixels using the camera distance and the field of view, which is the angle the camera can see. The coarsest level whose projected error still fits under the threshold τ wins.

In words: pixel error is the world error scaled by how big a metre looks at this distance; pick the coarsest level under τ; the switch distance is where a level's error crosses τ.

e_px = e_world · (H/2) / (d · tan(fov/2)) LOD = max { L : e_px(L) ≤ τ } d_switch(L) = e_L · (H/2) / (τ · tan(fov/2))

e_world is the level's measured error in metres, H the screen height in pixels (1080 here), d the camera distance, fov the vertical field of view, L the level and τ the threshold.

Switching meshes at one exact distance pops. The usual fix is a dithered cross-fade: over a short band past the switch distance both levels are drawn, and a fixed 4×4 pattern of dots called a Bayer mask decides which pixels belong to which level. Each pixel is drawn exactly once, so it works inside the normal opaque pass with a single depth write.

TAA, the anti-aliasing that blends frames over time, smooths the dots away. The cost is that both levels are drawn during the fade.

What this code does: converts metres to pixels, walks the levels and keeps the last one under τ, then uses the dot pattern to split pixels between the two levels during a fade.

float projectError(float eWorld, float dist) {
  return eWorld * (0.5 * viewportH) / (dist * tan(0.5 * fovY));   // metres -> pixels
}
int selectLOD(MeshLODs m, vec3 camPos, float tau) {
  float d = max(distance(camPos, m.center) - m.radius, nearZ); // closest point of the bounds
  int lod = 0;
  for (int i = 1; i < m.count; i++)
    if (projectError(m.error[i], d) <= tau) lod = i;   // error[] grows with i, so the last pass wins
  return lod;
}
// pixel shader, both levels drawn during the fade band
float t = bayer4x4[ivec2(gl_FragCoord.xy) & 3] / 16.0;
if (isOutgoingLOD ? (t < fade) : (t >= fade)) discard;      // masks are complementary: every pixel drawn once

Why tiny triangles cost so much

The boulder is 800 m away and only 17 pixels wide, but its mesh is still 2048 triangles. One of them sits on a 16×16 pixel patch of the screen, and the demo counts the colouring work it causes.

Every triangle pays for whole 2×2 blocks of pixels, so pixel-sized triangles cost up to four times more than they look.

Under the hood: the math and the code

The quad exists because of derivatives. dFdx and dFdy are shader functions that ask how much a value changes to the next pixel over, and they need a neighbour to subtract. Mip selection, which picks how blurry a copy of the texture to sample, uses those derivatives.

A triangle that covers one pixel centre still launches all four lanes. The three extras are helper lanes: they run the full shader and their results are thrown away.

Tile the whole area with pixel-sized triangles and the shader runs roughly four times per output pixel. The rasterizer, the fixed hardware that turns triangles into pixels, also spends its per-triangle setup rate on triangles that cover nothing. This is why a 2048-triangle mesh at 500 m is a bad idea even though it draws in one call.

In words: count the 2×2 blocks the triangle touches, multiply by four for lanes, and divide the useful pixels by that.

quads touched = |{ q : some pixel centre in q is covered }| lanes launched = 4 · quads touched quad efficiency = covered pixel centres / lanes launched

q is one quad, a 2×2 block of pixels. A pixel centre counts as covered when it falls inside the triangle.

Nanite, the cluster renderer in Unreal Engine 5, sidesteps the quad rule for its smallest clusters. Clusters whose triangles are only a few pixels wide are rasterized in a compute shader, a GPU program that runs outside the fixed pipeline, one pixel at a time. Each pixel records depth and a triangle id in a 64-bit visibility buffer, using an atomic max so the nearest triangle wins.

Large triangles still go through the hardware path. Material shading then runs once per pixel from that buffer, so shading cost stops depending on triangle size at all.

What this code does: shows the derivative read that forces the quad to exist, then Nanite's per-pixel write that packs depth and triangle id into one 64-bit number.

// why the quad exists: derivatives are differences across the 2x2 block
vec2 duvdx = dFdx(uv);                // reads the lane to the right, even if it lies outside the triangle
vec2 duvdy = dFdy(uv);
float lod = log2(max(length(duvdx * texSize), length(duvdy * texSize)));
vec4 albedo = textureLod(tex, uv, lod);
// helper lanes execute every line above and then write nothing.
// Nanite's software path for small triangles, per pixel, no quads:
uint64 packed = (uint64(depthBits) << 32) | (clusterId << 7) | triIndex;
InterlockedMax(visBuffer[pixel], packed);   // nearest depth wins, id rides along

Let each chunk pick its own level

The same boulder seen from above, with the player standing beside it. The outline is cut into clusters, and each one chooses its own level of detail.

Split the mesh into clusters and give each an error that only grows upward; then every cluster can pick its own level with no cracks.

Under the hood: the math and the code

Building the hierarchy: take neighbouring clusters, merge them into one group, simplify the group to half its segments, split the result back into clusters, and repeat until one cluster is left. The result is a DAG, a directed acyclic graph, which is a tree where a child may have more than one parent.

Points on a group's boundary are locked during simplification, so two groups always agree on their shared edge. The next level shifts the grouping, which moves those locked boundaries into the middle of a new group where they can finally be simplified.

Every cluster stores two errors: the error of the group that made it and the error of the group that consumed it. Both are made monotonic, meaning a parent's error is always at least the largest error below it. The cut then needs one test per cluster with no walk up or down the tree.

All clusters from one group share one error and one bounding sphere, the sphere that encloses them and gives the distance. So siblings decide identically, and a group boundary is either drawn at the same points on both sides or replaced as a whole. That is where the crack-free guarantee comes from.

In words: draw a cluster when its parent's error is too big for τ but its own error fits; because errors and bounds only grow going up, exactly one cluster on each path passes.

draw cluster c ⇔ parent_error_px(c) > τ ≥ cluster_error_px(c) parent_error ≥ max(child errors), parent bounds ⊇ child bounds ⇒ e_px monotonic on every root-to-leaf path vertex test: dist(p, ab) = |(b − a) × (p − a)| / |b − a| (Douglas-Peucker, kept if largest)

parent_error_px and cluster_error_px are the two stored errors projected to pixels. The vertex test is the point-to-segment distance used while simplifying: a and b are the segment ends, p the point being judged.

The GPU version runs one thread per cluster. After the error test it drops clusters outside the frustum, the wedge of space the camera can see, and clusters hidden behind others according to the HZB, a stack of shrinking depth images. Survivors go into a list that one indirect draw consumes, meaning a draw call whose arguments the GPU wrote itself.

What this code does: one GPU thread per cluster tests the two errors, drops what is out of view or hidden, and appends the survivors to the list a single indirect draw will eat.

[numthreads(64, 1, 1)]
void CullClusters(uint id : SV_DispatchThreadID) {
  Cluster c = clusters[id];
  float dC = sphereDistance(cam, c.lodBounds);     // bounds of the group that MADE c
  float dP = sphereDistance(cam, c.parentBounds);  // bounds of the group that CONSUMED c
  float eC = projectError(c.lodError, dC);
  float eP = projectError(c.parentError, dP);     // +inf for the root
  if (!(eP > tau && eC <= tau)) return;             // exactly one cluster per path passes
  if (!inFrustum(c.bounds) || occludedByHZB(c.bounds)) return;
  uint slot; InterlockedAdd(visibleCount, 1, slot);
  visibleClusters[slot] = id;                        // one indirect draw eats this list
}

Load only the pages you need

A valley with twelve of these boulders and one road. Their cluster data sits in 128 KB pages, and the demo shows which pages are in video memory as the player moves.

Stream the hierarchy in 128 KB pages, keep the root always, and drop the finest pages first; the mesh only ever gets briefly coarser.

Under the hood: the math and the code

Clusters are packed into fixed-size pages, coarsest levels first, so page 0 holds the top of the hierarchy and is never evicted. The cull pass that computes the cut also notices when a chosen cluster lives in a page that is not loaded. It writes a request, draws the nearest loaded ancestor instead, and the CPU streams the page in over the next frames.

Over budget, the finest pages are evicted first. An instance whose cut lost a page raises its own threshold until its cut fits in loaded memory. A coarser cut is still a valid cut, so the crack-free property survives eviction.

In this demo a page holds 4 clusters. That is a stand-in for engines that quantize and compress geometry to pack far more clusters into the same 128 KB.

In words: the loaded set is the root page plus every page any instance's cut touches; if that exceeds the budget, an instance loosens its τ to the next error step until its cut fits.

resident = page(root) ∪ ⋃ᵢ { page(c) : c ∈ cut(instanceᵢ, τᵢ) } constraint: |resident| · 128 KB ≤ budget fallback: τᵢ ← min { e_px(c) : e_px(c) > τᵢ } until cut(instanceᵢ, τᵢ) ⊆ resident

resident is the set of loaded pages, cut(instanceᵢ, τᵢ) the clusters instance i draws at its own threshold τᵢ, and page(c) the page that holds cluster c.

What this code does: on the GPU a missing page becomes a request and the cluster falls back to a loaded ancestor; on the CPU requests are sorted by priority, old pages are evicted until there is room, and new ones load.

// inside the cull pass, after the cut test passed for cluster c
if (!pageResident[c.page]) {
  InterlockedMax(pageRequest[c.page], priorityFromError(eC));  // GPU -> CPU readback next frame
  c = nearestResidentAncestor(c);      // same DAG, coarser cut, still crack-free
}
// CPU, once per frame
sortRequestsByPriority();
while (residentBytes + PAGE_BYTES > budget) evict(leastRecentlyRequestedPage());
for (req : requests) if (residentBytes + PAGE_BYTES <= budget) load(req.page);

Triangle count as you back away

Per-cluster LOD follows the pixel budget far more closely than whole-mesh levels, and ships as one draw request to the GPU.

Under the hood: the math and the code

The discrete curve is a staircase: each step is one switch distance from the first demo. The cluster curve steps more often and more gently, because each of the 33 clusters switches at its own distance and the near side of the boulder stays finer than the far side. Both reach the same floor of 32 triangles; the difference is how much they overshoot in between.

Draw calls, the requests the CPU sends to the GPU, tell the other half. Discrete LOD costs one draw per mesh per instance, or one instanced draw per level in use. The cluster path is one indirect draw for the whole scene, paid for with a cull dispatch that walks the hierarchy from the root and stops at the cut. The dashed line counts those visits.

In words: the triangle count is the sum over the clusters in the cut; the nodes visited are every cluster whose ancestors all failed the test.

triangles(d) = Σ_{c ∈ cut(d)} tris(c) nodes visited = |{ c : every ancestor of c has e_px > τ }| (traversal stops at the cut)

cut(d) is the set of clusters drawn at distance d, tris(c) the triangle count of cluster c.

What this code does: walks the hierarchy with a stack, emits a node as soon as its error fits under τ, and otherwise pushes its children, skipping any it has already seen.

// hierarchical cull: a stack of nodes, stop where the cut passes
push(root);
while (!empty()) {
  Node n = pop(); visited++;
  if (projectError(n.error, sphereDistance(cam, n.bounds)) <= tau) { emit(n); continue; }
  for (child : n.children) if (!seen(child)) push(child);   // DAG: siblings share children
}

The trap is the phrase "LOD distance": the real rule is triangle size on screen, which is projected error. A 200 m cliff at 1 km still needs its 1 m ledges, and a pebble at 3 m does not need 2048 triangles. Any setting that takes a distance quietly assumes an object size, and a huge object far away is where that guess breaks.
