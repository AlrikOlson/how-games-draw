Virtual Texturing

A texture is a picture wrapped over a surface, and a virtual texture is one so big that the graphics card never holds it all. On this page it is the painting of a one-kilometre game world: forest, river, village, fields. The card keeps only the small squares the camera is looking at right now, so texture memory stays at a fixed size no matter how big the world gets. The thing people get wrong: this does not make the game smaller to download. The whole painting still sits on disk. What shrinks is the amount in graphics memory at any one moment, and the cost of a texture stops depending on how big it is and starts depending on how many pixels it covers on screen.

A huge painting, a small cache

A camera flies low over a painted 1 km world. Drag the camera on the map, and the grid beside it shows which pieces of the painting are in memory right now.

Far ground sharpness (anisotropic filtering)

How many pages a view needs is set by the pixels on screen, so a 4 MiB cache can serve a 4 GiB painting.

Under the hood: the math and the code

Numbers first. 32,768² texels at 4 bytes each (RGBA8: one byte each for red, green, blue and transparency) is 4 GiB. Add the mip chain, the stack of half-size copies down to a single page at mip 8, and it's 5.33 GiB. Compressed as BC7, a GPU format that spends about one byte per texel, it's 1.33 GiB.

Cut into 128² pages, that's 256×256 pages at mip 0, 128×128 at mip 1, and one page at mip 8. The physical cache is an ordinary GPU texture of 2048² texels: 16×16 slots, 4 MiB as BC7. A page's slot has nothing to do with where it sits on the map; the page table in the next section remembers where each one went.

What one view needs is bounded by screen pixels, not by world area. A 1920×1080 frame at one texel per pixel touches about 127 pages plus the partial pages along their edges, whichever mips they come from. Next to the camera those are mip-0 pages covering 4 m of ground; at the horizon one mip-8 page covers the whole kilometre. Raising the camera moves demand to coarser mips without adding much.

Anisotropic filtering does add. At a grazing angle a pixel's footprint on the ground is long and thin. The sampler picks the mip that suits the thin axis, so the ground near the horizon asks for finer pages, and there are many more of those.

In words: the full texture is gigabytes, the cache is 4 MiB, and a 1080p view needs about 127 pages of it.

virtual = 32768² · 4 B = 4.00 GiB at mip 0 · ×4/3 with mips = 5.33 GiB · BC7 (1 B/texel) = 1.33 GiB pages(m) = (256 >> m)² 256² + 128² + … + 1² = 87,381 pages in the chain cache = 256 slots · 128² · 1 B = 4 MiB one page = 16 KiB as BC7 need ≈ W·H / 128² + partials = 1920·1080 / 16384 ≈ 127 pages at 1 texel per pixel

pages(m) is the number of pages per side at mip m. W·H is the screen size in pixels, and 128² is the texels in one page.

What this code does: measures how many texels one screen pixel covers, turns that into a mip level, and finds which page that lands in.

// which page does this pixel want? (same rule in the feedback pass and the sampler)
vec2  dx = dFdx(uv) * VT_SIZE, dy = dFdy(uv) * VT_SIZE;   // texels per screen pixel
float rhoMax = max(length(dx), length(dy));
float rhoMin = min(length(dx), length(dy));
float lod = log2(max(rhoMax / MAX_ANISO, rhoMin));        // aniso: the thin axis picks the mip, capped
uint  mip = uint(clamp(floor(lod), 0.0, 8.0));
uvec2 page = uvec2(uv * float(256u >> mip));               // 256 pages per side at mip 0

Finding a page in the cache

Hover the 256 m of map around the camera to follow one pixel's question from its spot on the painting to the cache slot that answers it.

Which copy the pixel asks for (mip)

One table read, one cache read: the table always hands back something usable, just maybe blurrier than you asked for.

Under the hood: the math and the code

The page table is itself a small mip-mapped texture: one texel per page, 256² texels at mip 0, 87,381 texels across the whole chain, about 340 KB as RGBA8. Each entry stores the slot coordinates and the mip of the page that sits in that slot.

Entries for pages that aren't resident are filled with their nearest resident ancestor, the closest blurrier page up the mip chain that is loaded. So the shader never walks. One fetch at the requested mip returns a page it can use, and the gap between the mip it asked for and the mip it got is how blurry that pixel will be.

The physical coordinate is scale and bias. Take the uv (the sample's position on the texture, 0 to 1 on each axis), keep the fraction that falls inside the resident page, add the slot's origin, and multiply by page size over cache size. The screen-space derivatives, how much uv changes from one pixel to the next, have to go through the same scale, or the hardware picks the wrong mip inside the cache. That's why the fetch is a textureGrad and not a plain texture call.

In words: look up the entry for the page you want, then place your sample inside whichever slot the entry names.

pagesAt(m) = 256 >> m page id = ( m, ⌊u·pagesAt(m)⌋, ⌊v·pagesAt(m)⌋ ) entry = pageTable[m][py][px] = (sx, sy, m_res) m_res ≥ m, copied from the nearest resident ancestor inPage = frac( uv · pagesAt(m_res) ) uv_phys = ( (sx, sy) + inPage ) · 128 / 2048

m is the requested mip, (px, py) the page's grid position, (sx, sy) the slot it lives in, m_res the mip of the page that's really there, and uv_phys the final position in the 2048² cache.

What this code does: one page-table read, a little arithmetic, one cache read with the derivatives corrected.

vec4 sampleVT(vec2 uv, float lod) {
  // page table: RGBA8, one texel per page, its own mip chain matches the virtual texture
  vec4 e = textureLod(pageTable, uv, lod);          // lod = floor(mip the pixel wants)
  float resMip = e.b * 255.0;                        // mip of the page that is really there
  float scale  = exp2(8.0 - resMip);                 // pages per side at that mip
  vec2 inPage  = fract(uv * scale);
  vec2 uvPhys  = (e.rg * 255.0 + inPage) * (128.0 / 2048.0);
  float g = scale * (128.0 / 2048.0);                // virtual → physical derivative scale
  return textureGrad(physCache, uvPhys, dFdx(uv) * g, dFdy(uv) * g);
}

How the GPU asks for pages

The camera walks over the world on its own, or you drag it. Watch the ground pop from blurry to sharp a few frames after each page was asked for.

The GPU draws a tiny shopping list of pages, the CPU loads a few per frame, and everything else waits on a blurry stand-in.

Under the hood: the math and the code

A 1/8-resolution pass, 240×135 here, writes the page id each pixel would sample into an integer render target. The CPU reads that buffer back a frame or two later, so it never stalls the GPU, and squeezes 32,400 entries down to a few hundred unique page ids. Then it compares them with the resident set, the pages already in the cache.

1/8 is enough because a page covers at least 128 screen pixels on a side at the mip the pixel asked for, so every page still lands in at least one feedback texel.

Then there's a budget. The disk read, the BC7 transcode and the upload each cost time, so a frame issues N loads and the rest wait in a queue. Until a page lands, its pixels take the coarser entry the page table already holds. Loads go coarse first: one mip-3 page in flight fixes 64 mip-0 pages' worth of ground at once. When the camera turns fast, requests outrun arrivals, and that gap is the pop-in.

In words: a small render lists the pages, each id packs into 32 bits, and the round trip costs about three frames.

feedback = (1920/8) × (1080/8) = 240 × 135 = 32,400 texels · R32UI = 130 KB readback per frame id = mip << 24 | py << 12 | px (4 + 12 + 12 bits) lod_fb = log2(ρ_fb) − 3 derivatives at 1/8 res are 8× too large latency ≈ 2 frames readback + 1 frame decode and upload = 50 ms at 60 Hz (estimate; a cold disk adds more)

px and py are the page position, mip the level, ρ_fb the texels per pixel measured at 1/8 resolution, and the −3 undoes that 8× shrink (2³ = 8).

What this code does: measures texels per pixel, picks a mip, and packs mip and page position into one integer.

// feedback.frag: 1/8-res target, one R32UI page id per texel
uint main(vec2 uv) {
  vec2 dx = dFdx(uv) * 32768.0, dy = dFdy(uv) * 32768.0;
  float rho = max(length(dx), length(dy)) / MAX_ANISO;
  rho = max(rho, min(length(dx), length(dy)));
  float lod = log2(rho) - 3.0 + mipBias;             // -3: this buffer is 1/8 of the screen
  uint m = uint(clamp(floor(lod), 0.0, 8.0));
  uvec2 p = uvec2(uv * float(256u >> m));
  return (m << 24u) | (p.y << 12u) | p.x;           // 0xFFFFFFFF = nothing sampled here
}

When the cache runs out of room

Throwing out the longest-unused slot works until a view wants more pages than there are slots; then only a bigger cache or less detail helps.

Under the hood: the math and the code

Each slot remembers the last frame a pixel used it. When a page arrives and no slot is free, the least recently used slot (LRU) is overwritten, and the page-table entries that pointed at it revert to the ancestor. That works while the working set, the pages one view needs, fits in the cache.

When it doesn't, the loop turns on itself. Every slot was used this frame, so the eviction takes a page that's needed again next frame. Loads per frame sit at the budget forever, and the hit rate can't rise above slots ÷ demand.

Mip bias −1 makes every pixel ask for the mip with four times the texels, which is what an "ultra" texture setting or a 4K target does to the same cache. Zooming out doesn't do this: demand is pixel-bounded, so a far view just moves it to coarser mips. Many small objects do, because each one needs at least one page per layer no matter how few pixels it covers.

The pinned coarse mips, 21 pages that never leave, are what keeps a thrashing cache from ever showing nothing. The fixes are a bigger physical texture, fewer layers per cache, or a smaller bias, not a cleverer eviction policy.

In words: hit rate is the share of wanted pages already loaded, and once demand exceeds the slot count it's capped at slots over demand.

hit rate = |requested ∩ resident| / |requested| steady state with demand D > slots S: hit ≤ S / D, loads/frame = budget, evictions/frame = budget bias b: texels per pixel × 4^(−b) → up to 4× the pages per −1 step, less once the near ground clamps at mip 0 LRU age = frame − lastUsed[slot] victim = argmax age over unpinned slots

S is the slot count (256), D the pages the view wants, b the mip bias, and lastUsed[slot] the frame a slot was last sampled.

What this code does: reads the two-frame-old feedback, marks the hits, loads the missing pages coarse first, and evicts the oldest slot when one arrives.

// CPU, once per frame
ids       = readback(feedback[frame - 2]);              // two frames old: never wait on the GPU
requested = unique(ids);                                 // 32,400 texels → a few hundred pages
for (p : requested) if (resident(p)) lastUsed[slot(p)] = frame;
missing = requested − resident − inFlight;
sort(missing, coarseMipFirst);
for (p : take(missing, budget)) issueLoad(p);            // disk → transcode → upload, lands in ~3 frames
for (p : arrived()) {
  s = freeSlot() ?? evictLRU();                          // evicting a slot used this frame = thrash
  upload(p, s);
  pageTable.write(p, s);                                 // and refill the entries of p's non-resident descendants
}

Neighbouring pages are not neighbours in the cache, so every page carries a copied border, and far-ground sharpness gets capped near 8×.

Under the hood: the math and the code

Bilinear filtering reads a 2×2 block of texels and blends them, so any sample within half a texel of a slot edge blends in the neighbouring slot, which holds an unrelated page. The fix is to store each page with a border of b texels copied from its virtual neighbours.

The unique content then shrinks to (p − 2b)² texels. A 128² page with a 4-texel border gives up 12.1 % of the cache; a 256² page gives up 6.1 %. Some engines keep 128 unique texels and store 136² slots instead; the arithmetic comes out the same.

Anisotropic filtering takes up to N taps along the long axis of the footprint, and the hardware places them in physical space with no idea where the page ends. A 4-texel border covers about 8× anisotropy; past that the seam comes back, which is why engines clamp anisotropy on virtual textures. Trilinear filtering, which also blends in the next blurrier mip, needs the coarser mip of the same page, so physical caches usually carry a short mip chain per slot.

A runtime virtual texture never loads pages at all. Each page is drawn into its slot from layers (the terrain material, a splat map saying how much of each material goes where, decals such as the chalk ring on the square) when the feedback pass asks for it. The border comes free: the viewport is widened by b texels and the same layers are drawn once. There's no disk copy of the texture, so the install doesn't grow with it either.

In words: a border of b texels leaves (p − 2b)² unique texels and covers filter taps that reach about N/2 texels.

inner = p − 2b unique texels per side lost = 1 − (inner / p)² p=128, b=4 → 12.1 % · p=256, b=4 → 6.1 % reach = 0.5 texel (bilinear) · ≈ N/2 texels (aniso N) → need b ≥ N/2 + 0.5 uv_phys = ( slot·p + b + frac(uv·pagesAt(m_res)) · inner ) / 2048

p is the page size in texels, b the border width, N the anisotropy level, and inner the texels that belong to the page alone.

What this code does: places the sample inside the inner region of its slot, then, for a runtime page, draws the layers into a slot rectangle widened by the border.

// physical uv with a b-texel border: unique texels live in [b, p − b)
vec2 inPage = fract(uv * scale);
vec2 uvPhys = (e.rg * 255.0 * P + b + inPage * (P - 2.0 * b)) / PHYS_SIZE;
// derivatives scale by inner/P as well, or the cache mip is off by a hair

// runtime VT: the page is rendered, not loaded
void fillPage(Page p, Slot s) {
  Rect vp = slotRect(s).expand(b);                    // border by rendering, no copies
  Rect uv = pageRect(p).expand(b / float(P - 2*b));   // same widening in virtual space
  for (layer : [base, splat, decals]) draw(layer, vp, uv);
}

One trap: virtual texturing does not make the game smaller to install. The whole texture still lives on disk, and unique texturing usually makes that copy bigger than a game built from repeating materials would need. What shrinks is the graphics memory in use, which becomes a fixed number chosen up front, and the per-frame cost, which tracks screen pixels instead of world size.
