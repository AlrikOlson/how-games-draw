Transparency & Sorting

A see-through pixel is a stack of blends, and the GPU stacks them in the order you draw. Get the order wrong and glass over smoke comes out a different colour from smoke over glass, which is why every engine has a separate translucent pass that sorts, fakes, or works around the problem, and none of the cheap ways is exact. The thing people get wrong is premultiplied alpha. It does not change which order is correct; it changes what the numbers in a colour mean, and that is what makes filtering and grouping of layers come out right.

Every time the GPU draws a see-through pixel, it mixes the new colour into whatever is already there and forgets the old value. It keeps no list of layers. So the draw order is the only thing that decides the final colour, and swapping two draws changes the picture everywhere they overlap.

    The real version

    The blend unit is the fixed piece of hardware that runs one formula per fragment, where a fragment is one candidate colour for one pixel from one triangle. It reads the target, multiplies, adds, and writes back. The formula is called "over".

    Straight alpha stores colour and alpha as separate numbers. The new pixel is the source colour scaled by its alpha, plus the old pixel scaled by one minus that alpha. Premultiplied alpha stores the colour already scaled by its alpha, so the source is added as-is and only the old pixel gets scaled.

    Premultiplied over is associative, which means you can blend B and C into a group first and then put A over the group, and get the same answer as blending one at a time. Straight over is not, because once (A over B) is treated as a new source its colour is scaled by alpha a second time. Neither convention changes which order is correct.

    In words: new pixel = new colour times its alpha, plus old pixel times whatever alpha is left over.

    straight: C = C_src·α + C_dst·(1 − α) premultiplied: C′ = C′_src + C′_dst·(1 − α_src) with C′ = C·α alpha: α_out = α_src + α_dst·(1 − α_src) premultiplied over is associative: (A over B) over C = A over (B over C) straight over is not: once (A over B) is treated as a new source, its color is scaled by alpha a second time.

    C_src is the incoming colour and C_dst the colour already in the target. α is the alpha of the incoming fragment. C′ is a premultiplied colour, meaning the colour times its alpha. α_out is the alpha left in the target after the blend.

    What this code does: sets the blend state for each convention, and shows a shader that premultiplies a straight texture on the fly so it can use the ONE state.

    // straight-alpha source: texture stores rgb and a separately
blend.srcColor = SRC_ALPHA;   blend.dstColor = ONE_MINUS_SRC_ALPHA;
blend.srcAlpha = ONE;         blend.dstAlpha = ONE_MINUS_SRC_ALPHA;

// premultiplied source: texture stores rgb·a, or the shader does it
blend.srcColor = ONE;         blend.dstColor = ONE_MINUS_SRC_ALPHA;
blend.srcAlpha = ONE;         blend.dstAlpha = ONE_MINUS_SRC_ALPHA;

float4 ps(...) {
  float4 t = tex.Sample(uv);         // straight (rgb, a)
  return float4(t.rgb * t.a, t.a);   // premultiply, use the ONE state
}
depth.write = false;  depth.test = LESS_EQUAL;   // see section 5

    The two squares above show the dark fringe bug. An 8×8 amber disc sprite sits over a blue quad, magnified 32× so each texel, one pixel of the texture, is a big square. The texels outside the disc have α = 0, and most exporters write black into their RGB. When the GPU smooths the edge by averaging neighbouring texels, straight alpha averages that black into the edge before the blend, and you get a dark rim. Premultiplied texels outside the disc are (0,0,0,0) by definition, so the same averaging adds nothing wrong. This is why engines premultiply at import or in the shader.

    Blending forgets earlier layers, so draw order alone decides the colour; premultiplying fixes filtering and grouping, not order.

    Sorting whole objects, one number each

    Drag the camera or its aim point and watch where sorting by object gets the per-pixel order wrong.

    Engines do not sort pixels. They sort whole objects by one distance number each and draw them far to near. That works until one object reaches both in front of and behind another. Then no single number is right for every pixel it covers, and some columns of the screen come out the wrong colour.

    What you're seeing

    The strip under the map is one row of the screen, 256 columns wide, rendered twice. The top row is the true answer, with each column's ray blending the fragments it crosses in real depth order. The middle row is what object sorting produced. Red marks along the bottom are the columns where the two disagree. The white ray on the map is one such column, and its hit dots are numbered in true depth order.

    The real version

    A sort key is one number per object, usually the distance from the camera to the center of its bounds, the box that fits around it. A pixel needs one number per fragment. Whenever an object is long enough that parts of it sit on both sides of another object, no single key can be right for every pixel it covers.

    Two crossing planes are the textbook case. A small object inside a big translucent volume, such as a character inside a glass tube or a fish inside a water volume, is the one that shows up in shipped games.

    In words: give each object one distance, draw them farthest first, and accept that this is only right at a pixel when the object order and the fragment order agree there.

    key(obj) = |center(obj) − cam| or view-space z draw order = sort(translucents, key descending) correct at a pixel only if, for every pair (i, j) it covers: key(i) > key(j) ⇔ t_i > t_j

    key(obj) is the one number the sort uses, either the straight-line distance to the camera or the depth along the camera's forward direction. t_i is the true distance along the pixel's ray to the fragment from object i. The sort is correct at that pixel only when the keys and the true distances agree for every pair.

    What this code does: computes one key per object on the CPU, sorts far to near, sets the blend and depth state, and draws.

    // per frame, CPU side, after culling
for (obj : translucents)
  obj.key = length(obj.bounds.center - cam.pos);   // or dot(center - cam.pos, cam.forward)
sort(translucents, [](a, b){ return a.key > b.key; });    // far to near
setBlend(premultipliedOver); setDepth(test = LESS_EQUAL, write = false);
for (obj : translucents) draw(obj);
// inside one mesh the triangle order is whatever the index buffer says;
// a few engines also sort triangles for glass, most do not

    One sort key per object cannot be right for every pixel once objects overlap in depth, and that is the default everything else on this page is trying to beat.

    Skip the blend: cutouts and dither

    Drag the leaf by fractions of a pixel and fade it out, and compare four ways of never blending at all.

    hover a pixel

    The cheapest fix is to refuse to blend at all. Each pixel is either fully leaf or fully background, so the draw can write depth and sort with the solid objects, and order stops mattering. The price is the soft edge, and each of the four methods here buys part of it back in a different way.

    The real version

    Alpha test keeps a pixel if its alpha is at least 0.5 and throws it away otherwise. It keeps the 0.5 contour of the texture and nothing else, so below 50 % opacity the whole leaf vanishes.

    Alpha-to-coverage uses MSAA, multisample anti-aliasing, where each pixel has several coverage samples that get averaged at the end. It turns alpha into a count of those samples, so 4× gives five levels of edge: 0, 1, 2, 3 or 4 samples covered.

    A Bayer dither compares alpha against a fixed 4×4 pattern of thresholds tiled across the screen, so a 50 % alpha keeps every other pixel in a checker. That gives 16 levels, but as a visible pattern. Rotate the pattern every frame and let TAA average 8 frames, and the pattern settles to a smooth blend, the same idea as stochastic transparency.

    In words: alpha test compares to 0.5; coverage rounds alpha to a sample count; dither compares to a pattern; TAA averages 8 different patterns.

    alpha test: keep if α ≥ 0.5 A2C, N samples: n = round(α·N), write n sample slots Bayer 4×4: B = [ 0 8 2 10 ] [12 4 14 6 ] [ 3 11 1 9 ] [15 7 13 5 ] T(x,y) = (B[x&3][y&3] + 0.5) / 16 keep if α > T(x,y) TAA, 8 frames: T_f = fract(T + f/8) result ≈ (1/8) Σ_f [α > T_f] err tiles: mean |result − ref| × 255, ref = α·leaf + (1−α)·bg

    α is the pixel's alpha after the opacity fade. N is the MSAA sample count, 4 here. B is the Bayer matrix and T(x,y) the threshold it gives the pixel at screen position (x, y). f is the frame number, and the bracket is 1 when the test passes and 0 when it fails. ref is the true blend the error tiles compare against.

    What this code does: looks up the pixel's dither threshold, rotates it by the frame number, and discards the pixel if its alpha is below it, all with depth writes on.

    static const float bayer4[16] = { 0, 8, 2,10, 12, 4,14, 6, 3,11, 1, 9, 15, 7,13, 5 };

void ps(float4 px : SV_Position, float2 uv, uint frame) {
  float a = tex.Sample(uv).a * fadeOpacity;
  uint  i = (uint(px.x) & 3) + 4 * (uint(px.y) & 3);
  float t = (bayer4[i] + 0.5) / 16.0;
  t = frac(t + frame * 0.125);          // rotate the pattern so TAA sees all 8 thresholds
  if (a < t) discard;                   // stochastic alpha test: writes depth, no blend
}
// alpha-to-coverage instead: output a as-is, set AlphaToCoverageEnable = true,
// the hardware writes round(a * sampleCount) of the MSAA samples

    If every pixel is all-or-nothing you can write depth and forget about order; the four methods differ only in how they hide the hard edge.

    Order-independent transparency, or OIT, means getting the right picture without sorting the draws. There are two ways. One keeps every fragment for every pixel and sorts them at the end, which is exact but needs an open-ended amount of memory. The other adds everything up with a weight and never sorts, which is cheap and bounded but only ever approximately right.

    What you're seeing

    The same five objects rendered into a 160×90 buffer three ways. Top left is the usual sort by object center. Top right is weighted blended OIT. Bottom left is a per-pixel linked list, sorted per pixel, which is the ground truth the other two are compared against.

    Bottom right is a heatmap. By default it shows how many translucent fragments landed on each pixel, from 0 to 5. Switch it to show where the sorted or the weighted image differs from the exact one; black is no error, full brightness is 64/255 or more.

    Try this

    • Set the heatmap to "sorted error" and walk into the scene. The bright patches are the pixels where object sorting picked the wrong order.
    • Set the WBOIT weight to "w = 1". With no weighting it becomes a plain average, and near objects stop hiding what is behind them.
    • Watch the "list memory" tile as you walk into the objects. More fragments per pixel means more nodes, and the bracketed figure is what that would cost at 1080p.

    The real version

    Weighted blended OIT never sorts. Every fragment adds its premultiplied colour times a weight into one accumulation target, and multiplies its transmittance, the fraction of light it lets through, into a second. The weight depends on depth and alpha, chosen so nearer and more opaque fragments count for more. One full-screen resolve pass divides the sum by the total weight.

    It costs one extra RGBA16F target and one R8 or R16F target. It is wrong wherever two fragments at similar depths have very different alpha, or where a nearly opaque fragment should hide what is behind it. The heatmap shows exactly where.

    A per-pixel linked list stores every fragment. The pixel shader atomically bumps a counter to allocate a node, writes colour, depth and the previous head, and swaps its node in as the new head of that pixel's list. A resolve pass walks each list, sorts it (usually an insertion sort of up to 8 or 16 entries in registers) and composites. It is exact, and the price is unbounded memory: the node buffer must be sized for the worst frame, and it is silently wrong when it overflows.

    In words: WBOIT adds up colour times weight, multiplies up what gets through, then divides once at the end. A linked list costs 12 bytes per fragment plus 4 bytes per pixel.

    WBOIT weight, McGuire & Bavoil 2013, eq. 9: w(z, α) = α · clamp( 0.03 / (1e−5 + (z/200)⁴), 1e−2, 3e3 ) z in metres eq. 7: w(z, α) = α · clamp( 10 / (1e−5 + (z/5)² + (z/200)⁶), 1e−2, 3e3 ) accumulate (additive blend): accum += (C·α·w, α·w) transmittance (multiplicative): reveal *= (1 − α) resolve: C = (accum.rgb / max(accum.a, 1e−5)) · (1 − reveal) + C_bg · reveal linked list node = rgba8 (4 B) + depth f32 (4 B) + next u32 (4 B) = 12 B memory = 4 B × pixels (heads) + 12 B × fragments (nodes)

    z is the fragment's depth in metres and α its alpha. w is the weight, clamped so it never gets too small or too large. accum holds weighted colour in rgb and total weight in a. reveal is how much of the background still shows through, and C_bg is the opaque colour underneath.

    What this code does: the first shader writes each fragment's weighted colour and its alpha into two targets with two blend modes; the second divides and lays the result over the opaque image.

    // pass 1: every translucent, any order. MRT0 = RGBA16F additive, MRT1 = R16F multiplicative
void psAccumulate(float4 c, float viewZ, out float4 accum, out float reveal) {
  float w = c.a * clamp(0.03 / (1e-5 + pow(viewZ / 200.0, 4.0)), 1e-2, 3e3);
  accum  = float4(c.rgb * c.a, c.a) * w;   // blend ONE, ONE
  reveal = c.a;                             // blend ZERO, ONE_MINUS_SRC_COLOR  →  Π(1 − α)
}
// pass 2: full-screen, over the opaque color
float4 psResolve(float2 uv) {
  float4 a = accumTex.Sample(uv);  float r = revealTex.Sample(uv).r;
  float3 avg = a.rgb / max(a.a, 1e-5);
  return float4(avg * (1.0 - r), r);        // blend ONE, SRC_ALPHA against the opaque buffer
}

    Keep every fragment and you are exact but unbounded; add them up with a weight and you are bounded but approximate. There is no third option that is both.

    Depth writes and the pre-pass trick

    Drag to turn, and toggle what the see-through draws are allowed to do to the depth buffer.

    Translucent draws still test against the depth buffer but must not write to it. If they do, the first see-through fragment at a pixel claims that pixel, and everything behind it is thrown away before it can blend, even a solid object that happens to be drawn later. You see sky through the hole instead of what should be there.

    What you're seeing

    An opaque box, a translucent sphere drawn with both its front and back faces, and a translucent plane cutting through the sphere, rendered into a 320×180 buffer. The readout gives the average error against a correct render, out of 255, and the draw order in use.

    Switch the view to "highlight culled" and every fragment that was thrown away by a depth test it should have passed turns red. The tiles count the opaque pixels lost, the translucent fragments culled, and the pixels where the sphere's back face ended up drawn over its front.

    Try this

    • At the defaults, translucents draw first and write depth. Where the box sits behind the sphere or the plane it has a hole in it, and "opaque pixels lost" is not zero.
    • Untick "translucents write depth". The hole in the box closes, but "back-over-front pixels" jumps up, because the sphere's inside faces blend in whatever order the mesh lists them.
    • Set Sphere to "depth pre-pass + EQUAL". Now only the nearest layer of the sphere blends, and that count drops to zero.

    The real version

    The opaque pass runs with the depth test set to LESS and depth writes on, so the buffer ends up holding the nearest solid surface at every pixel. The translucent pass keeps the LESS test, so glass behind a wall is still hidden, but turns writes off, so one translucent layer never hides another. With writes left on, the first translucent fragment at a pixel claims the depth buffer and anything behind it fails the test and never blends, including an opaque object drawn later. That is the failure to remember when a "transparent" material still has depth write enabled by accident.

    The sphere is one mesh with front and back faces, split into 72 patches drawn in index order. Without writes, both faces blend in whatever order the index buffer gives, so half the patches show the back over the front. The pre-pass trick draws the mesh once depth-only, then again with the test set to EQUAL, so only its nearest layer blends. It trades the inner layers for consistency, which is the right trade for glass, water surfaces and character shields. Objects behind it still get culled by the depth it wrote, which is why it is done per object, not for the whole pass.

    In words: solid things write depth, see-through things only read it; a self-overlapping mesh writes its nearest depth first, then blends only where the depth matches.

    opaque pass: test LESS, write ON translucent pass: test LESS, write OFF, blend pre-pass per mesh: pass 1: test LESS, write ON, color mask 0 pass 2: test EQUAL, write OFF, blend only z == nearest z of that mesh blends

    test is the comparison a fragment's depth must pass against the buffer. write is whether a passing fragment overwrites the stored depth. A colour mask of 0 means the pass touches depth only and leaves the picture alone.

    What this code does: draws sorted translucents with writes off, and for any mesh that overlaps itself, runs the depth-only pass and then the EQUAL pass before restoring the normal state.

    // after all opaques, depth buffer holds their z
setDepth(test = LESS, write = false);  setBlend(premultipliedOver);
for (obj : sortedTranslucents) {
  if (obj.selfOverlapping) {              // glass mesh with inner faces
    setColorMask(0); setDepth(test = LESS, write = true);
    draw(obj);                              // pass 1: nearest z per pixel
    setColorMask(RGBA); setDepth(test = EQUAL, write = false);
    draw(obj);                              // pass 2: exactly one fragment blends
    setDepth(test = LESS, write = false);
  } else draw(obj);
}

    Translucent draws read the depth buffer and never write it, except for the one-mesh pre-pass that writes depth on purpose so only the nearest layer blends.

    One naming trap. "Transparent objects render after opaques" sounds like a position in a queue, but it is a set of GPU states: the translucent pass switches on blending, switches off depth writes, and often changes the depth test. Move a mesh later in the draw list without changing those states and you get an opaque object that happens to draw last. The demo in section 5 is that mistake with the depth write left on.
