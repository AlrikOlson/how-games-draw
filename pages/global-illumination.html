Global Illumination

A lamp lights what it can see. That is direct light, and it is the easy part. Light does not stop at the first thing it hits: it bounces off the floor, the walls and everything else, and that bounce light is why the corner behind a cupboard is not pitch black. Games call it global illumination, and working it out properly takes far longer than one frame. This page plays through five ways games store or fake it, and what each one gets wrong.

Bounce light is what the right picture has and the left one lacks; getting it fast, without grain, is the whole problem.

Under the hood: the math and the code

Both views are path tracers: they follow light paths one random bounce at a time and add up where each path goes. This one starts paths at the lantern, a few hundred per frame, and keeps adding. The picture it settles on is unbiased, meaning that with enough rays it is the exact answer rather than an approximation.

The catch is noise. The readout compares two independent halves of the accumulation, and the gap between them is the grain you can see. A game gets one sample per pixel per frame, so a path tracer in a game needs a denoiser and a history buffer, which is a copy of last frame's result that this frame blends into. Every other method on this page gives up exactness for a picture that is stable on frame one.

In words: the light leaving a point is what the point emits itself, plus every bit of incoming light scaled by how the surface reflects it and by how steeply it arrives. The incoming light is just someone else's outgoing light, which is what makes it a bounce.

L_o(x, ω_o) = L_e(x, ω_o) + ∫_Ω f(x, ω_i, ω_o) · L_i(x, ω_i) · cosθ_i dω_i L_i(x, ω_i) = L_o(hit(x, ω_i), −ω_i) // recursive: the incoming light is someone else's outgoing diffuse: f = ρ / π (3D) f = ρ / 2 (this 2D slice) point light in 2D falls off as 1 / r, not 1 / r²

L_o is light leaving point x in direction ω_o, L_e is what x emits itself, f is the reflectance (the albedo ρ divided by π, or by 2 in this flat slice), and cosθ_i is the tilt of the incoming direction against the surface. In this flat slice a point light fades as 1 / r instead of 1 / r².

What this code does: starts one path at the lantern, and at every hit paints the path into the air, adds what landed on the wall, tints the path by the wall's albedo, and picks a new random direction.

// one light path; the "camera" is every cell the path crosses
vec2 p = lightPos;  vec2 d = uniformCircle(rand());
vec3 throughput = lightPower / float(raysPerFrame);
for (int bounce = 0; bounce < maxBounces; bounce++) {
  Hit h = traceScene(p, d);                 // nearest wall segment
  splatLine(p, h.pos, throughput);          // light density in the air
  addIrradiance(h.seg, h.u, throughput);    // what lands on the wall
  throughput *= albedo(h.seg);              // color bleeding lives here
  d = cosineSample(h.normal, rand());       // pdf = cosθ / 2 in 2D
  p = h.pos + h.normal * 1e-3;
}
// noise estimate: two independent accumulators A and B
noise = sum(|A - B|) / sum(A + B);

Cut the walls into patches, pass light between them a few times, and write the answer onto the walls: free to read, wrong once anything moves.

Under the hood: the math and the code

Radiosity assumes every surface is diffuse, meaning it scatters light evenly in all directions like matte paint. Then the light leaving a patch is one number per colour with no direction attached, and the whole problem turns into a linear system: a big table of numbers you solve pass by pass.

The entry that links patch i to patch j is the form factor F_ij, the fraction of light leaving patch i that lands on patch j. It depends only on geometry, so it is computed once. The direct light from the lantern is computed once too and folded into the emission term, so the solve only carries the bounces.

Each pass is one Jacobi step, meaning every patch gathers from last pass's values at the same time. A handful of passes is enough. The result lives on the surfaces, which is exactly what a lightmap is, and reading it costs one texture fetch. Bake it and the lighting is frozen: move the crates and their shadow stays where the bake left it.

In words: a patch's light is what the lantern puts on it directly, plus its albedo times the light it gathers from every patch it can see.

B_i = E_i + ρ_i · Σ_j F_ij · B_j // one Jacobi pass, all i at once 2D form factor, patch i center to patch j: F_ij ≈ cosθ_i · cosθ_j / (2 · r_ij) · len_j · V_ij // 3D: cosθ_i cosθ_j / (π r²) · A_j Σ_j F_ij ≤ 1 // energy conservation, per row E_i = ρ_i · I · cosθ_i / r_i · V_i // direct light, folded into the emission

B_i is the light leaving patch i, E_i is its direct light, ρ_i is its albedo, F_ij is the form factor from above, and V is 1 when the two can see each other and 0 when something is in the way. The rows of F add up to at most 1, so no pass can invent energy.

What this code does: for every patch, adds up the light from every other patch weighted by the form factor, multiplies by the albedo, and adds the direct light back in. Then copies the result into a strip texture, one texel per step along the wall.

// CPU bake, or a compute pass: B_new[i] for all patches
for (int i = 0; i < N; i++) {
  vec3 gathered = vec3(0.0);
  for (int j = 0; j < N; j++)
    gathered += F[i * N + j] * B_old[j];    // F is N×N, precomputed with visibility
  B_new[i] = E[i] + albedo[i] * gathered;   // each pass adds one more bounce
}
// bake: one texel per (texelSize) along the wall, RGBA8 or RGBM
lightmap[wall][t] = B[patchAt(wall, (t + 0.5) * texelSize)];

Bounce light for things that move

The player walks behind the screen. He was not there when the walls were baked, so he borrows bounce light from probes floating in the air.

How the four probes are blended
Light shown on the player

Probes give moving things bounce light from the air; store a distance per direction too, or the blend hands light through walls.

Under the hood: the math and the code

Each probe shoots rays and keeps the radiance it saw per direction; the 16 bins are the raw data. What ships is usually a projection onto a few basis functions, a handful of smooth curves that together approximate the bins. In this flat slice the equivalent of L1 spherical harmonics (the first, smoothest set of those curves on a sphere) is 3 numbers per colour channel, and the irradiance for any surface direction falls out of a dot product.

The failure is interpolation. Bilinear weighting, the plain blend by distance along each axis, knows nothing about walls. The player behind the screen sits in a cell whose right-hand probes are in the lit half of the hall, so their lit values get blended straight through the screen.

DDGI (dynamic diffuse global illumination) fixes this by storing a depth per bin: how far each probe can see in that direction. When the stored depth says the probe cannot see the shading point, its weight drops to almost nothing.

In words: squash the 16 bins into 3 numbers, read irradiance for a surface direction with one dot product, and weight each probe by distance, by whether it sits in front of the surface, and by whether it can see the point.

2D SH, order 1: a0 = (1/2π) ∫ L dθ a1 = (1/π) ∫ L cosθ dθ b1 = (1/π) ∫ L sinθ dθ E(n) = 2·a0 + (π/2) · (a1·n.x + b1·n.y) // cosine lobe, 3 coefficients w_k = bilinear_k · wrap_k · vis_k wrap_k = ((n · dir_to_probe) + 1)² / 4 // backface term vis_k = |p − probe_k| < depth_k(dir) + bias ? 1 : 0.01 // DDGI uses Chebyshev on (depth, depth²)

a0, a1, b1 are the 3 stored numbers, E(n) is the irradiance for a surface facing direction n, and w_k is probe k's weight: its bilinear share, times a wrap term that fades probes behind the surface, times a visibility term that is 1 if the probe's stored depth reaches the point and 0.01 if not. DDGI uses a Chebyshev test on the stored depth and depth squared instead of a hard cutoff.

What this code does: for each of the 4 probes around the point, works out the three weights, multiplies them together, and adds that probe's irradiance; then divides by the total weight.

// fragment shader: gather indirect irradiance from the 4 (8 in 3D) cell probes
ivec2 base = ivec2(floor(p / spacing));  vec2 f = fract(p / spacing);
vec3 sum = vec3(0.0); float wsum = 0.0;
for (int k = 0; k < 4; k++) {
  ivec2 id = base + ivec2(k & 1, k >> 1);
  vec2 toProbe = probePos(id) - p;  float dist = length(toProbe);
  float w = mix(1.0 - f.x, f.x, k & 1) * mix(1.0 - f.y, f.y, k >> 1);
  w *= pow((dot(n, toProbe / dist) + 1.0) * 0.5, 2.0);          // wrap shading
  float d = texelFetch(probeDepth, binOf(id, -toProbe / dist)).r;
  w *= dist < d + bias ? 1.0 : 0.01;                           // visibility
  sum += w * shEvalIrradiance(probeSH(id), n);  wsum += w;
}
vec3 indirect = albedo * sum / max(wsum, 1e-4);

Screen-space bounce light comes from the frame you already drew: no scene data, everything can move, and anything off screen is gone.

Under the hood: the math and the code

Screen-space GI reads two buffers the frame already produced: the depth buffer and the lit colour buffer. For each bounce ray it steps forward a little, projects the point back onto the screen, and compares the ray's depth with the stored depth at that pixel. If the ray has gone behind the stored surface by less than a thickness margin, that is a hit, and the colour stored there is the bounce light.

That is why it is cheap and fully dynamic, and why it shows up as the lowest tier in most engines and as the first trace in Lumen. The ray only knows what the camera knows. Rays that leave the screen or pass behind a thin object return nothing.

In words: step along the ray, look up the depth at that screen column, and call it a hit if the ray is just behind the stored surface. Average the colours of the hits.

screen-space march: for each step t: q = p + d·t col = project(q).x depth_ray = dot(q − C, forward) hit = depth_ray > zbuf[col] && depth_ray − zbuf[col] < thickness miss = col outside [0, W) || depth_ray − zbuf[col] ≥ thickness bounce(p) = (1/K) Σ_k color[col_k] · (hit_k ? 1 : 0) // cosine-weighted rays, so no cos term

p is the pixel's surface point, d the ray direction, C the camera, zbuf the depth buffer, W the screen width in pixels, and K the number of rays. The rays are already picked in proportion to the cosine, so no extra cosine term appears.

What this code does: for each of K random rays, marches up to 32 steps, stops when it leaves the screen, and adds the colour buffer's value when the ray dips just behind the stored depth.

// SSGI, per pixel, half resolution in practice
vec3 gi = vec3(0.0);
for (int k = 0; k < K; k++) {
  vec3 d = cosineSample(n, hash(pix, k, frame));
  vec3 q = p;
  for (int s = 0; s < 32; s++) {
    q += d * stepLen;                              // world step, then reproject
    vec2 uv = projectToScreen(q);
    if (any(lessThan(uv, vec2(0))) || any(greaterThan(uv, vec2(1)))) break;   // off screen: no data
    float zs = texture(depthBuf, uv).r;
    float zr = viewDepth(q);
    if (zr > zs && zr - zs < thickness) { gi += texture(colorBuf, uv).rgb; break; }
  }
}
gi *= albedo / float(K);   // then temporally accumulate: 1 spp is far too noisy

Cones trade hundreds of rays for a few blurry reads of a coarse grid, and the cache spreads relighting over frames.

Under the hood: the math and the code

A cone trace is a ray march that takes bigger steps as it goes. At distance t the cone is 2·t·tan(θ/2) wide, so the sampler reads the mip level (the downscaled copy of the grid) whose voxel is that size, and the number of steps grows with the logarithm of the distance instead of the distance. Occlusion builds up front to back with the same blend a volume renderer uses, so once the cone is 95 % blocked it stops.

Re-lighting the whole voxel grid every frame is the expensive part. Lumen keeps a surface cache instead: small radiance textures on the surfaces, updated a budgeted number of texels per frame, and each update gathers from last frame's cache. That gives multiple bounces for free and a visible lag when the light moves. SDFGI in Godot 4 and Lumen's software path swap the voxel opacity for a signed distance field, a grid that stores the distance to the nearest surface, and keep the same idea.

In words: step along the cone, pick the mip whose voxel matches the cone's width there, blend in that voxel's colour by how solid it is, and stop when the cone is mostly blocked. Add the cones up, weighted by how well each one faces the surface.

cone step: t += max(voxelSize, 2·t·tan(θ/2)) · 0.5 level = log2(2·t·tan(θ/2) / voxelSize) c_v, α_v = sampleMip(p + d·t, level) color += (1 − α) · c_v · α_v α += (1 − α) · α_v // front-to-back, stop at α > 0.95 E_ind(p, n) ≈ Σ_cones w_c · color_c, w_c ∝ cos(angle to n) surface cache: B_i ← ρ_i · (E_direct,i + gather from B_prev) // K texels per frame, round robin

t is the distance along the cone, θ its opening angle, c_v, α_v the colour and solidity read from the grid, and E_ind the bounce irradiance for a point p facing n. The last line is the cache update: a texel's light is its albedo times its direct light plus what it gathers from last frame's cache.

What this code does: marches one cone, growing the step and the mip level with distance, blending in each sample front to back until the cone is 95 % blocked or runs out of distance.

// one cone: origin p, direction d, aperture theta; voxels hold (rgb, alpha)
vec3 color = vec3(0.0); float alpha = 0.0;
float t = voxelSize;                                       // skip the voxel we stand in
while (alpha < 0.95 && t < maxDist) {
  float diameter = max(voxelSize, 2.0 * t * tan(theta * 0.5));
  float level = log2(diameter / voxelSize);
  vec4 v = textureLod(voxelRadiance, (p + d * t) / gridSize, level);
  color += (1.0 - alpha) * v.rgb * v.a;                    // premultiplied by voxel alpha
  alpha += (1.0 - alpha) * v.a;
  t += diameter * 0.5;
}
// 5 cones per pixel, then albedo * sum(w_c * color_c)

Memory is what decides lightmaps in practice. One 8 m × 8 m wall at 2 cm texels is 160 000 texels, and a level has thousands of surfaces like it. Probe volumes cost little memory and pay for it in artifacts, and that is the trade every runtime method makes.
