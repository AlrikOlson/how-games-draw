Depth Precision

A depth buffer is the GPU's per-pixel record of how far away the nearest surface is, and it decides which object draws in front. It stores a function of 1/z, not the distance itself, so with a 0.1 m near plane 90% of a 24-bit buffer describes the first metre and far objects get scraps. Reverse-Z flips the mapping so far objects land near 0.0, which is where a float32 has its densest values. The part people get wrong: the flip only pays off with a float buffer, and on a 24-bit integer buffer it changes almost nothing.

Where the codes go

A player stands at the start of a night road with lamp posts at 1, 10, 100 and 1000 m. Move the near and far planes and see which stretch of road gets the buffer's 16,777,215 steps.

The depth buffer doesn't store distance. It stores a value that rises fast near the camera and then flattens out, so half of its codes are used up by twice the near distance. Move the near plane in and the first few centimetres eat everything. Every 10× further out gets a tenth as many codes.

The real version

The vertex shader outputs a clip-space z and a w, where w is the view depth: the straight-line distance in front of the camera. The rasterizer divides z by w, and that divide is what bends the curve. What lands in the buffer is a hyperbola in z, steep at the near plane and flat for the rest of the scene. Half of the codes sit below 2n no matter where far is.

The smallest step the buffer can tell apart at distance z is the slope of that curve divided by the code count, and it grows with z². At the 1 m lamp you resolve fractions of a micrometre. At the 1000 m lamp two surfaces must be half a metre apart to get different codes.

In words: stored depth is a 1/z curve, and the step at any distance is that curve's slope there divided by the number of codes.

z_ndc = f·(z − n) / (z·(f − n)) z_ndc ∈ [0,1], 0 at near: D3D, Vulkan, Metal dz_view/dz_ndc = z²·(f − n) / (n·f) metres per unit of stored depth Δz(D24) = z²·(f − n) / (n·f·(2²⁴ − 1)) smallest resolvable step at z

z is the view distance, n and f are the near and far planes, z_ndc is the stored value between 0 and 1, and Δz is the smallest distance difference the buffer can hold at z.

What this code does: builds the clip z and w the way D3D, Vulkan and Metal expect, then counts how many 24-bit codes fall between two distances.

// vertex shader output, D3D / Vulkan / Metal clip convention (0 = near, 1 = far)
float zClip = zView * f / (f - n) - n * f / (f - n);
float wClip = zView;                 // the rasterizer divides: zNdc = zClip / wClip
// after the divide: zNdc = f * (zView - n) / (zView * (f - n))

// 24-bit codes spent between view distances a and b
uint codesBetween(float a, float b) {
  return uint((zNdc(b) - zNdc(a)) * 16777215.0);
}
// zNdc(2n) = f / (2(f - n)) ≈ 0.5: half the codes are gone by twice the near distance

Depth is stored as a 1/z curve, so half the codes are gone by twice the near distance and each decade further out gets a tenth as many.

The near plane sets everything

The same road. The near plane is the white line just in front of the player, the far plane the one past the last lamp. Slide each and watch the step at the 100 m lamp.

If your scene flickers in the distance, the fix is to push the near plane out, not pull the far plane in. Halving the near plane halves your precision everywhere. Multiplying the far plane by 100 costs under 1%. The far slider is close to a placebo.

The real version

The step formula has n in the denominator and f only inside (f − n)/f, which is 0.999 for any far plane worth having. So the near plane controls the answer and the far plane is a rounding error. That is why "push the near plane out" is the first fix for z-fighting and "pull the far plane in" almost never helps.

The practical rule for a 24-bit buffer: to hold a 1 mm step at distance z you need a near plane of about z² / (0.001 · 2²⁴). For 100 m that is 0.6 m, which a first-person camera cannot afford. This is the gap reverse-Z closes in the next section.

In words: the step is distance squared divided by the near plane and the code count; turn it around to get the near plane you need.

Δz ≈ z² / (n · 2²⁴) for f ≫ n n_needed = z² / (Δz_wanted · 2²⁴) near plane that keeps Δz at z

z is the distance you care about, n is the near plane, Δz is the step in metres, and 2²⁴ is the code count of a 24-bit buffer.

What this code does: computes metres per code at a distance, and the near plane you can afford for a wanted step.

// metres of scene per depth code at view distance z, integer buffer
float depthStep(float z, float n, float f, int bits) {
  float dzdn = z * z * (f - n) / (n * f);     // slope of view depth against stored depth
  return dzdn / float((1u << bits) - 1u);
}

// near plane you can afford for a wanted step at distance z
float nearFor(float z, float stepM, int bits) {
  return z * z / (stepM * float((1u << bits) - 1u));   // (f - n)/f dropped: it is ~1
}

Precision scales with 1 over the near plane; the far plane is close to free.

Reverse-Z: flip it, then use floats

The same road stored two ways. Under the road are two depth buffers, standard and reverse; below them, the step size for integer and float buffers.

A float32 packs its values tightest near zero. Standard Z puts almost the whole scene near 1.0, where floats are no denser than a 24-bit integer. Reverse-Z sends far objects toward 0.0, where the float's tightening cancels the curve's flattening. The result is steps that grow with z instead of z².

What you're seeing

Amber is reverse Z, which fades to black down the road, and 0 is where a float32 packs its values tightest. The upper plot draws both as curves; each shaded band is one float32 exponent, and every band holds the same 2²³ codes, so the narrow bands near 0 are where values are dense.

The real version

A float32 spends 8 bits on an exponent and 23 on a mantissa. The exponent picks a power-of-two band; the mantissa picks one of 2²³ evenly spaced values inside it. So every band has the same number of codes, and the bands get narrower toward 0.

Standard Z puts almost the whole scene in [0.5, 1), a single band where the spacing is 2⁻²⁴: no better than a 24-bit integer. Reverse-Z maps the far end of the scene toward 0, so the range 100 m to 1000 m alone gets four bands. The hyperbola's flattening is cancelled by the float's tightening.

On the bottom plot that is the amber sawtooth. The step halves every time the stored value crosses a power of two, and the trend is linear in z instead of quadratic. The two D24 curves lie on top of each other, because flipping 1 − z inside an integer buffer keeps the same code spacing.

In words: swap what near and far map to, then the float's spacing at the stored value times the curve's slope gives the step.

z_rev = n·(f − z) / (z·(f − n)) 1 at near, 0 at far ulp(x) = 2^(⌊log₂ x⌋ − 23) float32 spacing at value x Δz(D32F rev) = ulp(z_rev) · z²·(f − n)/(n·f) ≈ z · 2⁻²³ … z · 2⁻²⁴ reverse projection z row: [ 0 0 n/(n − f) −f·n/(n − f) ] w row unchanged

z_rev is the flipped stored value, ulp(x) is the gap between a float and its neighbour at x, Δz is the step in metres, and the last line is the projection matrix row that produces the flip.

Switching costs three lines. Swap near and far in the projection, test with GREATER instead of LESS, and clear to 0.0 instead of 1.0. Then check everything that assumed "smaller is closer": the sign of depth bias, Hi-Z downsampling (a shrunken copy of the depth buffer used to skip hidden objects, which must now take the max, not the min), soft-particle and SSAO fades, and any shader that turns depth back into metres.

What this code does: builds the swapped projection, optionally drops the far plane, and sets the compare and clear values on each API.

// projection with near and far swapped: z_rev = n·(f − z) / (z·(f − n))
mat4 P = perspectiveZO(fovY, aspect, far, near);   // same helper, last two arguments swapped
// infinite far plane: z_clip = n, w_clip = z_view
P[2][2] = 0.0;  P[3][2] = near;                     // column-major; row-major writes P[2][3]

// D3D12
dss.DepthFunc = D3D12_COMPARISON_FUNC_GREATER;
cmd->ClearDepthStencilView(dsv, D3D12_CLEAR_FLAG_DEPTH, 0.0f, 0, 0, nullptr);
// Vulkan
ds.depthCompareOp = VK_COMPARE_OP_GREATER;
clear.depthStencil = { 0.0f, 0 };
// OpenGL 4.5: without this the [-1,1] to [0,1] remap throws the float precision away
glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE);
glDepthFunc(GL_GREATER);  glClearDepth(0.0);

Reverse-Z works because float spacing tightens toward 0 as fast as the 1/z curve flattens; it needs a float buffer to do anything.

Z-fighting: the flickering poster

A poster is glued to a wall down the street, 1 mm in front of it. Drag the wall away from the player and watch the poster start flickering through the wall.

Z-fighting is two surfaces closer together than one depth step, so they share a code and the pixels flicker between them. Here a poster sits 1 mm in front of a wall. Move the wall away and the fight starts where the step size reaches 1 mm. Depth bias is the usual patch: nudge the poster toward the camera before the test.

What you're seeing

The red dashed line marks the distance where the fight begins.

Green means the poster won the pixel. Red means both surfaces got the same code and the wall kept it, so the wall shows through.

The real version

Both surfaces are rasterized, projected and quantized per pixel exactly as the buffer would store them. The wall is drawn first, the poster (a decal) second with the same test. Green pixels are where the decal's code is strictly closer; red pixels are where the two codes are equal and the wall keeps the pixel. The stripes are the two 1/z curves crossing code boundaries at slightly different places.

Depth bias moves the decal before the test. The constant part is in units of the smallest step r. The slope part scales with how fast depth changes across one pixel, which is what a grazing angle does to the gap. Under reverse-Z "toward the camera" is +z, so both factors change sign, which is the most common bug when a renderer switches.

In words: the bias is a slope term for tilted triangles plus a constant term counted in depth steps.

bias = m · slopeFactor + r · constantFactor m = max(|∂z_ndc/∂x|, |∂z_ndc/∂y|) per pixel, from the triangle's plane r = 2⁻²⁴ (D24) or ulp(max z of the triangle) (D32F)

m is the biggest change in stored depth across one pixel, r is one depth step in the current format, and the two factors are the numbers you set in the rasterizer state.

What this code does: sets the two bias factors in D3D12, then shows the no-bias alternative where ties go to the decal.

// D3D12 rasterizer state (Vulkan: depthBiasConstantFactor, depthBiasSlopeFactor, depthBiasClamp)
rs.DepthBias            = 2;      // × r: 2^-24 for D24, ulp(largest z in the triangle) for D32F
rs.SlopeScaledDepthBias = 1.5;    // × m = max(|dz/dx|, |dz/dy|) in ndc units per pixel
rs.DepthBiasClamp       = 0.0;
// bias = m * SlopeScaledDepthBias + r * DepthBias, added to z before the test
// reverse-Z: negate both factors, or the decal moves away from the camera

// decals with no bias at all: same vertex math as the wall, then
dss.DepthFunc = D3D12_COMPARISON_FUNC_GREATER_EQUAL;   // ties go to the later draw

The fight starts where the step size reaches the gap; bias buys some distance, and a float reverse-Z buffer buys far more.

Reading the buffer back

Hover over a pixel of the road's depth buffer, as the player sees it, and turn its stored value back into metres, with the right formula and the wrong one.

Effects like ambient occlusion, fog and reflections need to turn a stored depth back into a real distance. That only works if you use the same convention the buffer was written with. Mix them up and the result looks almost right, with near and far swapped. The error tile shows the buffer's precision at the pixel under your cursor, measured directly.

The real version

The image brightens the raw value with a 0.25 power. Under reverse-Z the region between two contours has 2²³ codes to itself. Under standard Z there is one contour, hugging the near plane, and the whole scene shares a single band.

Linearizing means undoing the 1/z curve to get view depth in metres, and it needs the same convention the buffer was written with. The bottom plot shows what happens otherwise: the reverse formula applied to standard data, or the other way round, maps near to far and far to near through a curve that looks plausible for one frame. The reconstruction error tile is the true view depth minus the linearized one, which is the buffer's precision at that pixel measured directly.

In words: each convention has its own formula for turning a stored value back into metres, and with an infinite far plane the reverse one collapses to n divided by the stored value.

standard: z = n·f / (f − d·(f − n)) reverse: z = n·f / (n + d·(f − n)) reverse, f = ∞: d = n / z so z = n / d infinite far, reverse: z_clip = n, w_clip = z_view infinite far, standard: z_clip = z_view − n, w_clip = z_view

d is the stored value between 0 and 1, z is the view depth in metres, n and f are the near and far planes, and z_clip and w_clip are what the vertex shader outputs before the divide.

What this code does: three one-line linearize functions, one per convention, and a helper that rebuilds a full view-space position from a pixel and its depth.

float linearStd(float d, float n, float f) { return n * f / (f - d * (f - n)); }  // d in [0,1], 0 = near
float linearRev(float d, float n, float f) { return n * f / (n + d * (f - n)); }
float linearRevInf(float d, float n)      { return n / d; }
// OpenGL default [-1,1] range instead: z = 2nf / (f + n - d*(f - n))

vec3 viewPos(vec2 uv, float d, mat4 invProj) {
  vec4 ndc = vec4(uv * 2.0 - 1.0, d, 1.0);   // raw buffer value, no remap on [0,1] APIs; flip uv.y for D3D
  vec4 v = invProj * ndc;
  return v.xyz / v.w;                          // the divide undoes the perspective
}

Linearize with the formula that matches how the buffer was written, or you get a plausible picture with near and far swapped.

Logarithmic depth writes log2(1 + w) / log2(1 + f), which gives a constant relative error the way reverse-Z float does. The catch is where it is written. A depth written in the fragment shader cannot be tested before shading, so those draws lose the early-Z and hierarchical-Z rejection that saves most of a frame's overdraw.

The trap: reverse-Z only pays off with a floating-point buffer. On a 24-bit integer format, 1 − z quantized to 2²⁴ codes has exactly the same spacing as z, so flipping the compare op and clear value while keeping D24S8 changes almost nothing. Change the format to D32F first; the flipped test is what makes that format useful.
