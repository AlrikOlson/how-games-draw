Ambient Occlusion

Ambient occlusion darkens corners, creases and the ground under things, so objects look like they sit in the world instead of floating on it. It costs about a millisecond a frame and makes almost every scene read better, which is why nearly every game runs it. The thing people get wrong is what it should darken: only the soft light that comes from everywhere at once, never the direct light from the sun or a lamp. A sunlit corner already has real shadows and should not be darkened a second time.

The true answer: 64 rays per point

A player stands in a cellar with crates, a barrel and stone steps. Drag the white point along the floor, the crates or the steps and watch which of its 64 rays get out.

Ambient occlusion asks one thing at every point on every surface: how much sky can you see from here. On top of the crate you see most of it; on the floor between the barrel and the crate, almost none. The way to find out is to fire rays in every upward direction and count how many get away. That count, as a fraction, is the AO value. This is slow, which is why the rest of the page is about faking it, but it is what every faster method is trying to match.

What you're seeing

A cross-section of a 10 m cellar: the player at the left, a big crate, a barrel, a small crate, and two stone steps up to the right. The engine's camera on this page looks straight down from above. From the white point, 64 rays fan out in a half circle. Blue rays escape past the dashed radius. Amber rays hit something first, with a dot where they stopped.

Every surface carries a grey band painted by the same test: bright means open sky, dark means buried. The darkest stretches are the floor between the player and the crate, and the gap between the barrel and the small crate.

The real version

The reference is a Monte Carlo estimate, which means it approximates an integral with random samples. From point p, shoot rays across the hemisphere, the half-dome of directions above the surface, and count the ones that travel the full distance r without hitting anything.

The rays are not spread evenly. They are cosine-weighted: dense near the normal, the direction the surface faces, and sparse near the horizon. A ray that skims the surface would bring in little light anyway, so it gets fewer samples. With this spread the estimate is the plain average of hit or miss, with no extra weights.

The radius r is a design choice, not physics. A small r gives tight contact shadows where the crate meets the floor; a large one darkens the whole cellar. Every method on this page uses the same r, and the 64-ray reference is what they all try to match for a fraction of the work.

In words: average, over all upward directions with straight up counting most, whether a ray gets out.

AO(p) = (1/π) ∫_Ω V(p,ω) (n·ω) dω V = 1 if the ray escapes within r cosine pdf (n·ω)/π ⇒ AO ≈ (1/N) Σ V(p, ω_i) 2D slice: AO = ½ ∫ V(φ) cos φ dφ, φ ∈ (−π/2, π/2) φ_i = asin(2u_i − 1)

p is the surface point, n its normal, ω a direction and Ω the hemisphere. V is 1 when the ray escapes and 0 when it hits. In the 2D slice on this page, φ is the angle from the normal and u_i is a random number between 0 and 1 turned into a cosine-weighted angle.

What this code does: fires 64 rays with the cosine spread and returns the fraction that got out.

// reference AO: cosine-weighted rays from p, hemisphere around n
float vis = 0.0;
for (int i = 0; i < 64; i++) {
  vec3 w = cosineSampleHemisphere(n, halton(i));  // pdf = (n·w)/π, so no weight needed
  vis += traceRay(p + n * EPS, w, r) ? 0.0 : 1.0;  // any hit inside r counts as blocked
}
float ao = vis / 64.0;                            // 1 = open sky, 0 = buried

AO is the fraction of the sky a point can see, and 64 rays per point is the answer everything else on this page is chasing.

SSAO: guessing from the depth buffer

The engine takes one depth photo of the cellar from above, the strip at the top. Move the point and watch each test sample get checked against that photo instead of the real crates.

Firing real rays is too slow for a game, so SSAO cheats with the depth buffer, the image the GPU already has that stores how far away each pixel's surface is. Around each pixel it sprinkles a handful of test points in a half-dome and asks, for each one, whether there is a surface in front of it. If the depth buffer says yes, that point counts as blocked. No rays, no crates, one lookup per point.

What you're seeing

The strip along the top is the depth buffer, the camera's photo of the cellar from above: 320 cells, each 3.1 cm wide, brighter where the surface is closer to the camera. The player's head and the crate tops are bright, the floor is dark. Around the white point, each test sample is a dot. Blue dots sit in open air. Amber dots are under the stored surface, with a line up to the cell that said so. Hollow dots were under the surface but too far from the point in depth, so the range check threw them out.

The band along every surface is shaded by the same test, and the readout puts the result next to the 64-ray reference.

The real version

This is Crytek's 2007 method. Take the pixel's position in view space, which means measured from the camera, scatter N points around it, and project each one back onto the screen. Read the depth stored at that screen position. If the stored surface is closer to the camera than the sample, the sample is inside something, so it counts as occluded.

The original kernel, the cloud of sample offsets, was a full sphere. On flat ground half of it is below the floor, so an open surface reads 0.5 instead of 1. A hemisphere kernel turned to face along the normal fixes that.

Two guards make it usable. A bias, a small offset added to each sample's depth, stops a surface from occluding itself because stored depth comes in steps. A range check drops samples whose stored depth is far from the pixel's own depth. Without it, a tree behind a character darkens the character.

In words: a sample is blocked if the depth buffer holds something in front of it, and it only counts if that something is close to the pixel.

occ_i = [ z_buf(proj(s_i)) ≥ z(s_i) + bias ] stored surface is closer than the sample w_i = smoothstep(0, 1, r / |z(p) − z_buf(s_i)|) AO = 1 − (1/N) Σ occ_i · w_i sphere kernel on flat ground: half the samples are underground ⇒ AO ≈ 0.5

s_i is the i-th sample point, proj puts it on the screen, z_buf reads the stored depth there and z(s_i) is the sample's own depth. w_i is the range weight, which fades to 0 as the stored surface gets far from the pixel.

What this code does: places N points in a half-dome around the pixel, looks each one up in the depth buffer, and averages how many were buried.

// SSAO, view space; one depth fetch per kernel sample
vec3 p = viewPos(uv), n = viewNormal(uv);
mat3 tbn = kernelBasis(n, noiseTex[ivec2(gl_FragCoord.xy) & 3]);  // 4×4 random rotation
float occ = 0.0;
for (int i = 0; i < N; i++) {
  vec3 s = p + tbn * kernel[i] * radius;        // kernel[i]: unit hemisphere, |k| = sqrt(u)
  vec4 clip = proj * vec4(s, 1.0);
  vec2 suv = clip.xy / clip.w * 0.5 + 0.5;       // where the sample lands on screen
  float sceneZ = viewPos(suv).z;                 // what is stored there
  float rangeW = smoothstep(0.0, 1.0, radius / abs(p.z - sceneZ));
  occ += (sceneZ >= s.z + bias ? 1.0 : 0.0) * rangeW;
}
float ao = 1.0 - occ / float(N);

SSAO never touches the scene; it only asks the depth buffer whether each nearby test point is inside something.

Horizons: walk out, keep the steepest angle

Same cellar, same depth photo. Move the point and watch the march to the left and to the right find how high the crates, the barrel and the player rise above it.

Instead of random test points, HBAO and GTAO walk away from the pixel in a few screen directions and, at each step, note how steeply the surface there rises above the point. The steepest angle found is the horizon in that direction, like the skyline you see from a street. Everything below the horizon is blocked, everything above is open. Two angles replace dozens of yes-or-no tests, and the result is much less noisy for the same cost.

What you're seeing

The white lines run to the sample that set each horizon, the top of the crate or the player's head, and the amber wedges under them are the blocked part of the half circle. The blue wedge between them is the open part.

The real version

Walk away from the pixel in a screen direction, read the depth at each step, and keep the steepest elevation angle seen so far. That angle is the horizon in that direction. Everything under it is blocked and everything above is open. Two numbers per direction replace N independent hit tests, and the estimate changes smoothly as the horizon moves, so it is far less noisy for the same number of depth fetches.

HBAO (NVIDIA, 2008) integrates the horizon evenly over the view hemisphere and fades blockers by distance. GTAO (Activision, 2016) integrates the cosine-weighted hemisphere around the normal in closed form per slice, a slice being one screen direction and its opposite. That matches the reference definition. In 3D the slice result is averaged over directions φ; with one slice here it is divided by its open-sky value. Samples beyond r are ignored in both.

In words: HBAO scores each direction by how high its horizon is; GTAO takes two horizons per slice and solves the cosine-weighted integral between them exactly.

HBAO h(φ) = max_k atan(Δz_k / Δxy_k) t(φ) = tangent angle in slice φ AO = 1 − (1/N) Σ_φ (sin h − sin t) W(r_k) GTAO h1, h2 = horizons from the view vector, clamped to n ± π/2 V̂ = ¼(−cos(2h1−n) + cos n + 2h1 sin n) + ¼(−cos(2h2−n) + cos n + 2h2 sin n) AO = (1/π) ∫_φ |n_proj(φ)| V̂(φ) dφ

h is the horizon angle in direction φ, t the angle of the surface's own tangent plane, and W the distance falloff. In GTAO, h1 and h2 are the two horizons of a slice measured from the view direction, n is the normal's angle in that slice, and V̂ is the visible fraction the closed-form integral gives.

What this code does: steps outward from the pixel, tracks the highest elevation it has seen, and returns it as a sine so the two directions can be averaged.

// horizon march in one screen direction; call once per direction (2 here, 4–8 in 3D)
float horizonSin(vec2 uv, vec2 dir, vec3 p, vec3 n) {
  float maxSin = 0.0;                            // start flat, at the tangent plane
  for (int k = 1; k <= STEPS; k++) {
    vec2 suv = uv + dir * (float(k) - 0.5 + jitter) * stepPx;   // jitter per pixel from the noise tile
    vec3 s = viewPos(suv) - p;
    float d = length(s);
    if (d > radius) break;
    float el = dot(s, n) / d;                    // sin of elevation above the tangent plane
    float falloff = 1.0 - d * d / (radius * radius);
    maxSin = max(maxSin, el * falloff);
  }
  return maxSin;
}
float ao = 1.0 - 0.5 * (horizonSin(uv, +dx, p, n) + horizonSin(uv, -dx, p, n));

A horizon march finds the skyline in each direction, and everything below the skyline is blocked.

Noise, blur, history

The cellar floor seen from above, as the AO image the engine computes. Drag the crate around the floor and watch the four stages that turn a noisy AO image into a clean one; the inset shows the finished picture the player gets.

Twelve test points per pixel is nowhere near enough, so the raw AO image is speckled with noise. The trick is to make the noise a repeating 4×4 pattern and then blur it away in a way that stops at the edges of the crate. Then the game keeps a running average across frames, so each pixel ends up drawing on hundreds of tests it never ran.

What you're seeing

A 160×90 depth render of a 16 m × 9 m cellar floor seen from above: a crate you can drag, a barrel, a drain channel across the floor and a raised ledge on the right. Panel 1 is the raw SSAO with 12 samples per pixel. Panel 2 is a plain 4×4 blur that ignores depth and smears a halo around the crate. Panel 3 is a blur that checks depth and stops at the crate's edge. Panel 4 adds the previous frames on top, and its inset multiplies that result over the coloured floor, which is what the player sees.

The readout counts the depth fetches for the whole image and how long the JavaScript took.

The real version

Each pixel of a 4×4 tile rotates the sample kernel differently, so a 4×4 blur sees all 16 rotations, which is 192 effective samples. A blur that ignores depth smears the dark floor onto the crate top and lightens the floor next to it: the halo in panel 2. The bilateral blur, a blur that weights each neighbour by how close its depth is, stops at the edge, panel 3.

Temporal accumulation blends in the previous frames, with a new noise phase every frame, panel 4. In a real engine the history has to be reprojected with motion vectors, the per-pixel record of where each point was last frame. Here the camera is fixed, so the only rejection needed is a depth mismatch.

In words: weight each neighbour by how similar its depth is, average, then blend a tenth of the new result into last frame's running total unless the depth changed.

w_ij = exp(−Δz² / σ_z²), Δz = z_j − z_i blurred = Σ w_ij ao_j / Σ w_ij history = |z_prev(uv') − z(uv)| > τ ? blurred : hist(uv') uv' = uv − motion vector result = (1 − α) history + α blurred α = 0.1 ⇒ ~10 frames, ~1900 effective samples

w_ij is the weight of neighbour j for pixel i, σ_z sets how big a depth difference counts as an edge, τ is the mismatch that throws history away, and α is how much of the new frame goes into the running average. At α = 0.1 about 10 frames are blended, so roughly 1900 effective samples.

What this code does: blurs 4×4 with depth-aware weights, then reads last frame's value at the reprojected position and blends it in unless that pixel used to be a different surface.

// 4×4 bilateral blur; the footprint matches the 4×4 noise tile on purpose
float z0 = depth(uv), sum = 0.0, wsum = 0.0;
for (int j = -2; j < 2; j++)
for (int i = -2; i < 2; i++) {
  vec2 o = uv + vec2(i, j) * texel;
  float dz = depth(o) - z0;
  float w = exp(-dz * dz / (sigmaZ * sigmaZ));   // ~1 on the same surface, ~0 across an edge
  sum += ao(o) * w; wsum += w;
}
float blurred = sum / wsum;

// temporal: reproject, then reject a history sample that belonged to another surface
vec2 uvPrev = uv - motionVector(uv);
float h = abs(depthPrev(uvPrev) - z0) > 0.1 ? blurred : history(uvPrev);
aoOut = mix(h, blurred, alpha);

Make the noise a known pattern, blur it away without crossing edges, then average across frames and you get hundreds of samples for the price of twelve.

What the depth buffer cannot see

The cellar again, now with a shelf over the ledge and the cellar wall just past the right edge of the screen. Drag the point onto the floor beside the shelf, then onto the top step beside the wall, and compare the three methods.

The depth buffer only knows about the nearest surface in each pixel, and nothing outside the frame. So SSAO thinks everything under the shelf is solid and the cellar wall just off screen does not exist. Both mistakes shift as the camera turns, which is the crawling AO players notice. The only fix is to ask the scene itself, with a distance field or real rays, and that costs more.

The real version

The depth buffer stores one surface per texel, the nearest. Everything behind it is assumed solid and everything outside the frame does not exist. Under the shelf, SSAO's samples land inside a volume the buffer thinks is filled, so the floor beside the shelf's edge is darkened as if it stood against a wall. At the right end of the top step the real wall is one texel outside the frame, so SSAO sees nothing and the step stays bright. Both errors change as the camera pans, which is the view dependence that players notice as AO "crawling".

Distance-field AO (Unreal, 2014) cone-traces a signed distance field of the whole scene, on screen or not. A signed distance field is a 3D grid that stores, at every point, how far it is to the nearest surface. Along each cone the ratio of that distance to the cone's width says how much of the cone is still clear. Ray-traced AO is the reference itself with hardware rays, usually one ray per pixel and a denoiser. Both cost more per pixel; only they get these cases right.

In words: SSAO fails wherever the sample is in air but the buffer says solid, or off screen; DFAO takes the worst clearance along each cone; RTAO is the reference with fewer rays.

SSAO fails if z_buf(proj(s)) ≥ z(s) but s is in air (under the shelf), or proj(s) is off screen DFAO vis_c = min_t sat(d(p + ω_c t) / (t tan θ)) AO = Σ_c w_c vis_c / Σ_c w_c, w_c = n·ω_c RTAO AO = (1/N) Σ V(p, ω_i), N = 1 + denoiser

d is the distance-field lookup, ω_c the direction of cone c, θ its half angle, t the distance along it, and sat clamps to 0 to 1. w_c weights each cone by how close it is to the normal.

What this code does: for each cone, steps along it using the distance field, keeps the smallest clearance-to-width ratio it sees, then averages the cones weighted toward the normal.

// DFAO: cone trace the global distance field, several cones over the hemisphere
float coneAO(vec3 p, vec3 n, float r) {
  float sum = 0.0, wsum = 0.0;
  for (int c = 0; c < NUM_CONES; c++) {
    vec3 dir = coneDir[c]; float w = dot(dir, n);
    float vis = 1.0, t = 0.05;
    for (int s = 0; s < 24 && t < r; s++) {
      float d = sampleSDF(p + n * 0.02 + dir * t);
      vis = min(vis, saturate(d / (t * tanHalfAngle)));  // fraction of the cone still clear
      t += max(d, minStep);                              // step by the distance to the nearest surface
    }
    sum += vis * w; wsum += w;
  }
  return sum / wsum;
}

Screen-space AO can only be as right as the depth buffer, and the depth buffer knows nothing about what is hidden or off screen.

Every row estimates the same integral. What differs is what the query reads: the depth buffer, a distance field, or the geometry.

The trap is what AO gets applied to. It only approximates how much ambient light a point misses, and direct light already has its own shadows, so a crease facing the sun should be as bright as the sun makes it. Many games still multiply AO over the whole lit image because it looks "grounded", which darkens sunlit corners twice; the right place for it is the indirect light, and in a GTAO pipeline also the specular occlusion derived from it.
