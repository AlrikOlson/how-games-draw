Anti-Aliasing

Your screen is a grid of small squares, and a game picks each square's colour by checking one point inside it. That is why slanted edges come out as staircases and fine patterns shimmer. Anti-aliasing is the family of fixes, and each one pays in its own way: MSAA with memory, FXAA with blur, TAA with ghost trails. The thing people get wrong: MSAA does not fix every jaggy. It only smooths the edges of triangles. Shimmer inside a surface, like a far-off picket fence, needs the shader, the program that picks each pixel's colour, to run more than once per pixel, or a fix that works over time.

Several test points per pixel, one shader run, then an average: edges smooth out for far less than the cost of the extra points.

Under the hood: the math and the code

The rasterizer, the GPU stage that decides which pixels a triangle touches, tests coverage at points, not areas. With one sample per pixel that point is the pixel center. An edge either covers it or does not, so the edge renders as a staircase of whole pixels.

Multisampling adds more test points per pixel and stores a colour and a depth for each one. The resolve, the step that averages a pixel's samples into one colour, turns 3 of 4 covered into 3/4 roof colour.

What runs once and what runs N times is the whole trick. Coverage and the depth test run per sample. The fragment shader, the program that computes the colour, runs once per pixel per triangle at the pixel center, and its one result is copied into every covered sample.

Shading is usually the expensive part, so MSAA 4× costs far less than four 1× frames. Supersampling (SSAA) is the same machinery with the shader forced to run at every sample.

The sample positions are not a square grid. Direct3D's standard 4× and 8× patterns are rotated grids, so a near-horizontal or near-vertical edge crosses the samples at different heights. A 2×2 grid gives a horizontal edge only three coverage levels; the rotated 4× pattern gives five.

In words: a pixel's coverage is the share of its test points inside the triangle, and its final colour is the average of its stored samples. The last two lines are the Direct3D sample offsets, in sixteenths of a pixel.

coverage(p) = (1/N) · Σ_i inside(tri, c_p + o_i) o_i in 1/16 px resolve(p) = (1/N) · Σ_i color_i(p) color_i = shade(c_p) if covered, else clear D3D 2×: (4,4) (−4,−4) 4×: (−2,−6) (6,−2) (−6,2) (2,6) D3D 8×: (1,−3) (−1,3) (5,1) (−3,−5) (−5,5) (−7,−1) (3,7) (7,−7)

p is the pixel, c_p its center, o_i the offset of sample i, and N the number of samples. inside() is 1 when the point lands in the triangle and 0 otherwise.

What this code does: gets one bit per sample from the rasterizer, runs the shader once if any bit is set, copies that colour into every covered sample, then averages the samples at the end.

// rasterizer side: N coverage bits per pixel, one shader invocation per covered pixel
uint mask = coverageMask(tri, p);              // bit i set if sample i is inside
if (mask != 0u) {
  vec4 c = fragShader(centerOf(p));           // once, at the pixel center
  for (int i = 0; i < N; i++)
    if ((mask >> i) & 1u) msaaColor[p][i] = c;  // same color into every covered sample
}
// resolve pass: one texelFetch per sample, averaged, once at the end of the pass
vec4 resolve(ivec2 p) {
  vec4 sum = vec4(0.0);
  for (int i = 0; i < N; i++) sum += texelFetch(msaaColor, p, i);
  return sum / float(N);
}

Under the hood: the math and the code

Geometric aliasing lives on triangle edges. The rope drops out wherever its 0.6 px width misses the pixel center, and the roof's slanted edge is a staircase.

Shading aliasing lives inside triangles. The fence's pickets shrink toward the horizon until a picket and its gap are smaller than a pixel, and the shader, run at one point, returns whichever of the two happens to sit under that point. The result is the moiré band across the far fence.

With MSAA 4× the rope and the roof edge get coverage-blended, because coverage is tested per sample. The moiré does not move: the shader still ran once per pixel at the center, and all four samples inside the fence quad received that one colour. SSAA 4× runs the shader at each sample, and the moiré softens at four times the shading cost.

Anything a shader computes can alias this way: specular highlights on normal-mapped surfaces, procedural patterns, foliage and fences drawn with a cut-out mask (alpha test), shadow-map edges. Textures escape only because mipmapping, which keeps pre-shrunk copies of every texture, has already averaged them down to the pixel's size.

This is the case MSAA cannot help with. It is the main reason deferred renderers, which draw all the geometry first and light it afterwards, and physically based renderers moved to temporal methods.

In words: at one sample per pixel, any pattern that repeats faster than every 2 pixels cannot be drawn correctly and shows up as a slower, false pattern instead. The last two lines are the only difference between MSAA and SSAA: where shade() is called.

sampling rate f_s = 1 sample / px detail with period P < 2 px cannot be represented a checker of period P aliases to a period of 1 / |1/P − round(1/P)| px (moiré) MSAA: color(p, i) = covered_i ? shade(c_p) : clear // one shade() per pixel per triangle SSAA: color(p, i) = covered_i ? shade(c_p + o_i) : clear // N shade() per pixel

f_s is the sampling rate, P the pattern's repeat length in pixels (here one picket plus one gap; the formula is written for a checker but holds for any repeating pattern), c_p the pixel center, o_i the offset of sample i, and covered_i whether sample i is inside the triangle.

What this code does: shows the two shader keywords that change where shading happens. centroid moves the interpolation point inside the covered samples; reading the sample index forces the shader to run once per sample.

// MSAA interpolates attributes at the pixel center even when the center is outside the triangle.
// 'centroid' snaps the interpolation point inside the covered samples, fixing edge sparkle only.
centroid in vec2 uv;                           // HLSL: centroid float2 uv : TEXCOORD0

// Forcing per-sample shading turns MSAA into SSAA for this draw:
// GL:  glEnable(GL_SAMPLE_SHADING); glMinSampleShading(1.0);
// D3D: read SV_SampleIndex in the pixel shader
in int gl_SampleID;                             // reading this alone forces one invocation per sample
vec3 c = shadeFloor(uv);                        // now evaluated at sample i, not at the center

FXAA is a cheap blur that fires only on sharp edges; it fixes the jaggies it can see and nothing that was never drawn.

Under the hood: the math and the code

FXAA (Lottes, NVIDIA, 2009) never sees a triangle. It reads the finished frame and converts each pixel to luma, its brightness as a weighted mix of red, green and blue. It flags a pixel as an edge when its contrast to the four neighbors exceeds a threshold that scales with local brightness. Most pixels fail that test and exit in a few instructions.

For each edge pixel it decides whether the edge runs horizontally or vertically from a 3×3 second-derivative estimate, a measure of how sharply brightness bends across the block. It picks the steeper side, then walks along the edge in both directions until the luma changes, to find the edge's ends.

The distance to the nearer end sets how far to shift the texture fetch across the edge. The bilinear filter, the GPU's built-in blend between neighbouring pixels, does the mixing.

It is one full-screen pass, well under a millisecond at 1080p on any GPU from the last decade, and it works on any image, including deferred output where MSAA is expensive. The cost is that it cannot tell an aliased edge from wanted detail. Lower the threshold and the HUD text softens.

The 0.5 px rope is worse. Where the rasterizer dropped it, the frame contains no information to recover, so FXAA blurs the fragments that survived and leaves the gaps.

SMAA (Jimenez et al., 2012) keeps the luma edge detection but replaces the blend. It classifies the edge shape (L, U and Z patterns) with a precomputed area table and computes the exact coverage that shape would have had, which keeps far more sharpness. It costs three passes and two small render targets, the images a GPU draws into, instead of one pass.

In words: measure brightness, compare a pixel to its four neighbours, call it an edge if the difference is big enough, decide which way the edge runs, then shift the read across the edge by an amount set by how close the edge's end is.

luma = dot(rgb, (0.299, 0.587, 0.114)) range = max(l_M, l_N, l_S, l_E, l_W) − min(l_M, l_N, l_S, l_E, l_W) edge = range ≥ max(0.0312, thr · max) thr = 0.166 default, 0.125 high quality horizontal edge if |l_NW − 2l_W + l_SW| + 2|l_N − 2l_M + l_S| + |l_NE − 2l_E + l_SE| ≥ |l_NW − 2l_N + l_NE| + 2|l_W − 2l_M + l_E| + |l_SW − 2l_S + l_SE| offset = 0.5 − d_near / (d_near + d_far) px, across the edge toward the steeper side

l_M is the luma of the pixel itself; N, S, E, W and the corner letters are its neighbours. thr is the edge threshold slider. d_near and d_far are the distances to the two ends of the edge.

What this code does: computes the five lumas, returns the pixel untouched if the contrast is low, works out the edge direction from second derivatives, then reads the image slightly across the edge so the hardware blend does the smoothing.

// FXAA edge test, per pixel, on the tone-mapped image
float lM = luma(tex(uv)), lN = luma(tex(uv + vec2( 0,-1) * px));
float lS = luma(tex(uv + vec2( 0, 1) * px)), lE = luma(tex(uv + vec2( 1, 0) * px));
float lW = luma(tex(uv + vec2(-1, 0) * px));
float lMax = max(lM, max(max(lN, lS), max(lE, lW)));
float lMin = min(lM, min(min(lN, lS), min(lE, lW)));
if (lMax - lMin < max(EDGE_THRESHOLD_MIN, lMax * EDGE_THRESHOLD))
  return tex(uv);                             // early out: most of the frame
// orientation from second derivatives over the 3x3 block
float edgeH = abs(lNW - 2.0*lW + lSW) + 2.0*abs(lN - 2.0*lM + lS) + abs(lNE - 2.0*lE + lSE);
float edgeV = abs(lNW - 2.0*lN + lNE) + 2.0*abs(lW - 2.0*lM + lE) + abs(lSW - 2.0*lS + lSE);
bool horizontal = edgeH >= edgeV;
// ... pick the steeper side, walk along the edge to both ends, compute offset ...
vec2 n = horizontal ? vec2(0.0, side) : vec2(side, 0.0);
return tex(uv + n * offset * px);              // bilinear filtering is the blend

TAA gets many test points per pixel for the price of one by blending frames; motion arrows and the correction stop old frames from ghosting.

Under the hood: the math and the code

Each frame the projection matrix is offset by a sub-pixel jitter, so the one sample per pixel lands somewhere new. The offsets come from the Halton(2,3) sequence, a fixed list of points that fills the pixel evenly no matter how many of them you have used so far.

The frame is blended into a history buffer, last frame's finished picture, with weight α. After eight frames the history holds a weighted average of eight sample positions: close to 8× supersampling for the price of 1×, plus one full-screen resolve.

The catch is that the history was rendered from the previous camera with the previous object positions. Reprojection handles anything that moved coherently: each pixel writes a motion vector, and the resolve reads history at uv − motion instead of uv. The player's leading edge stops smearing, because the pixels they newly cover now fetch history from where the player was.

What reprojection cannot fix is disocclusion, the grass and fence that were hidden behind the player a frame ago. That history is wrong, and blending it in leaves the trail.

Neighborhood clamping is the fix nearly every shipped TAA uses. Take the 3×3 block of pixels around the current one, find the range of colours in it, and clamp the history sample into that range before blending. History that could not plausibly have produced the current pixel's surroundings gets pulled to the nearest plausible colour.

YCoCg is a colour space that separates brightness from tint. Clamping in it makes the box tighter along the brightness axis, where ghosts are most visible, at the cost of some flicker on high-contrast detail.

In words: pick this frame's jitter from the Halton list, read the history where this surface was last frame, clamp it to the range of colours around the current pixel, then mix a little of the new frame into it.

halton(i, b): f = 1, r = 0; while i > 0: f /= b; r += f · (i mod b); i = ⌊i / b⌋ jitter_n = ( halton(n, 2) − 0.5, halton(n, 3) − 0.5 ) px, n = 1..8, then repeat uv_prev = uv − motion(uv) motion = uv_now − uv_prev of the surface box = [min, max] of current over the 3×3 neighborhood, in RGB or YCoCg c_hist' = clamp(history(uv_prev), box.min, box.max) c_out = lerp(c_hist', c_curr, α) frame k ago weighs α(1−α)^k effective samples ≈ (2 − α) / α α = 0.1 → 19

halton(i, b) is the i-th point of the sequence in base b, and n is the frame number. motion(uv) is the motion vector at that pixel. α is the blend slider: the share of the new frame in the output, which is why a smaller α means more effective samples.

What this code does: reads the motion vector, fetches history from where the pixel came from, builds the 3×3 colour box in YCoCg, clamps the history into it, and blends. History from off screen is thrown away.

// TAA resolve, one pass. Output becomes next frame's history.
vec2 mv   = texture(motionTex, uv).xy;              // written by the geometry pass, unjittered
vec3 cur  = texture(colorTex, uv).rgb;
vec3 hist = texture(historyTex, uv - mv).rgb;       // reprojection: read where this surface was
vec3 mn = vec3(1e9), mx = vec3(-1e9);
for (int j = -1; j <= 1; j++) for (int i = -1; i <= 1; i++) {
  vec3 c = rgb2ycocg(texelFetchOffset(colorTex, ivec2(gl_FragCoord.xy), 0, ivec2(i, j)).rgb);
  mn = min(mn, c); mx = max(mx, c);
}
hist = ycocg2rgb(clamp(rgb2ycocg(hist), mn, mx));   // reject what the neighborhood cannot explain
float a = alpha;
if (any(lessThan(uv - mv, vec2(0))) || any(greaterThan(uv - mv, vec2(1)))) a = 1.0; // off screen: no history
outColor = mix(hist, cur, a);

MSAA costs memory, TAA costs kept frames, FXAA costs one cheap pass, and SSAA costs four of everything.

Under the hood: the math and the code

MSAA spends memory and rasterizer bandwidth: N colour and N depth samples per pixel, so a 4× target at 4K with 32-bit colour and depth is 265 MB before the resolve target. Hardware compresses samples that share a colour, so real bandwidth is lower than the allocation, but the allocation is real.

On a tile-based mobile GPU, which renders the screen in small blocks kept on chip, the samples stay on chip and never touch that memory.

TAA spends memory on history: two RGBA16F buffers (16 bits per colour channel) to swap between, a motion-vector target, and a resolve pass that reads all of them plus a 3×3 neighbourhood every frame. FXAA spends almost nothing: one pass, one input, five taps for the early-out and up to about thirty on an edge pixel. SSAA spends everything four times.

TAA with upscaling, the DLSS 2, FSR 2 and Unreal TSR shape, renders at a lower internal resolution and lets the jitter accumulate detail at output resolution. Its history lives at output resolution, so memory does not shrink with the render scale, but shading does.

In words: bytes are width times height times samples times bytes per sample. The three lines below work that out at 1080p.

bytes = W · H · samples · bytes_per_sample MSAA 4× at 1080p: 1920·1080·4·(4 + 4) = 66.4 MB, + 8.3 MB resolve target TAA history: 1920·1080·2·8 = 33.2 MB, + 8.3 MB RG16F motion FXAA: 1 pass, reads 8.3 MB, writes 8.3 MB, 0 extra allocations

W and H are the output size in pixels. bytes_per_sample is 4 for colour plus 4 for depth in the MSAA line, and 8 per RGBA16F pixel in the TAA line.

Assumptions: 4-byte colour (RGBA8) and 4-byte depth (D24S8) for the methods that work within one frame. TAA uses 8-byte colour (RGBA16F) for the frame and the kept frames plus 4-byte motion vectors (RG16F), because it runs before tone mapping, the step that converts the high-range lit image to screen colours. SMAA adds a 2-byte edge map (RG8) and a 4-byte weight map (RGBA8). Shader-run counts ignore overdraw, pixels drawn more than once.

People say temporal AA is blurry. That describes a bad implementation, not the method: the softness comes from three fixable places, reading the kept frame with the GPU's plain built-in blend every frame (a sharper read, called Catmull-Rom, fixes it), a correction that is too loose and lets stale colours in, and a missing sharpening pass after the blend. Every shipped upscaler includes all three fixes, which is why DLSS 2 output at 67 % scale often looks sharper than a naive native-resolution TAA.
