Post Effects

A game draws its picture, then runs a few last passes over the finished image before it goes to the screen. Bloom puts a soft glow around bright things, depth of field softens whatever is nearer or farther than the thing you are looking at, and motion blur smears whatever moved. Each pass is a filter that reads real data about the picture: how bright each pixel is, how far away it is, how far it moved since the last frame. The thing people get wrong: these are not decoration painted on top. Feed them the wrong data, or run them in the wrong order, and they turn into haze and smears.

Bloom: which pixels get to glow

A player stands in a village street at night with seven street lamps, a lit tavern and the moon. The bright things glow, and one number decides which count as bright.

squeezed for the screen
View

A threshold picks which pixels may glow and a strength scales the glow; the threshold is a brightness, not a list of objects.

Under the hood: the math and the code

The first step is the prefilter. It keeps only pixels brighter than the threshold T. A hard cut at exactly 1.0 flickers when a pixel hovers near it, so a knee K ramps the pixel in gently between T−K and T+K.

In words: fade a pixel in around the threshold instead of cutting it off hard, then add the finished glow to the picture.

br = max(r, g, b) soft = clamp(br − T + K, 0, 2K)² / (4K + ε) c' = c · max(soft, br − T) / max(br, ε)

Here br is the brightest of the three colour channels, c is the pixel's colour and c' is what survives the prefilter.

What this code does: runs the soft threshold, and at the very end adds the glow to the raw picture.

// prefilter, full res: soft-knee threshold
vec3 c = texture(sceneHDR, uv).rgb;
float br = max(c.r, max(c.g, c.b));
float soft = clamp(br - T + K, 0.0, 2.0 * K);
soft = soft * soft / (4.0 * K + 1e-5);
c *= max(soft, br - T) / max(br, 1e-5);   // 0 below T-K, 1 above T+K

// composite: bilinear read of u1, the prefilter itself is never added back
color = sceneHDR + I * texture(bloomU1, uv).rgb;

Shrink, blur a little, grow back and add: about 16 reads per pixel for a glow hundreds of pixels wide.

Under the hood: the math and the code

Next the chain halves the image six times. Each halving is a downsample, a pass that reads 13 taps, where a tap is one bilinear texture read that already averages a 2×2 block. Six halvings at 13 taps give a blur that reaches 6·2⁶ pixels wide for about 16 reads per full-res pixel.

Then the upsample walks back up. Each level applies a 3×3 tent filter (a small blur with a peak in the middle) to the smaller image and adds it to the image at this level. Adding at every step is what gives a bright core with a wide soft falloff, without ever computing a blur that wide.

In words: fade a pixel in around the threshold, average 13 neighbouring reads to make each smaller image, and on the first shrink let dim pixels outvote one very bright one.

down = ½·avg(j,k,l,m) + ⅛·[avg(a,b,d,e) + avg(b,c,e,f) + avg(d,e,g,h) + avg(e,f,h,i)] per texel: e ⅛ · b,d,f,h 1/16 · a,c,g,i 1/32 · j,k,l,m ⅛ (Σ = 1) Karis, mip 1 only: inside each group of 4 taps g = Σ w_t·t / Σ w_t, w_t = 1 / (1 + luma(t))

The letters a to m are the 13 tap positions, and the fractions are how much each one counts. In the Karis line, luma is the perceived brightness of a tap and w_t is its vote.

The firefly is one 400× white pixel. Depending on where it sits, a 2×2 read covers it with one pixel or two, so its energy doubles and halves as it slides. The tiles measure the bloom peak the firefly adds across eight positions and report the swing, max minus min, which is what flickers on screen. The Karis average weights each tap in its group of four by 1/(1+luma), so one 400× tap cannot outvote three dim ones, and the swing drops by more than ten times.

What this code does: builds the first small image from five groups of four reads, with the Karis vote applied inside each group, then grows one level back up.

// mip 1: 13 bilinear taps = five 2x2 groups, partial Karis average
vec3 box(vec2 o) { return texture(src, uv + o * texel).rgb; } // bilinear at a corner = 2x2 box
vec3 grp(vec3 a, vec3 b, vec3 c, vec3 d) {
  if (!firstMip) return 0.25 * (a + b + c + d);
  float wa = 1.0 / (1.0 + luma(a)), wb = 1.0 / (1.0 + luma(b)), wc = 1.0 / (1.0 + luma(c)), wd = 1.0 / (1.0 + luma(d));
  return (a*wa + b*wb + c*wc + d*wd) / (wa + wb + wc + wd);   // one 400x tap cannot outvote three dim ones
}
vec3 g0 = grp(box(vec2(-1,-1)), box(vec2(1,-1)), box(vec2(-1,1)), box(vec2(1,1)));
vec3 g1 = grp(box(vec2(-2,-2)), box(vec2(0,-2)), box(vec2(-2,0)), box(vec2(0,0)));
// g2, g3, g4: the other three outer corners
vec3 down = 0.5 * g0 + 0.125 * (g1 + g2 + g3 + g4);

// upsample, one level: 3x3 tent of the smaller mip, added to this mip
vec3 up = mipHere + tent9(smallerMip, uv, radius);

Glow first, then squeeze for the screen

The same street bloomed twice, in the two possible orders. One of them makes the house walls glow.

glow first, then squeeze
squeeze first, then glow

Blur the raw brightness, then squeeze it to the screen; never the other way round.

Under the hood: the math and the code

On HDR data the threshold at 1.0 is a physical statement: only things brighter than a white diffuse surface glow. In this street that is the seven lamp heads, the tavern's neon sign, the two lit windows and the moon, under 2 % of the pixels. Everything else contributes exactly zero.

After a tone curve every value sits between 0 and 1 and nothing passes a threshold of 1.0. To get any glow, the threshold has to move down to 0.3 or 0.4, and now the beige wall of a house contributes as much as a lamp. The result is a low-contrast fog over the whole frame. The bloom was fine; it ran on the wrong data.

In words: add the glow to the raw brightness first and squeeze once at the end. Squeezing first caps every value below 1.0, so the threshold has to drop.

right: tonemap(hdr + I·blur(thr(hdr, 1.0))) wrong: tonemap(hdr) + I·blur(thr(tonemap(hdr), t)) tonemap(x) = x / (1 + x) never reaches 1.0, so thr(tonemap(hdr), 1.0) = 0 everywhere and t must be < 1

Here hdr is the raw scene colour, thr is the threshold step, blur is the mip chain, I is the intensity slider, and t is the lowered threshold the wrong order is forced to use.

What this code does: the top block keeps everything in raw brightness and applies one curve at the end; the bottom block is the haze version, with the curve first.

// correct: everything in linear HDR, one curve at the end
vec3 hdr   = texture(sceneHDR, uv).rgb;   // ground 0.1, lamps 8..50
vec3 bloom = texture(bloomMip0, uv).rgb;  // chain fed by thr(hdr, 1.0)
vec3 ldr   = tonemap(hdr + I * bloom);
outColor   = encodeSRGB(ldr);

// the haze version, seen in LDR-era pipelines
vec3 ldr0  = tonemap(hdr);               // max value 0.98
vec3 glow  = blur(thr(ldr0, 0.3));        // house walls now pass
outColor   = encodeSRGB(ldr0 + I * glow);  // low contrast everywhere

The same rule applies to depth of field and motion blur: averaging tone-mapped values gives the wrong average. A 50× lamp blurred in HDR still reads as a bright disc after the curve. Blurred after the curve it becomes a grey smudge, because 0.98 spread over 60 pixels is 0.016 each.

Depth of field: blur by distance

Blur size comes from distance to the focus, and near things spill over far things, never the reverse.

Under the hood: the math and the code

A thin lens focuses one distance exactly. A point at any other depth lands on the sensor as a disc, the circle of confusion (CoC), whose diameter grows with the aperture A = f/N and with the distance from the focus plane. The aperture is the hole light comes through: focal length f divided by the f-stop N.

The sign matters. Objects in front of the focus plane (near field, blue) blur over whatever is behind them, including sharp things. Objects behind it (far field, amber) are hidden by sharp things in front. A single blur cannot honour both rules, so engines split the two fields and composite near over far.

The naive method blurs every pixel by its own CoC. The crates' edge stays sharp against the player because the player's pixels have CoC 0 and never gather it, and the in-focus player leaks a halo into the blurred street behind because those far pixels gather the player. The gather with a CoC compare fixes both: a sample contributes only if its own disc reaches this pixel, and a farther sample can only leak onto a pixel that is itself blurry.

In words: work out the disc size from the lens and the distance, then for each neighbour ask whether its disc reaches this pixel, and shrink its vote if it is farther away than a sharper pixel here.

A = f / N aperture diameter, mm CoC = A · |f (d − d_f)| / (d (d_f − f)) on the sensor, mm px = CoC / 36 mm · 256 px this frame (×7.5 at 1920) signed: c = +px for d > d_f (far), −px for d < d_f (near) gather: w_q = clamp(|c_q| − ‖q − p‖ + 1) does q's disc cover p? far: if z_q > z_p then w_q *= |c_p| / c_q occlusion by sharper pixels near: α = Σ w_q / N, out = lerp(far, near, α)

Here d is a pixel's distance, d_f is the focus distance, and 36 mm is the width of the sensor. p is the pixel being shaded, q is a neighbour, c is the signed CoC in pixels, z is depth, w_q is the neighbour's weight, and α is how much near field covers this pixel.

What this code does: loops over N neighbours inside the widest nearby disc, keeps each one only if its own disc reaches this pixel, and cuts its weight when it is farther away than a sharper pixel here.

// half-res far-field gather. coc is signed px, + behind the focus plane
float cocP = texture(cocTex, uv).r;  float zP = texture(depthHalf, uv).r;
float R = texture(tileNeighbourMax, uv).r;      // widest far CoC nearby, 8 px tiles
vec3 sum = vec3(0); float wsum = 0;
for (int i = 0; i < N; i++) {
  vec2 o = kernel[i] * R;                        // circle or hexagon pattern, norm <= 1
  vec2 q = uv + o * texel;
  float cocQ = texture(cocTex, q).r;  float zQ = texture(depthHalf, q).r;
  float w = saturate(cocQ - shapeNorm(kernel[i]) * R + 1.0);   // does q's disc reach us?
  if (zQ > zP) w *= saturate(abs(cocP) / max(cocQ, 1e-3));   // farther sample, sharper pixel: occluded
  sum += w * texture(colorHalf, q).rgb;  wsum += w;
}
vec3 far = sum / max(wsum, 1e-4);
// near field: same loop over cocQ < 0 with R = tile max of -coc,
// alpha = wsum / N, then full res: lerp(lerp(sharp, far, |coc|-0.5), near, alpha)

The sample pattern is the bokeh, the shape a blurred light takes. With a circular pattern every street lamp becomes a disc; with a hexagonal pattern and a hexagonal distance rule it becomes a six-sided iris. At 16 samples and a 12 px radius the disc breaks into visible dots, which is why engines either take 64 samples or run the pass at half resolution, or both.

Motion blur: smear along the movement

A car drives past behind the player while the camera pans. Each pixel gets smeared along the way it moved since the last frame.

Smear along the longest movement in the neighbourhood, and let depth decide who smears over whom.

Under the hood: the math and the code

The car moves in the world; the camera pans. Both end up in the velocity buffer as pixels per frame, written by the geometry pass from where each pixel was this frame and last frame. The shutter is the fraction of the frame the blur covers: at 0.5 it covers half the distance moved in 16.7 ms.

Blurring each pixel along its own velocity stops at the silhouette, because the street behind the car has a different velocity. McGuire's 2012 filter takes the longest velocity per 16 px tile, widens it to the 3×3 tiles around (that is the dilation), and samples along that instead. Each sample then gets a weight from whether its own velocity is long enough to reach this pixel, so the still street stays sharp while the car's colour spreads over it.

The depth terms decide which way the smear goes. The car must smear over the street behind it, but it must not smear over the player standing in front of it, and a moving street behind a still car must not eat the car's edge.

In words: walk N steps along the longest nearby movement. A sample counts if it is in front and moving enough to reach us, or if we are in front and moving enough to reach it, or if both move together.

v_max = neighbourMax(tileMax(v)) 16 px tiles, 3×3 dilation p_i = p + v_max · (i/N − ½) · shutter N samples along the longest vector d_i = ‖p_i − p‖ cone(d, v) = clamp(1 − d / ‖v‖) sample's blur reaches distance d cyl(d, v) = 1 − smoothstep(0.95‖v‖, 1.05‖v‖, d) front(a, b) = clamp(1 − (a − b) / Δz) 1 when b is in front of a w_i = front(z_p, z_i)·cone(d_i, v_i) blurry thing in front smears over us + front(z_i, z_p)·cone(d_i, v_p) we are in front and blurry ourselves + 2·cyl(d_i, v_i)·cyl(d_i, v_p) both moving together

Here v is a pixel's velocity, p is the pixel being shaded, p_i is the i-th sample position and d_i how far away it is. z is depth and Δz the soft depth margin. cone says how far a moving pixel's blur reaches, cyl is a soft "about the same distance" test, and w_i is the sample's final weight.

What this code does: reads the longest velocity around this pixel, steps along it N times with a small per-pixel jitter, and weights each sample by the depth and reach tests above.

vec2 vN = texture(neighbourMax, tileUV).xy * shutter;  // longest velocity in 3x3 tiles
if (length(vN) < 0.5) return colorX;
float wX = 1.0 / max(length(vX * shutter), 0.5);       // centre weight, McGuire 2012
vec3 sum = colorX * wX; float wsum = wX;
for (int i = 0; i < N; i++) {
  float t = (i + 0.5 + jitter) / N - 0.5;              // jitter per pixel breaks banding
  vec2 p = uv + vN * t * texel;
  float d = abs(t) * length(vN);                        // distance walked, px
  vec2 vY = texture(velocity, p).xy * shutter;  float zY = texture(depth, p).r;
  float f = saturate(1.0 - (zX - zY) / SOFT_Z);         // Y in front of X
  float b = saturate(1.0 - (zY - zX) / SOFT_Z);         // X in front of Y
  float w = f * cone(d, vY) + b * cone(d, vX) + 2.0 * cylinder(d, vY) * cylinder(d, vX);
  sum += w * texture(color, p).rgb;  wsum += w;
}
return sum / wsum;

Post passes are cheap per pixel and expensive per frame; shrink the image before you blur it.

Under the hood: the math and the code

The order in the bar is a common one: motion blur and depth of field want linear HDR and depth, bloom wants the result of those, tone mapping ends the HDR part, and anti-aliasing or the upscaler follows. Orders vary. Unreal runs its temporal AA before motion blur and bloom so that the blur hides temporal noise. DLSS, FSR and XeSS are built to sit where temporal AA sat, so everything after them runs at output resolution.

Depth of field at half resolution costs a quarter of the gather and needs one extra composite pass. Bloom starting from a half or quarter mip costs almost nothing.

In words: a pass costs its pixel count times a fixed time per pixel, and a colour image costs 8 bytes per pixel.

ms ≈ pixels · ns_per_pixel motion blur 0.30 · DoF gather 1.6 · bloom 0.30 per start-res px tone map 0.12 · TAA 0.35 · upscaler 0.28 per output px · UI 0.05 bytes = pixels · 8 (RGBA16F) per colour target, · 4 for RG16F velocity or 32-bit depth

ns_per_pixel is the per-pass cost in nanoseconds, listed on the right. RGBA16F is four 16-bit channels per pixel, so 8 bytes; RG16F velocity and 32-bit depth are 4 bytes each.

The budgeting trap is that post effects look free one at a time. Every one of them touches every pixel every frame, and at 4K that is 8.3 million pixels per pass, so six passes at a few hundred picoseconds each add up to 2–5 ms of a 16.7 ms frame. That is why depth of field runs at half resolution, bloom starts at a quarter, and motion blur is the first thing switched off on a performance preset.
